# Design

## Продолжение после ce0679c7 — 14.10.2026

Согласованный план реализуется в прежних №168/169 без нового инструментария. №168 уменьшает дубли/обвязку и усиливает существующие UI cases; №169 закрывает конкретные runtime gaps в существующем изолированном CI. Сначала буквальная карта удаления с сохраняемыми условиями, затем edits по разграниченным владельцам. PostgreSQL гонки/rollback/Decimal, HTTP denial до чтения body, storage errors и actual source provenance не заменяются mock/source-string проверкой. Warehouse guards требуют отдельной подтверждённой передачи, а не слепой смены pin.

После freeze выполняются затронутые существующие suites и один итоговый локальный прогон, затем один обычный CI и реальный staging. Счётчики включают весь добавленный код; отсутствие новой квоты не отменяет прозрачный подсчёт. Исторические accepted receipts и checkbox разделов 1–5 сохранены; завершение нового раздела 6 требует evidence нового кандидата.

## Context

См. `proposal.md`. Web запускает `tsx --test tests/*.test.ts tests/*.test.mjs`; существующая `docs/testing/contract-matrix.json` привязывает критические контракты к файлам и test blocks. В QA есть ручные entrypoints, для которых отсутствие импортов не доказывает неиспользование.

## Goals / Non-Goals

**Goals:** не менее 50% чистого сокращения строк в прежнем tracked-text scope: web 64 722 → не более 32 361, совокупно 69 662 → не более 34 831; сохранить содержательные проверки действующего бизнес-поведения, данных, безопасности и UI приложения, работающую команду тестов и точную причину каждого удаления. Весь добавленный test/QA код общего runner и перенесённых cases включается в итог, вынос за границы scope не считается сокращением. Числа файлов/suites отражают итоговую структуру, но не служат заменой сохранности контрактов.

**Non-Goals:** новая система метрик, новые тесты ради удаления, minify, изменение runtime, зависимостей, бизнес-данных или исторических evidence.

## Decisions

1. В `reduction-map.md` до удаления фиксируется точный allowlist: удаляемый файл/блок → сохраняемый действующий контракт приложения и уровень доказательства либо точная причина obsolete/закрытого QA/тавтологии/always-green/постоянного skip без действующего покрытия. Отдельные уникальные assertions закрытого QA-helper не требуют переноса. Цель 50% обязательна; совпадение имени, одинаковый setup или сама квота не оправдывают потерю действующего контракта приложения.
2. При пересечении source-string и исполняемой проверки сохраняется проверка поведения; действующие route/ACL/денежные и native/browser условия остаются. QA-копия удаляется при каноническом entrypoint либо явно закрытом workflow с проверенными текущими потребителями. Отсутствие импортов не доказывает obsolete самостоятельного CLI: нужны evidence закрытия задачи и проверка операторских entrypoints. Retirement старого CLI не объявляется выполнением его прежних native/browser сценариев на новом SHA.
3. Удаления выполняются по буквальным путям после проверки абсолютной границы checkout и reparse points всех предков. Общие helpers удаляются только вместе с последним подтверждённым потребителем.
4. Обновляются только существующие живые ссылки и контрактная карта. Исторические OpenSpec receipts не переписываются. По явному уточнению владельца разрешён малый общий runner только для замены существующих test/QA/native контуров с чистым минусом строк и сохранением действующих условий приложения; самостоятельная QA-система, новые проверочные слои и скрытие кода из счётчика в объём не входят.
5. Повторяемые native lifecycle/guards допускается объединять через существующие доменные helpers или такой общий runner, сохраняя действующие exact target binding, ownership/CAS, rollback и проверку baseline, drain/close clients, money/S3 и UI условия. Исполняемые автоматические проверки сохраняют свой уровень доказательства: native `NOT_RUN` не заменяет выполненный test block. Замена действующего native контура требует карты сохранённых business/data/security cases и их фактического выполнения; retirement obsolete selftest закрытого helper требует точной причины, а не нового теста его старого assertion.

## Risks / Trade-offs

[Потеря уникального условия] → сопоставление до удаления и независимое review; money/ACL/CAS/idempotency/rollback/S3/native guards сохраняются.

[Ручной QA нужен оператору] → действующая замена либо evidence закрытия задачи и отсутствие текущих потребителей/операторского использования; только отсутствие импортов не считается основанием.

[Метрики вводят в заблуждение] → одинаковый tracked-text scope до/после и отдельно число suites; уменьшение не достигается форматированием.

## Migration Plan

Миграций нет. Первая фаза завершена и принята на `e986e290`; её команды и receipts остаются в `verification.md` как отдельный факт. Продолжение после уточнения цели требует нового allowlist и консолидации, проверки live refs и уникальных контрактов. После завершения параллельных edits оркестратор один раз выполняет полный автоматический прогон, typecheck/lint, OpenSpec validation и `coverage-baseline.mjs --check`. Зафиксировать счётчики и отсутствие runtime diff; после review выполнить обычный merge в staging, CI, проверку нового SHA/образа/здоровья и GET-only smoke.

## Next Architecture Option — USER_APPROVED_FOR_169

Возможный следующий этап для цели 50%: один управляемый integration environment с ephemeral CI PostgreSQL, S3 и web, без реальных данных, с exact target guards, обязательным lifetime и автоматическим завершением собственных ресурсов.
