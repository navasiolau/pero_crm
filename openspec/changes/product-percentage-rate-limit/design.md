# Design

## Context

Согласованный шаг0.5 находится в отдельной76; округление новых денег —77. Generic parsePercentageRate используется также для исторических snapshots и долей до100%.

## Goals / Non-Goals

**Goals:** новые ставки/начисления трёх специалистов0–15, невозможность ввести больше15.
**Non-Goals:** денежный backfill, изменение старых snapshots, лимит15 на доли распределения, новая миграция.

## Decisions

Отдельный MAX_PRODUCT_PERCENTAGE_RATE=15 и parser новых ставок, использующий generic parser и проверку верхнего предела. UI допускает прежнюю syntax/precision, но запрещает draft>15; step clamps15. Patch валидирует новое значение после replay/CAS; expectedValue старой ставки допустим. Direct completion проверяет новую положительную ставку перед деньгами; исторический/frozen retry остаётся прежним.

Стандартные ставки этих этапов получают тот же max15, сохраняя точность0.1 и отсутствие стрелок. Чтение snapshot/expectedRates допускает прежние0–100, чтобы сохранённые настройки можно было исправить; новые defaults и создание продукта из defaults проверяются до записи.

Интеграция обычным merge76/80 объединяет на одной строке шаг50сотых и максимум1500сотых; после разрешения конфликта повторить граничные UI/controller тесты. Новая version4 SQL-проверка77 сохраняет допустимость уже созданной истории; ограничение новых действий обеспечивается доменным серверным кодом.

## Risks / Trade-offs

Сохранённая ставка>15 → история читается неизменно, новые начисления требуют исправления ставки; первый шаг приводит draft к15. Подмена запроса → серверное отклонение без записи. Одновременные saves → прежние CAS/UUID/rollback.
