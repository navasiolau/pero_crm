# Design

## Context

См. proposal.md. Состав хранится в LogisticsTrip, денежные снимки — в LogisticsPosting. Требование ТТН проверяется схемой, posting-core, payment-context и отложенным PostgreSQL trigger. Обновление оплаченного рейса выполняется только вместе с исправлением расхода.

## Goals / Non-Goals

**Goals:** согласованная проверка исключения на всех уровнях и сохранение истории.
**Non-Goals:** изменение ролей, обычных расходов, складских движений или статусов изделий.

## Decisions

1. Добавить NOT NULL boolean ttnNotRequired DEFAULT false в Trip и Posting. В отличие от проверки текущего флага рейса, собственный снимок проведения сохраняет основание старой ревизии.
2. Create нормализует отсутствие поля в false; update и optional manifest коррекции сохраняют отсутствие до разрешения по текущему рейсу под lock. Включить значение в snapshots и fingerprint.
3. documentIds допускает пустой массив; решение о допустимости принимает сервер по сохранённому/атомарно обновляемому manifest. Каждый переданный ID всё равно проверяется. Внутренний Payment проверяет снимок Posting, PostgreSQL проверяет тот же снимок.
4. Сохранить общий денежный lock, CAS ревизии и текущие receipts. Загрузка документа не меняет денежную ревизию.

## Risks / Trade-offs

- Проверка только UI оставит обход → серверный writer и PostgreSQL сохраняют независимые проверки.
- Пропуск нового поля старым клиентом сбросит флаг → сохранять прежнее значение в update/correct.
- Изменение флага повлияет на историю → собственный неизменяемый scalar Posting и manifest snapshot.

## Migration Plan

Аддитивная миграция двух boolean и замена функции проверки только в части необходимости ТТН. Исторические строки получают false. Local5433 и staging без дампов/reset/seed; production — после приёмки и отдельного разрешения с одним проверенным dump по AGENTS.md. Обратная миграция не удаляет сохранённую историю.
