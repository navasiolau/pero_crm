# Proposal

## Why

Общая загрузка теряет причины ошибок storage и может вернуть ошибку после сохранения файла. Предыдущая S3 QA успешна, текущая причина пользовательского сбоя пока не установлена.

Прямое уточнение владельца 03.10.2026: первый выбранный файл обложки проекта отклоняется клиентской проверкой контекста PHOTO≠undefined. Сохранённый recovery context также блокирует новый выбор. Требуется обычная загрузка выбранного файла для текущей сущности без видимых действий проверки/повтора прежней загрузки. Причина отдельного server non-JSON HTTP500 пока UNKNOWN.

## What Changes

- Явный CRM_FILE_STORAGE=s3|local; неполная S3 конфигурация не включает диск.
- Закрытый безопасный JSON ошибки с code/requestId/phase/message/commitState.
- UUID повтор обычной загрузки, атомарные File и audit receipt, уведомление после commit.
- Исходные байты и существующие ACL/CAS/форматы сохраняются.
- Новый выбранный файл получает fresh request для текущей сущности; выбор блокируется только во время busy. Удаляются все видимые «Проверить прежнюю загрузку»/«Повторить…» и блокировки по stale recovery ref/context во всех upload UI; в каталоге меняется только upload recovery.
- Friendly error и безопасные копируемые технические подробности сохраняются; неизвестный ACK не считается успехом. Фактическая регрессия проверяется через rendered file picker → browser POST → настоящий staging S3.

## Capabilities

### New Capabilities
- `reliable-file-upload`: определённое хранилище, диагностируемая и повторяемая загрузка.

### Modified Capabilities

Нет.

## Impact

lib/s3.ts, сервер загрузки, POST /api/files/upload и upload UI. Диагностика задачи48 и server/CAS обложки задачи53 сохраняются; их прежние требования видимого explicit retry заменены прямым решением 03.10 только для клиентского upload recovery. Нет схемы/миграции или инфраструктурных изменений. Production не затрагивается. Deployment должен явно задать storage mode.
