# Design

## Context

См. proposal.md. Product.number уже защищён partial UNIQUE только для deletedAt IS NULL. Общая mutation transaction и блокировка Project существуют; КП использует временные номера, сохраняет стабильные ID и инвалидирует прежние адреса.

## Goals / Non-Goals

**Goals:** единый вычисляемый порядок живых изделий, согласованность обычных операций и КП, точечная исправляющая операция с проверяемым повтором.

**Non-Goals:** schema migration, массовая обработка production, изменение project numbering, пересчёт денег, переписывание исторических документов, новый пользовательский редактор номера или публичный endpoint.

## Decisions

- Общий numbering core читает и блокирует действующие строки проекта; порядок suffixInt ASC NULLS LAST, createdAt ASC, id ASC. Только изменяемые номера освобождаются временным UUID-префиксом и назначаются окончательно в той же tx; каждый сдвиг получает аудит. COUNT+1 без нормализации отклонён: существующие пропуски могли бы давать коллизии.
- Стандартное создание нормализует состав после всех проверок входа и настроек, перед insert. Внутренний вызов из КП явно откладывает нормализацию, поскольку порядок там задаётся полным снимком позиций. Удаление сначала стабилизирует ссылку скрываемого изделия, затем скрывает и нормализует остаток; receipt сохраняет список изменённых номеров для повторной инвалидации.
- Старые Notification.link по затронутому активному номеру переводятся на ID до переиспользования номера; query/hash остаётся буквальным. Новые публичные параметры не добавляются; metadata инвалидации остаётся внутренней.
- Операторский TS core использует общие блокировки, точный baseline (ID, updatedAt, состав и hash защищённых данных), deterministic receipt ID и проверку результата до commit. CLI ограничен проектом №1 и 1.64 → 1.15, проверяет host/app revision/storage/DB identity, поддерживает check/apply/rollback; секреты и baseline хранятся только в ignored evidence.
- После прямой исправляющей операции проверяются свежие HTTP/браузерные страницы: product/list pages force-dynamic. Обычные app mutations используют существующий revalidateProductPaths для каждого сдвинутого ID и прежнего номера.

## Risks / Trade-offs

- Перенумерация может инвалидировать открытую форму → updatedAt меняется, существующий CAS отказывает устаревшему сохранению.
- Partial UNIQUE немедленный → временные номера существуют только внутри tx и откатываются при ошибке.
- Ссылка по старому номеру после переиспользования неоднозначна → внутренние ссылки фиксируются по ID; новые aliases соответствуют текущему составу.
- Первоначальный check отверг ошибочное предположение о 1.1–1.14. После отдельного разрешения владельца выполнен READ ONLY: действуют 1.2–1.5, 1.7–1.12, 1.14, 1.61–1.64, удалённых нет. Владелец выбрал только 1.64 → 1.15. CLI фиксирует именно этот состав и прочитанный ID, не нормализует остальные production-строки; любое новое расхождение блокирует apply.

## Migration Plan

Без миграций. Локальная существующая БД 5433, штатный CI и staging на точном SHA. Владелец 04.11.2026 разрешил commit/release на production и отдельно поручил заблаговременный production-дамп; перед выпуском создаётся одна копия и проверяется изолированное восстановление. Local/staging дампы и restic не используются. После принятого production deployment выполняется отдельный check/apply и read-only приёмка. Обратная операция проверяет unchanged post-state и пишет компенсирующий аудит; старый дамп автоматически поверх рабочей БД не восстанавливается.
