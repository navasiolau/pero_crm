# Design

**Execution agreement:** Номер задачи 125, ветка feature/125 согласованы владельцем 10.10.2026; OpenSpec и реализация одобрены. Одна целевая локальная проверка, затем существующий полный CI без изменений и развёртывание на staging только через него; одна целевая staging-приёмка. Повторные полные ручные проверки не выполнять без конкретного сбоя. Production/main этим запуском не разрешены.

## Context

Мотивация — в `proposal.md`. Зависимости: `logistics-trips-and-ttn` и `logistics-cash-allocation`. Исследован свежий `origin/staging` `ab1c77f3b82cab788f206914d5b2a063e6aafe68`.

Карточка проекта использует `ProjectTabs`, допустимые `?tab=` и ролевые серверные проекции. Снабженец уже имеет readonly офисный и финансовый доступ. Бухгалтер ограничен финансовым workspace; новая возможность получать ТТН не должна раскрывать ему техническую карточку. Общие примитивы — `DataTable`, `SearchableSelect`, `FileViewer`, `ConfirmDeleteDialog` и унифицированная обработка загрузки.

## Goals / Non-Goals

**Goals:** один реестр и один редактор рейса, переиспользуемые в проекте; понятные доли и сводка бюджета; реальная защита выдачи данных и файлов.

**Non-Goals:** дополнительный календарь/канбан рейсов, карта, интеграция 1С/интернет-магазина, новые права менеджмента, новый механизм пересчёта склада или общих пользовательских списков.

## Decisions

1. **Общий реестр `/logistics`.** Для полного доступа колонки: дата, связанные проекты, состав отгрузки, общая стоимость/валюта, касса, доли, ТТН и состояние оформления. Один trip ID создаёт одну строку независимо от числа проектов. Поиск/сортировка/пагинация — существующий `DataTable`; фильтры по проекту, периоду и документам. Переход по строке открывает общий редактор. Состояние самого списка не заимствуется из предпочтений Projects/Products.

2. **Проектная вкладка.** Список использует тот же trip ID и данные, отфильтрованные по связи проекта. Помимо общей суммы явно выводятся «Доля проекта, %» и «Затраты проекта, BYN». Над списком — «Доставка по КП», «Потрачено», «Остаток» либо «Перерасход»; отсутствующий бюджет помечается «Не указан». Фактические затраты вычисляются по активным логистическим распределениям этого проекта; сводка использует сохранённые BYN-суммы его долей. Исправление общего рейса из одного проекта отражается во всех его проектах.

3. **Одна форма и server-owned расчёт.** При открытии из проекта он предвыбран; можно добавить другие проекты и их изделия/материалы. Один проект получает 100%. При добавлении второго сотрудник задаёт проценты, UI показывает остаток до 100% и расчётные суммы, сервер повторно валидирует всё. Стоимость вводится одной суммой в валюте кассы и прямо записывается в расходы проектов по долям. По прямому уточнению владельца в UI отсутствуют настройка или выбор статьи, предварительная конфигурация ExpenseArticle/OrgSetting для проведения не требуется. До «Списать из кассы» нужен сохранённый файл ТТН и подтверждение её стадии с одной печатью. После возврата добавляется файл со второй печатью. Наличие печати подтверждает сотрудник, автоматической проверки изображения нет.

4. **Бухгалтер получает отдельную узкую проекцию.** В том же пункте «Логистика» ему доступны дата, номер/идентификатор отгрузки, номера проектов и ТТН; отсутствуют логистические writes и новая техническая информация. Файлы доступны через защищённый маршрут. Проектная логистическая вкладка добавляется только полным логистическим ролям; бухгалтерский финансовый workspace продолжает работать по прежним правилам. Совмещённый `ACCOUNTANT+PROCUREMENT` получает полный доступ через union.

5. **Права проверяются до формирования данных.** В `roles.ts` появляются отдельные наборы чтения документов и управления, в nav/auth/server actions/queries/HTTP используются они. Недостаточно скрыть TabsTrigger: закрываются прямой `/logistics`, `?tab=logistics`, action, file ID и внутренние JSON/RSC-проекции. Если роль потеряна, прежняя ссылка перестаёт раскрывать документ. Общая бухгалтерская возможность не превращается в OFFICE_ROLES grant.

6. **Исправление использует ревизию.** Форма передаёт актуальную revision и mutation ID. Изменение общего рейса показывает затронутые проекты и текущие/новые суммы; stale form получает конфликт, не откатывая чужую успешную правку. Связанные финансовые строки имеют ссылку на рейс; отдельно менять/удалять их нельзя. Двухпечатная ТТН добавляется без нового списания.

## Risks / Trade-offs

- Менеджер видит логистический документ через общие Files → отдельный документальный namespace и тест прямой выдачи; обычные файловые проекции не содержат ТТН.
- Полная стоимость рейса принята за расход конкретного проекта → разные подписанные колонки и показ доли рядом с суммой.
- Бухгалтерская ссылка раскрывает проект → документальная проекция ограничена минимальными метаданными, технический route guard сохранён.
- На мобильном экране таблица выходит за границы → существующий контейнер горизонтального просмотра, адаптивная форма и проверки 1440/390.

## Migration Plan

Отдельной UI-миграции не требуется. После принятия первых двух changes подключить route/menu/tab и общие формы. На staging проверить реального пользователя со снабженческой ролью, ADMIN/DIRECTOR, бухгалтера и запрещённые чистые роли; QA-набор ограничен своими строками и очищается без удаления исходных данных. Один рейс на два проекта проверяется от кассы до обеих маржей и ТТН.

В рабочей ветке от свежего staging пройти локальные проверки; ordinary merge и CI через GitHub API с установленным read-only токеном; отдельно сверить deployed SHA/image/health и пользовательские сценарии. Номера трёх задач согласовываются перед ветками. Production — только по прямому указанию, после всей приёмки; restic и local/staging дампы исключены.
