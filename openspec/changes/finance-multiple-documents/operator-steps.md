# Операторские шаги №195

Этот файл описывает операции root и не означает их выполнение. Разрешение на миграцию/production оценивается по текущему поручению владельца. Обязательны `D:/Projects/pero_infra/infra-recovery/SAFETY-RULES.md`, СТОП при несовпадении target guard. Restic не используется.

## До применения

1. Подтвердить ожидаемую среду и DB identity read-only: host/port, database/schema/user, PostgreSQL major, точный Git SHA и список `_prisma_migrations`. Local — только существующий разрешённый PostgreSQL 5433, legacy 5432 исключён. Секретные URL не выводить. Не создавать reset/seed/новый стенд.
2. Сверить checksum всех уже применённых миграций с имеющимися принятыми исключениями; новая pending должна соответствовать именно `20261022090000_finance_multiple_documents`. Новые расхождения — СТОП.
3. Сохранить read-only counts/хэши существующих FinanceDocument (включая IDs, key, hash, authorship), Payment и request receipts. Это небольшое доказательство метаданных, не dump и не копия объектов. У legacy payment с `reportDocumentId` проверить FK/уникальность и отсутствие логистической привязки к обычному отчёту. Backfill не меняет эти строки.
4. На production с миграцией применять только отдельно утверждённый порядок: один временный дамп затронутой БД перед выпуском, реальный совместимый изолированный restore, сохранённый rollback образ/config. Local/staging dump не создавать.

## Применение и проверки

5. Оператор применяет подготовленную миграцию в согласованном окне. SQL содержит `BEGIN/COMMIT` и блокировку Payment: backfill и включение legacy-sync становятся видны атомарно. При lock/error не обходить guard и не менять applied checksum вручную.
6. До первого нового бизнес-запроса проверить: число новых связей равно числу non-null legacy `reportDocumentId`; каждая старая ссылка имеет ровно позицию 0; FinanceDocument, Payment и прежние request receipts имеют прежние counts/хэши. Проверить unique documentId, unique(paymentId,position), FK и три новых функции/четыре триггера. Все прежние logistics triggers и `check_logistics_posting_total` сохранены.
7. Native guarded acceptance на разрешённой цели: старый single/no-document replay не пишет деньги; новый расход с тремя файлами даёт один Payment и позиции 0/1/2; закупка даёт один StockMovement+Payment; чужой/PENDING/занятый/повторный ID и смешанные поля отклоняются без частичных денег/связей. Проверить конкурентное связывание одного документа двумя операциями и deferred-set/logistics invariants. Тесты не должны создавать новый стенд автоматически при несовпадении guard.
8. Реальный staging SHA/образ: три выбранных файла, partial UNKNOWN, повтор ровно одного UUID, drop/paste всех файлов, исключение ошибки, закрытие/новое открытие формы, точный повтор сохранённой денежной операции. Сверить web/API/бот; все файлы доступны в списках, поиске, книге проекта, ведомости касс и оплаченных складских приходах на desktop/mobile. У логистики видны все ТТН. Закупщик не получает новых payroll-данных, обычные финансовые роли/scopes прежние.

## Откат

## Общий production-выпуск №190–196

Перед выпуском владелец принимает фактический staging SHA и отдельно разрешает main/production-миграцию. Повторное согласование уже выданного разрешения не требуется. Выпуск выполняется по AGENTS.md: только fast-forward принятого staging в main; новый SHA требует проверки затронутого поведения. Production до этого этапа не изменяется.

В пакете одна schema migration — `20261022090000_finance_multiple_documents`; №190/193 имеют отдельные идемпотентные операторские стадии. Перед production-миграцией создать ровно один временный дамп затронутой БД и проверить настоящее изолированное восстановление совместимой версией PostgreSQL. Сохранить прежние образ и конфигурацию, точную identity БД/тома и recovery artifacts по установленному release-порядку. Local/staging дампы, reset/seed и Restic не требуются и не допускаются.

После штатного deploy проверить фактические SHA/образы/здоровье web и бота. Затем через одобренный production transport с живой проверкой цели и отсутствия прежних writers выполнить plan/review/apply для cutoff №190 и переноса статусов №193. Target `kind:'production'` требует фактический imageDigest, БД `crm/public` и точный systemIdentifier; staging proof и флаг согласия не заменяют production proof. Прямые CLI остаются INERT, подключения/запуска из web/API/cron нет. Все планы, UUID, hashes и результаты сохраняются; неопределённый ACK повторяется с прежним UUID и планом.

Подтвердить миграцию, число legacy-связей и старые финансовые receipts, закрытие только открытых timer, согласованное отображение статусов, отсутствие новых начислений/выпусков/заданий cleanup от технического переноса. При успешной миграции и проверке временный дамп удалить только по точному пути, когда он больше не нужен; при ошибке или неясности сохранить. Автоматической физической очистки S3 в этом выпуске нет.

## Откат приложения

Откат приложения сохраняет additive таблицу и файлы; старый клиент видит первый документ через прежний FK, дополнительные связи сохраняются. Откат не включает удаление документов, S3 cleanup или переписывание receipts. При ошибке миграции/неясности артефакты восстановления сохраняются. Production-временный дамп удаляется только root по точному пути после успешной приёмки, когда больше не нужен.
