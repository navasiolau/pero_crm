# Design

## Context

Сейчас Payment.reportDocumentId имеет unique FK, а загрузка и диалоги принимают один файл. Платежи и закупки используют разные исторические fingerprints: платеж включает null для отсутствующего документа, закупка пропускает поле. UNKNOWN денежной операции сохраняет исходный запрос. Логистическое проведение отдельно защищено deferred-инвариантом миграции 20261010143000.

## Goals / Non-Goals

**Goals:** упорядоченная атомарная коллекция при прежних денежных блокировках; байтовая совместимость прежних fingerprints; все файлы в существующих читателях; надёжный повтор отдельной загрузки.

**Non-Goals:** изменение права FINANCE_ROLES, файлов Payout/прихода, редактирование проведённых операций, удаление файлов и изменение транспорта загрузки.

## Decisions

1. PaymentReportDocument(paymentId, documentId, position) с составным PK, unique documentId и unique(paymentId,position). Legacy FK сохраняется как совместимый первый документ. Backfill только создаёт связи. Deferred DB-проверка запрещает разные платежи в legacy и новой связях, обычные документы у логистики и неподтверждённые файлы у новых связей; legacy-вставки синхронизируются в коллекцию. История и storageKey не переписываются.
2. Новый reportDocumentIds[] взаимоисключающ с reportDocumentId, дубликаты запрещены, порядок значим. Новый формат получает отдельную версию fingerprint; отсутствие нового поля оставляет старый алгоритм буквально прежним. Receipts не переписываются. COMMITTED проверяет полный упорядоченный комплект.
   Совместимость включает ранее допустимый INCOME + одиночный reportDocumentId. Новый массив у INCOME запрещён; UI/бот прихода не получают загрузку. Additive followup `20261022110000_finance_document_legacy_income_compatibility` разрешает такому приходу только position=0 с documentId, равным legacy FK. Применённая `20261022090000` остаётся побайтно прежней.
3. Под общей денежной транзакцией каждый файл проверяется как READY, загруженный текущим активным актёром и свободный в обеих связях. Привязки создаются вместе с Payment; ошибки откатывают весь комплект и деньги.
4. Читатели используют одну общую проекцию коллекции с legacy fallback; логистическая проекция возвращает все ТТН. Один payment остаётся одним денежным фактом. Старый reportDocument в read-контрактах остаётся первым элементом для совместимости.
5. UI хранит очередь отдельных файлов: QUEUED/UPLOADING/READY/UNKNOWN/ERROR. На каждый файл один стабильный UUID; отправка по одному через существующий endpoint. UNKNOWN повторяется только с тем же UUID/файлом. Пользователь исключает проблемную строку без очистки хранилища. Денежная отправка заблокирована до разрешения очереди. Бот расширяет только существующие шаги документов, добавляя список и кнопку продолжения; старые сохранённые одиночные/UNKNOWN денежные запросы отправляются неизменно.

## Risks / Trade-offs

- Смешанные версии клиентов → legacy FK и синхронизация сохраняются, новые массивы версионированы отдельно.
- Сбой ответа после загрузки → отдельная строка UNKNOWN с тем же UUID, без повторов всего комплекта.
- Неявная потеря документов в одном читателе → общий select/view и проверки трёх файлов/всех ТТН.
- Требуется настоящая PostgreSQL-проверка deferred/unique/FK и UI на развёрнутой схеме → отдельный операторский этап, без заявления о выполненной runtime-приёмке в этой ветке.

## Migration Plan

Оператор проверяет точный target, применяет additive миграцию `20261022090000_finance_multiple_documents`, сверяет число legacy-ссылок и backfill и запрещённые конфликты. Ни файлового копирования, ни S3 удаления нет. На staging требуется native transaction/race/replay-приёмка и браузер/бот. Для production с миграцией применяется утверждённый порядок одного временного дампа и реального изолированного restore; эту операцию выполняет root отдельно. При откате приложения новая таблица и документы сохраняются; старый клиент видит первый файл, дополнительные связи не удаляются.
