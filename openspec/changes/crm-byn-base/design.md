# Design

## Context

Исследование исходников f036823: проектные Server Actions вызывают общее `projects/core.ts`; create schema принимает произвольную строку currency с default BYN, update schema — optional currency. Это ядро используется API/Telegram. `finance/queries.ts` суммирует Payment.projectAmount и местами при ошибке курса подставляет исходное число. `payroll/queries.ts` читает изменяемую orgSetting и агрегирует amount без currency. Денежные helpers cash-ledger уже используют Decimal и фиксируют BYN/кассовые снимки.

Первичное проектирование опиралось только на исходники. После разрешения 02.10.2026 реализация начата, сведения staging-preflight предоставлены оркестратором и приведены ниже. Статус локальных проверок и приёмки фиксируется в tasks по фактическим финальным logs; наличие артефактов само по себе завершённость не доказывает. См. proposal для мотивации.

## Goals / Non-Goals

**Goals:** единый небольшой денежный policy/helper для действующих writers и достоверных агрегатов; общий отказ до записи; сохранение валютных касс, immutable snapshots и ролевой видимости.

**Non-Goals:** универсальное inline-ядро №17–18, initialPrice №26, изменение процентной базы/получателей №23–24, отмена allocation groups №22, новый FX-механизм/миграция истории или изменение production.

## Decisions

### Политика на сервере, без переключателя обхода

Зафиксировать BYN как внутреннюю валюту в общей доменной политике; create без currency означает BYN, явный не-BYN отвергается, update валюты допускает только BYN при сохранении существующих currency guards. Не скрывать ошибочный currency простым удалением неизвестного поля при parsing. Бот/API вызывают то же ядро; stale формы/`npc:*` не обходят политику. `setPayrollCurrency` сохраняет текущие права ADMIN/DIRECTOR, но отклоняет не-BYN. Новые начисления/выплаты независимо от прежней orgSetting используют BYN после activation gate.

Альтернатива «только скрыть select» оставляет server bypass; runtime-флаг и массовый rewrite добавляют ненужные пути обхода/данные. Выбран проверяемый gate выпуска, без нового env/DB-флага.

### Разделить новые writers и исторические факты

Проверить и покрыть BYN policy в `products/actions`, `works/actions`, `tasks/actions`, `tasks/share-core.ts`, `tasks/completion-core.ts`, `product-stage-pay/core.ts`, `product-percentage-pay/core.ts`, `payroll/actions.ts`, `payroll/cash-core.ts`, `payments/core.ts`, `/api/v1` и их общих helpers. PriceItem/Work не несут currency: если старая настройка зарплаты была не BYN, простая смена подписи не доказывает единицу старых цен. Для будущего production подтверждение владельцем согласованности таких записей остаётся gate; разрешённая staging-приёмка проверяет BYN-настройку и ограниченный fail-closed, не делает пересчёт или backfill. Для оставшегося non-BYN проекта новые денежные writes отвергаются локально; разрешённые неденежные правки продолжают работать.

Retry frozen PENDING_FX — продолжение уже зафиксированной исторической операции, исключение из правила новой ставки: сохранённые валюты/база/получатели не заменяются BYN policy, разрешается завершение того же снимка с существующей идемпотентностью. Для внутреннего итога пригоден только сохранённый bynAmount после корректного расчёта; retry не меняет текущую ставку и не создаёт второе начисление.

Исторические allocation groups, priceSnapshot/executorShare и незавершённые группы сохраняют исходную единицу/снимки. Новое начисление по такой истории не трактует старую валютную базу как BYN; неподтверждённый эквивалент отклоняет только это действие. Формулы распределения №22 не меняются.

### BYN-проекции из сохранённых снимков

Для BYN-проектов Payment.bynAmount — база оплат/расходов и строк внутренней экономики; исходные amount/currency и projectAmount сохраняются. StockMovement.totalByn и BYN прайсовые суммы включаются в Decimal-агрегат. ProductStageSettlement/ProductPercentageCompletion используют существующие фиксированные BYN-поля, не начисляются повторно и не переписываются; связанный PayrollEntry не учитывается второй раз. Existing foreign payroll без фиксированного эквивалента не пересчитывать сегодняшним НБ РБ.

В payroll/my/summary/CSV/dashboard/боте вернуть типизированное состояние суммы: доступный BYN либо недоступность с причиной; UI не показывает 0/NaN/исходное число под BYN. Исторические строки отдельно показывают сохранённую currency. Payout с bynAmount использует его; legacy Payout без валюты/снимка не выводится из текущей orgSetting, даты или величины. Долг, баланс и массовые выплаты блокируются только при зависимости от такой неизвестности. Частичный недостоверный итог не называется полным итогом.

Альтернатива группировать/пересчитать текущим курсом делает долг исторически изменяемым; выбрана фиксированная база либо явная недоступность.

### Сохранить валютные кассы и точность

Не сужать общий cash currency enum, selectors касс/операций и Telegram `cur:*`: они управляют физической валютой. Payment/Payout продолжают сохранять cash amount/currency/rate/date и bynAmount; payout payroll side для новых записей BYN. Использовать существующие Decimal helpers и ROUND_HALF_UP до двух знаков; отсутствие курса новой валютной операции означает отказ, не fallback. Null/подтверждённый ноль различаются; API/новые денежные DTO передают десятичные строки, преобразование для UI только после расчёта. Новые внутренние денежные действия без FX не обращаются к НБ РБ.

### Небольшие правки интерфейсов

Убрать проектный currency state/select/payload из create-project-dialog и overview-tab, currency step/`npc:*` Telegram engine; payroll-settings-form показывает BYN. Обновить денежные подписи/исторические строки finance-tab, payroll views/CSV и процентных панелей без глобальной замены всех currency на BYN. Не менять визуальный дизайн карточек и не расширять права (`roles.ts`, access/visibility).

### Приёмочный контур и адаптивная предпосылка

Для local native/browser проверок используются `tests/crm-byn-native.mjs`, `crm-byn-native-runner.mjs`, `crm-byn-browser.mjs` и существующий W07-контур идентификации с HMAC. Identity/target guards проверяются до запуска; несоответствие означает STOP. Native runner выполняет разрешённые сценарии в откатываемой транзакции существующего local окружения; table hashes и exact rollback проверяют сохранность, дамп не нужен и не создаётся. Browser-контур сохраняет разрешённые краткоживущие сессии/собственные изменения отдельно, восстанавливает захваченные preferences через CAS и подтверждает table hashes; evidence не содержит секретов. Generated QA-файлы/результаты остаются ignored, owned temporary profile очищается.

Минимальная responsive правка существующего product header устраняет несжимаемые элементы/переполнение на tablet/zoom и является предпосылкой фактической приёмки валютных форм №16. Это не перенос компоновки/порядка полей №25 и не новый inline UX №17. Полные локальные результаты описаны в evidence.md; staging runtime пока pending.

## Risks / Trade-offs

- [Frozen guard мешает ручному USD→BYN] → считать blocker будущей ручной подготовки production; staging сохраняет проект и проверяет локальный отказ новых денежных действий. Не ослаблять guards и не создавать conversion writer; отдельное решение владельца необходимо.
- [Legacy Payout без currency/BYN, foreign PayrollEntry без fixed BYN, PriceItem/Work без currency] → подтверждение согласованности требуется перед будущим production-выпуском; локальный fail-closed остаётся защитой чтения/операции при неизвестности.
- [Staging ночью refresh из production] → перед staging-приёмкой учитывать актуальный состав данных и повторно проверить gate; refresh/W07 не менять.
- [История percentages/allocations смешана с новыми writes] → fixtures для frozen/незавершённых записей, проверка сохранности и отсутствия дубля начисления. Не подменять историю новыми правилами.

## Migration Plan

1. Владелец 02.10.2026 явно разрешил «все...без согласований...tested staging»: согласование OpenSpec, реализация, коммиты, обычный merge и tested staging входят в текущий объём; main/production исключены. feature/16 создана от свежего origin/staging f036823. Дополнительные согласования внутри этого объёма не требуются.
2. RED→GREEN расчётов/прав/серверных контрактов; существующие local/staging без reset/seed/дампов. Новые QA-данные только по отдельному точному разрешению. Restic не трогать. Завершённость локальных проверок отмечается по финальным root logs, а не по существованию исходников.
3. Оркестратор выполнил read-only staging preflight под W07 identity: 184 проекта (174 BYN, 8 RUB, 2 USD), payrollCurrency=BYN, Payroll/Payout без bynAmount — 0, 221 PriceItem и 6449 Work. Это полученное evidence оркестратора, не самостоятельное чтение БД автором документов. Десять non-BYN проектов сохраняются без конвертации; staging-gate проверяет их доступность/сохранность, локальный запрет новых денежных действий, fixed snapshots и недоступность неоднозначного итога без перемаркировки.
4. После разрешённого атомарного коммита обычный merge feature/16 → staging, CI, фиксация фактической SHA/образа/здоровья и приёмка денежных/ролевых/ботовых/визуальных сценариев. Ночной refresh/W07 сохраняются; после изменения состава данных повторяется затронутая проверка. При ошибке исправить в feature/16 и повторить цикл, не объявлять staging принятым по build.
5. Будущий main/production-выпуск вне текущего объёма. Он потребует отдельного прямого указания владельца, ручной подготовки non-BYN проектов, подтверждения единицы старых PriceItem/Work и согласованности исторических payroll/payout, разрешения frozen blockers без обхода guards. Отчёт32 не является доказательством всей готовности. Агент production-БД не проверяет/не правит. Порядок будущего выпуска — весь принятый staging через ff-only, сверка refs и фактического deployment; настоящая staging-приёмка не заменяет эти действия.

## Open Questions

Для будущего production остаются вопросы ручной подготовки проектов, чью валюту frozen guards запрещают менять, и подтверждения единицы старых PriceItem/Work/исторических BYN-эквивалентов. Эти вопросы не блокируют явно разрешённую staging-проверку с сохранением non-BYN истории и fail-closed; change не предоставляет механизм исправления или автоконвертации данных.
