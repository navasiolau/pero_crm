# Design

## Context

См. proposal.md. ProductsView уже подтверждает полный query === resolvedQuery, отсутствие pending, совпадение текущего draft q и закрытие мобильной панели. ProductsKanban хранит локальные строки для оптимистичного DnD; начальная и последующие выборки проходят filter по видимым статусам. Поэтому сравнение локального отфильтрованного массива с исходным ответом всегда ложно. Общий useKanbanSearchFocus уже отменяет RAF старого q, однократно потребляет запрос, включая отсутствие точного совпадения, и сохраняет caret/ручную прокрутку.

## Goals / Non-Goals

**Goals:** после commit React идентифицировать, какому конкретному ответу сервера и набору ролей принадлежат отображённые строки, и сохранить существующее ожидание авторитетного ответа после оптимистичного изменения.

**Non-Goals:** менять hook или проектный канбан, добавлять server revision/API, перестраивать DOM/CSS, memo/виртуализацию142–146, переносить actor128, менять server policy, persist/CAS, денежные расчёты или БД. Task141 остаётся BLOCKED_DEVICE_UNAVAILABLE и не является условием исправления145.

## Decisions

1. Хранить в одном state объект с отфильтрованными rows, исходным initialProducts и actorRoles, которые породили именно эти rows. Начальная и последующая синхронизация записывают весь объект атомарно. Готовность сравнивает метаданные применённого ответа с текущими props, а не rows после filter с исходным массивом. Ссылка исходного неизменённого ответа служит локальным token полученной RSC-выборки; дополнительная серверная ревизия не нужна. Альтернатива убрать сравнение полностью позволит потребить новый q по старым локальным строкам; отдельно изменяемый ref может объявить готовность до commit rows.
2. При applyStatus обновлять rows и сбрасывать ссылку подтверждения ответа. Optimistic DnD и его локальный rollback не становятся серверным подтверждением. Следующий initialProducts/actorRoles, применённый существующим effect, снова подтверждает rows. Существующие серверные действия, rollback/toast/navigation и текущий activeId gate сохраняются.
3. ProductsView searchReady остаётся внешним подтверждением полного query и модальности; ProductsKanban добавляет подтверждение своих отображённых rows и отсутствие activeId. Общий hook остаётся единственным механизмом однократности, отмены, центрирования и восстановления snap. Порядок effects не используется как доказательство готовности.
4. Добавить отдельный regression реального ProductsView/ProductsKanban с React, DnD, KanbanScrollArea и useKanbanSearchFocus в Chromium; controlled transport только для Next/server boundaries. RED должен воспроизводить отсутствие прокрутки на исходном filter-created array. GREEN подтверждает ровно одну пару board/page scroll, поздние query/filter ответы, пустой набор, роль, ручной scroll+SSE, clear/re-enter, caret, DnD и мобильную Sheet. Существующий kanban-search-focus-browser.mjs дополнительно проверяет оба раздела, реальные Tailwind/BaseUI и три viewport.
5. Проверять preservation в 1440×900, 390×844 и 360×800: исходные PNG/data pins сохраняются, геометрия колонок/карточек и DOM-фокус не меняются; ожидаемый scroll-delta относится только к исправлению145. Staging проверяется лишь на фактически развёрнутом accepted SHA, с reviewed read/prefs-CAS caller, блокировкой неизвестных POST/prefetch и защитой исходных бизнес/аудит/финансовых данных. DnD на настоящих записях не разрешён этим протоколом.

## Risks / Trade-offs

- Старый локальный набор на render нового RSC → атомарные rows+source+roles в state; searchReady не становится истинным до применения строк.
- Возврат после неудачного DnD блокирует pending поиск до ответа → локальный rollback не авторитетен; новая поисковая выборка или штатный refresh подтверждает rows. Отдельный regression сохранит этот консервативный контракт.
- Свежие массивы/SSE могут повторно сдвигать экран → однократность остаётся в неизменённом hook и проверяется реальным scroll count.
- Role union/скрытые статусы → исходная visibleProductStatuses фильтрация сохраняется; поиск использует только отображённые карточки.
- Независимая интеграция128 меняет тот же файл → обычный merge с сохранением обеих атомарных задач и повтор целевых role/search regressions; копирование файлов или cherry-pick запрещены.

## Migration Plan

Без миграции. Local RED→GREEN и браузерные проверки, независимое code review, коммит только после явного указания владельца, затем обычный merge staging оркестратором и приёмка actual SHA/image/health/search/preservation. При отказе возвращается предыдущий совместимый образ либо исправление вперёд, без восстановления/удаления данных. Main/production не затрагиваются.
