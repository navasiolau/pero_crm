# Design

## Context

См. proposal.md. Исходный компонент до #214 использовал одну Textarea с классами h-80 min-h-80 resize-y, Label и внешним Card. #216 заменил внутренность на девять независимых полей. Его forProduct на чтении и ручной записи также отбрасывает custom, канонизирует названия и сортирует строки, поэтому одного изменения JSX недостаточно.

## Goals / Non-Goals

**Goals:** Одна прежняя рамка с inline-строками, непосредственная запись пар label/value, сохранение порядка и безопасное слияние.

**Non-Goals:** Новая схема БД, глобальное изменение формата КП/PDF, массовое преобразование данных, production-выпуск.

## Decisions

1. Общая рамка повторяет размеры, шрифт, цвет и отступы исходного поля; внутри используются обычные borderless input/textarea. contenteditable не нужен: контролируемые поля сохраняют предсказуемые IME, доступность и черновики. Заголовок и значение стоят в строке, а не в отдельных карточках.
2. Пустая завершающая строка получает локальный стабильный ID при первом вводе; следующая появляется без отдельного действия. Обе пустые строки не записываются. Очистка сохранённой пары удаляет её; Enter в значении сохраняет многострочный текст, Tab переводит к следующему названию.
3. Существующий envelope sections/sourceGeneration остаётся. Product-validator сохраняет ID, type/group, произвольный label, value и порядок массива, без каталожной сортировки и устранения custom. description/size/note не отображаются. Строгая глобальная нормализация КП не меняется. Вход fromProposalForProduct остаётся единственным ограниченным адаптером КП.
4. Mutation technicalSpecificationRow: sectionId, expectedSourceGeneration, expectedRow:{label,value}|null, row:{label,value}|null плюс прежние productId/clientMutationId. В существующей транзакции/блокировке проверяются ACL, receipt, поколение и CAS пары. Создание добавляет в конец, правка сохраняет ID и место, удаление не позволяет позднему update воссоздать ID. Receipt и очередь обеспечивают повтор запроса без дубликатов.
5. UI хранит отдельный контроллер пары по ID. Автосохранение 400 мс, IME, blur/Ctrl+Enter и более свежие локальные draft сохраняются. Успешный ответ не пересортировывает список. При конфликте показывается только существующая ошибка через toast, draft остаётся в строке.
6. Первые создания отправляются по локальному порядку; правки существующих строк остаются независимыми. Product-only JSON получает необязательный editRevision (старые записи = 0), который растёт под той же блокировкой при фактической ручной правке. ACK возвращает revision. UI сравнивает sourceGeneration/editRevision и отбрасывает устаревший RSC, чтобы поздний снимок не убрал созданную строку и не вернул удалённую. При замене из КП поколение растёт, editRevision начинается с 0; сравнение содержимого КП исключает этот счётчик.

## Risks / Trade-offs

- Потеря ручного названия через старый forProduct → отдельная Product-нормализация на всех ручных read/write/create путях, профильный reload-тест.
- Фокус исчезает после создания строки или ACK → стабильный локальный ID; виртуальная следующая строка меняется только после первого ввода.
- Перекрытие обновления КП и ввода → прежняя sourceGeneration и CAS всей пары, никакого автоматического переноса устаревшего draft в новое поколение.
- Длинные значения на мобильном → перенос строк, отсутствие горизонтального overflow, проверка 390/1440 px.

## Migration Plan

Новых миграций нет. Проверить существующую разрешённую local БД 5433, выполнить обычный merge bugfix/217 в staging, дождаться штатного CI и принять фактический SHA/образ и UI. Main не менять. При ошибке исправлять ветку и повторять приёмку, без переписывания истории.
