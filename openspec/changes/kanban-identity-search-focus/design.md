# Design

## Context

Поиск строится в `projectWhere` и `productWhere`: оба запроса соединены с серверной видимостью через AND. Серверная страница заранее знает вид списка, а один общий запрос обслуживает канбан и таблицу. Клиентский контроллер меняет URL оптимистично раньше получения новых RSC-строк; канбан отдельно синхронизирует локальные строки эффектом. `KanbanScrollArea` прокручивается только по горизонтали и синхронизирует нижнюю полосу; вертикальная прокрутка принадлежит странице. На телефоне колонки используют `scroll-snap-type: x proximity`, а фильтры открываются в модальной панели.

## Goals / Non-Goals

**Goals:** ограничить область поиска внутренним параметром канбана и использовать общий безопасный механизм перехода к точному номеру после синхронизации результатов.

**Non-Goals:** изменять сохранённый URL/настройки, глобальный поиск, таблицы, порядок доски, права доступа, миграции БД или добавлять виртуализацию.

## Decisions

1. Внутренний `searchScope: identity` задаётся только серверной страницей для канбана. По умолчанию запрос сохраняет прежнюю область; параметр не читается из URL и не сохраняется в предпочтениях. Это сохраняет совместимость других вызывающих методов.
2. Сервер передаёт канбану `resolvedQuery` вместе с набором строк. View подтверждает совпадение текущего полного запроса с `resolvedQuery`, завершённый pending, текущий черновик поиска и отсутствие модальности; board дополнительно ждёт синхронизации локальных строк и завершения DnD. Без подтверждённой пары обычный caller не запускает поиск. Одна генерация непустого q потребляется один раз, включая отсутствие точного результата; SSE, новая ссылка массива или ручная прокрутка не запускают повтор.
3. Только draggable-обёртки карточек имеют устойчивый `data-kanban-card-id`. Поиск ID выполняется внутри собственного boardRef; DragOverlay и общие карточки не получают маркер. Совпадение проверяется по полному отображаемому номеру, без числового преобразования.
4. Общий механизм измеряет карточку и доступные границы, прокручивает доску и страницу, не вызывает `.focus()` и не меняет данные. При программном центрировании мобильный snap временно подавляется: немедленное восстановление способно вернуть начало колонки вместо центра. Исходный snap возвращается перед следующим ручным wheel/touch/pointer/навигационным key-жестом, новым запросом или размонтированием; layout и CSS глобально не меняются. Поведение учитывает reduced motion и отмену отложенных кадров при новом запросе или размонтировании.
5. Мобильная панель сообщает открытую и завершающую закрытие модальность. Перемещение ждёт `onOpenChangeComplete(false)`; пользователь сам закрывает панель. Другая разметка и поведение фильтров сохраняются.

## Risks / Trade-offs

- Устаревший RSC-ответ → сравнение всей пары query/строки, pending и синхронизации, отмена при изменении q.
- Перехват прокрутки при частых обновлениях → однократная генерация поиска, отсутствие повторов от SSE или новых массивов.
- Мобильный snap смещает центр → временное отключение только на программном переходе с восстановлением ручного поведения; браузерная проверка фактических координат после завершения.
- Граница доски/страницы не позволяет точный центр → ограничение целевых координат доступным диапазоном, проверка ближайшей достижимой позиции.

## Migration Plan

Миграция не требуется. Реализация и OpenSpec коммитятся вместе после локальных проверок и независимого ревью; обычный merge в staging, затем приёмка фактически развёрнутой ревизии. Main и production остаются отдельным решением владельца.
