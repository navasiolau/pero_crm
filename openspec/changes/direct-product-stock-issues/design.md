# Design

## Context

См. proposal.md. StockMovement уже имеет productId без обязательного projectMaterialId. WarehouseMovementValuation хранит точную цену и связанные возвраты. Ограничение потребностью находится в одном warehouseMove; финансовая проекция101 уже читает сохранённые движения.

## Goals / Non-Goals

**Goals:** единый writer выдачи/возврата, самостоятельный план, корректный факт/стоимость/повтор в обоих интерфейсах.

**Non-Goals:** новые кассовые операции и переоценка истории. Не менять ограничения распределённых работ при изменении количества изделий.

## Decisions

- Расширить warehouseMove прямым productId/materialId для выдачи и productId/sourceMovementId для возврата. Прежние line-inputs остаются совместимы; их fingerprint не меняется. Новые поля включаются в fingerprint только когда заданы.
- После shared-gate и mutation lock блокировать Material, затем Product; перепроверить живое изделие/строку/источник. Лимит выдачи — текущий склад. Цена только из issuePosition, возврат только через существующий returnShare сохранённой выдачи.
- Потребность не создаётся автоматически. Если строка существует, её issuedQty учитывает прямое движение. При создании новой потребности взять ранее выданное netto из журнала под теми же блокировками. AddMaterialNorm получает порядок Material→Product до FK insert, чтобы не возникал взаимный deadlock.
- Для уже превышенного плана общий materialPlanFloor=min(текущий план, выдано) позволяет править комментарий, сохранять или увеличивать план без искусственного роста до всего расхода. Для обычных строк прежняя защита уменьшения ниже выданного сохраняется. Тот же helper используется UI и пересчётом количества; факты не переписываются.
- DTO принадлежат warehouse/contracts. Операционный reader выдаёт все доступные источники возврата независимо от потребности, маскируя деньги по WAREHOUSE_MONEY_ROLES. Общий итог изделия использует сохранённые факты/агрегатор101 без лимита500 и с явнымNULL для неизвестной истории; отображаемая страница журнала может оставаться ограниченной.
- Один StockMovementDialog обслуживает выдачу из строки потребности, прямую выдачу и возврат. Изменение потребности остаётся своим действием. Исторический manual-return доступен только прежнему ограниченному legacy-остатку; новые выдачи нельзя возвращать по произвольной цене.
- Общий сервис складских операций используется web и bot. Новые bot issue/return endpoints и диалог проверяют складские роли, private chat, актуальный выбор/nonce и UUID. Финансовые суммы выдачи не возвращаются роли без финансового доступа. Финансовый Payment не создаётся.
- Тот же bot-адаптер предоставляет уже существующий инвентарный приход102 и ограниченный исторический возврат; новых правил расчёта для этих путей нет. Выбор с nonce и разбор положительного ввода разделяются с диалогом закупки103.
- События/уведомление только после нового commit, общая инвалидация включает финансы проекта.

## Risks / Trade-offs

- Concurrent issue/return/norm → одинаковый порядок блокировок, повторное чтение, тест недостатка/двойного возврата/создания потребности.
- Потребность появилась после выдачи → инициализация issuedQty фактом, без изменения её планового количества.
- История без снимка → сохранять неизвестную сумму; не использовать сегодняшнюю цену.
- Широкие права финансового чтения и узкие операционные права → отдельные guards и безопасные DTO при сохранении объединения ролей.

## Migration Plan

Без миграции. Локальные проверки/настоящий SQL, обычный merge, CI, проверка фактического staging; main ожидает владельца. Без dumps/Restic/reset/seed.
