# Design

## Context

См. proposal.md. ChangeLog совмещает бизнес-события и durable receipts. Для КП основное событие содержит только ревизию; договор сохраняет fingerprint/result. Сырой actor нужен для replay-проверок. Основа №221 предоставляет отдельное представление и транзакционный writer.

## Goals / Non-Goals

**Goals:** зафиксировать доступные на момент операции бизнес-снимки, контекст и исполнителя без изменения исходного протокола.

**Non-Goals:** изменение денежных формул, прав бизнес-команд, storage-процессов, истории старых событий или интерфейса журнала.

## Decisions

- Передавать writer №221 исходный payload без изменений и независимые hints before/after/entity/contexts/links. Не встраивать новые данные в квитанции: их структура участвует в replay.
- Использовать небольшие чистые helpers бизнес-контекстов. Номер и название сохранять из заблокированной сущности; ссылки строить по стабильному ID.
- Системность задавать явно в подтверждённых путях автоматизации. DomainActor и changedById остаются исходными, отображаемый исполнитель и инициатор независимы.
- Сохранение договора передаёт снимки как отдельный аргумент writeReceipt; завершение выпуска создаёт самостоятельное событие. Сохранение исходного КП, его downstream проект/изделие и выпуск являются разными фактами.
- Реальные изменения изделия, ранее записанные только агрегатом проекта (цены, каскадное скрытие), получают собственный product audit. Неизменившиеся последствия не добавляют событий.
- Веб, Telegram и API используют существующие общие cores. Новых транспортных writers не создавать.

## Risks / Trade-offs

- Изменение raw-квитанции нарушит replay → тесты сравнивают исходные поля и повтор на старом формате.
- Новый audit может нарушить транзакцию → fault injection проверяет полный rollback на существующих DI fixtures; runtime проверяет root.
- Контекст удалённой сущности нельзя восстановить после удаления → снимок фиксируется до изменения.
- Ссылки на пользователей и клиентов могут содержать только ID → сохранять названия доступных ссылок вместе с before/after, не выводить секреты.

## Migration Plan

Сначала принять №221; обычным merge принятого staging получить foundation в bugfix/225. Затем local checks, независимое review root и штатный CI/staging. Отдельной миграции №225 нет. Production вне задачи.
