# Design

## Context

См. proposal.md. FINANCE_ROLES используется одновременно страницей зарплаты, экспортом, actions, начислением от оборота и проверкой SALARY ядра выплат. Выплаты ADVANCE и SALARY удаляются одним action. Сервис выплат проверяет квитанцию до входа в ядро; это чтение также требует предварительного допуска. Опубликованные основные specs зарплату не описывают.

## Goals / Non-Goals

**Goals:** единый зарплатный grant и отказ на каждой серверной границе; независимые права ADVANCE; поведенческие проверки реальных модулей с заблокированными внешними вызовами.

**Non-Goals:** изменение финансовой арифметики, кассы по умолчанию, схемы БД, собственной зарплаты, иных видов уведомлений или переписывание исторических выплат.

## Decisions

- Ввести PAYROLL_MANAGE_ROLES и requirePayrollManagement. Не менять FINANCE_ROLES/ADVANCE_ROLES: их сужение отнимет общие финансовые права. Проверять объединение ролей через hasAnyRole.
- На странице и CSV проверять доступ до запросов. Карточку финансов рендерить по актуальной сессии; дополнить middleware для согласованного перехода, сохранив серверные guards.
- Для addPayout определять право по kind, для начисления/массового расчёта использовать зарплатный helper. В сервисе и ядре проверять kind до любых чтений, сохранив прежний протокол повторов.
- Удаление: внутри существующей транзакции сначала select только kind, затем assertPayoutRole; полный объект и аудит читать после допуска, сохраняя доступное удаление аванса.
- payroll.orgAccrued и старый смешанный payroll.orgPayout ограничить зарплатными ролями при отправке и чтении. По согласованию новые авансы используют payroll.orgAdvance и /finance/advances; исторические смешанные записи не переклассифицировать по свободному тексту.
- При отправке авансов и отображении настроек читать явную настройку payroll.orgAdvance, затем прежнюю payroll.orgPayout, затем дефолт true. Общий resolver гарантирует одинаковый приоритет; настройки старого скрытого типа читаются для наследования и у PROCUREMENT. Сохранённые значения не мигрировать, явная новая настройка имеет приоритет.

## Risks / Trade-offs

- [Общая форма выплат поддерживает два вида] → проверять kind в action, сервисе, ядре и удалении; отдельные тесты ADVANCE и SALARY.
- [Старый тип уведомлений смешивает авансы и зарплату] → скрыть его у снабженца без изменения истории; новые авансы отделить. Пользователь с ACCOUNTANT сохраняет полный доступ.
- [Локальная БД 5433 недоступна] → не создавать/запускать замену; выполнить модульные поведенческие проверки, типизацию и lint, native/runtime и staging оставить явно неподтверждёнными.

## Migration Plan

Миграция БД не требуется. Проверить ветку локально, затем обычный merge и независимая приёмка реального staging с подтверждением SHA/образа. Коммиты и продвижение выполняет оркестратор по разрешению владельца. Откат — штатный новый коммит с повторной приёмкой, без изменения исторических данных.
