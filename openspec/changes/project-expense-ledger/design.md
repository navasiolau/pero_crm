# Design

## Context

См. proposal.md. Экономика уже складывает Payment и StockMovement, однако делает собственную группировку по названию статьи. Точная складская цена доступна в WarehouseMovementValuation; округлённая денежная сумма — в StockMovement.totalByn.

## Goals / Non-Goals

**Goals:** общий расчёт фактов для статей и итогов, безопасный финансовый просмотр исходных движений, повторное использование FinanceTab.

**Non-Goals:** новые складские операции и кассовые проводки; они относятся к задачам 102–104. Зарплата сохраняет существующую отдельную агрегацию снимков.

## Decisions

- ProjectExpenseRow — вычисляемая проекция, а не таблица. Источник и sourceId сохраняют связь; дополнительные Payment дали бы двойное списание.
- Чистый сумматор использует Decimal и сохранённый BYN. Возврат имеет отрицательный знак. Статьи группируются по ID, склад имеет отдельный стабильный ключ. Неизвестная сумма распространяется в зависимые итоги.
- Экономика принимает предварительно загруженные факты. Загрузчики обоих экранов используют тот же сумматор и проектор; SQL не дублируется при подготовке журнала.
- Складской финансовый reader выбирает только безопасные поля и проверяет FINANCE_ROLES. Детали открываются в финансовом диалоге, не требуют технического доступа бухгалтера к изделию.
- Снимковая цена сериализуется строкой с сохранением точности. Для старого движения допускается только его собственный unitPrice, никогда сегодняшняя цена номенклатуры.

## Risks / Trade-offs

- Неполная история → явное «Нет данных», не ноль и не пересчёт.
- Совпадающие названия статей → разные ID и отдельные строки.
- Расхождение журнала и итогов → общие входные факты, тест выдачи 60 BYN и возвратов.

## Migration Plan

Без миграции. Локальные проверки, обычный merge feature/101 в staging, проверка фактической ревизии. Main только после отдельного решения владельца.
