# Design

## Context

См. proposal.md. Склад использует INCOME/EXPENSE/RETURN и точную средневзвешенную оценку. Текущий addStockIncome не имеет денежной части.

## Goals / Non-Goals

**Goals:** достоверная классификация и ясное назначение формы при сохранении ядра/receipt.

**Non-Goals:** проведение оплаты; его транзакция и выбор кассы принадлежат 103. Не выводить пока неработающую кнопку оплаченного прихода.

## Decisions

- Nullable StockMovement.receiptKind с enum INVENTORY/PAID и CHECK: вид допустим только для INCOME. Старые записи остаются NULL без backfill. Определять прошлую оплату по комментарию или цене недостоверно.
- Существующее складское ядро сохраняет INVENTORY для новых INCOME. Контракт inventory запрещает PAID/кассу; новый метод оплаченной закупки 103 будет единственным путём PAID с финансовой связью.
- Схемы принадлежат server/warehouse/contracts; прежний lib/warehouse-input реэкспортирует их для совместимости. Валидация не дублируется.
- Старое имя action сохраняется как делегирующая совместимость. Форма использует addInventoryReceipt. Отпечаток складского повтора неизменён, старые подтверждения работают.
- Общий модуль меток/фильтров обслуживает журнал. NULL обозначается «Приход (вид не указан)».

## Risks / Trade-offs

- Нельзя доказать оплату прошлого прихода → не классифицировать историю.
- Обновление клиента во время запроса → старый action и idempotency сохранены.

## Migration Plan

Аддитивная миграция на существующем local/staging без дампов и переписывания строк. Проверить количество/хеш старых полей, остатки, деньги и повтор. Main не выпускать.
