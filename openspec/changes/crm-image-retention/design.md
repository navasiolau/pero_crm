# Design

## Context

Исследован `deploy/watch-crm.py` на `efe1607f`. В `watch_pair` и `_watch` есть pull, проверка образов, up, health и postcheck БД, но нет проверки свободного места и удаления старых образов. Журнал успешных запусков содержит web/renderer image IDs и revision. W07 ограничивает внешний запуск 240 секундами, внутренний общий deadline — 200 секунд.

Инцидент 10.11.2026 и ручное устранение описаны в change №212. Само приложение обновляется через GHCR; host watcher лежит отдельно в `/opt/crm-staging`, поэтому merge исходников не доказывает установку механизма очистки.

## Goals / Non-Goals

**Goals:** встроить ограниченную уборку в существующий watcher, обеспечить доказуемое владение удаляемыми образами и запас до pull.

**Non-Goals:** новый cron, общий Docker prune, SQL, изменение БД/volumes, переполнение диска ради QA, удаление журналов или работа с restic.

Уточнение владельца: стандартный CI production, команда запуска web и штатные миграции сохраняются. Ретеншн добавляет только проверку места и ограниченные image-операции в существующий watcher.

## Decisions

1. Построить чистый planner поверх metadata adapter: protected set содержит все ссылки всех контейнеров и image IDs трёх последних различных успешных версий. Для КП версия включает оба образа. Запись неуспешной попытки не продвигает окно хранения.
2. Владение подтверждать проверенным repository/digest из текущего deployment и защищённого журнала watcher. Старые неопознанные dangling images не считать своими только по отсутствию тега. Для первого включения подготовить dry-run и проверенный allowlist исторических образов CRM; отказ от удаления неопознанных объектов явно отражать в отчёте.
3. До pull измерять свободное место на фактическом Docker data-root filesystem; при запасе менее 3 GiB удалить допустимых кандидатов, повторить измерение и завершить запуск с `insufficient-image-space`, если запаса не достигнуто. Фиксированный порог соответствует текущей поставке; изменение порога входит в проверяемую конфигурацию релиза.
4. После успешного health повторить planner для остаточной уборки. При `unchanged` разрешить продолжение накопившейся уборки; каждое решение пересчитывать по свежим ссылкам контейнеров. Удалять через Docker API по полному ID, без force и без удаления родителей каскадом.
5. Cleanup использует тот же W07/workflow lock и внутренний watcher lock. Начинать следующую команду только при наличии времени вне резервов postcheck/rollback; незавершённую уборку фиксировать отдельно от результата здорового deployment. Ошибка housekeeping после успешного up не является поводом для отката БД или приложения.

Реализация ограничивает фазу 20 кандидатами. Владение также подтверждается сочетанием CI repository/service/revision labels; посторонние repository refs исключаются. История читается потоково из защищённого append-only журнала, сохраняющего предыдущие релизы; неполный участок не считается готовым окном отката. Родительские image IDs, именованные теги и renderer-зависимости защищённых web остаются защищёнными. Измеряется минимум свободного места на root, Docker data-root и существующем containerd filesystem.

## Risks / Trade-offs

- Старый журнал не содержит всех исторических образов → dry-run, точный начальный allowlist, сохранение неопознанных объектов.
- Общий слой используется защищённым образом → удаление только через Docker, без ручной очистки containerd/overlay.
- Между планированием и удалением появился контейнер → перечитать ссылки перед удалением; отсутствие force дополнительно защищает ссылку.
- Увеличился размер поставки → пересмотреть запас до релиза; нехватку места обнаруживать до pull, а не после деградации БД.
- Cleanup не укладывается в deadline → ограниченный проход и продолжение в следующем штатном запуске.

## Migration Plan

После согласования proposal — fake-adapter тесты планировщика и полного watcher, затем dry-run действующего staging. Установку host helper выполнять с проверкой исходного SHA, целевого hostname/project, W07 hash и сохранением штатного внешнего entrypoint. Принять реальный установленный helper, сохранность текущей пары и работу последующего обновления. Production требует отдельного прямого поручения. Миграций БД и дампов нет. Откат helper сохраняет уже защищённые текущую и две предыдущие версии; удалённые старые образы не восстанавливаются из БД.
