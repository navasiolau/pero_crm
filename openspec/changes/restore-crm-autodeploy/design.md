# Design

## Context

См. `proposal.md`. В репозитории уже есть `needs: test` для обоих jobs публикации. Live watcher хранится вне Git; основной агент подтвердил одинаковую ошибку сравнения before/after локального image tag. На staging внешний `/opt/crm-staging/watch-staging.sh` вызывает W07 controller, который под lock проверяет SHA и запускает `watcher.original.sh`.

## Goals / Non-Goals

**Goals:** Один тестируемый watcher с закрытым при ошибке допуском к двум существующим средам; короткий код без сторонних Python-зависимостей; доказательство причины RED и корректного поведения GREEN.

**Non-Goals:** Изменение БД, миграций CRM, refresh, watchdog, секретов, proxy, автоматический rollback БД, удаление override или автоматическое снятие инфраструктурной паузы из приложения.

## Decisions

- Python stdlib с core и runtime adapter: тесты моделируют Docker и время без контакта с серверами. Альтернатива shell затрудняет детерминированную проверку ошибок и сохранности.
- Точный hostname/cwd выбирает среду без пользовательских параметров. Docker вызывается через локальный Unix socket, Compose — с явными project directory/name и существующим `docker-compose.yml`, включая `docker-compose.override.yml` при наличии. Нестандартные альтернативные compose-файлы требуют отдельного согласованного изменения, а не обхода проверки.
- Итоговая compose-конфигурация проверяется в памяти; она не сохраняется и не выводится. Обычный pinned image или `pull_policy: never` отвергаются до pull. Проверяются включённый healthcheck web, только image без build и mounts БД.
- Flock сериализует watcher внутри среды; W07 остаётся внешним владельцем staging coordination. Lock не распространяется на сторонние ручные действия, поэтому снимки конфигурации/БД повторно проверяются перед up и после него.
- Общий deadline 200 секунд вместо суммы локальных timeout: последние 15 секунд резервируются postcheck, каждая subprocess-команда оставляет до 5 секунд на cleanup. `Popen(start_new_session=True)` создаёт отдельную process group; timeout приводит к SIGKILL всей группы и ограниченному reap. Внешний W07 timeout 240 секунд сохраняется.
- W07 перехватывает stdout, поэтому результат дополнительно пишется в `/var/lib/pero-crm-deploy/result.json` атомарно и `/var/log/pero-crm-deploy.jsonl` через append. Root ownership, тип и mode 700/600 проверяются; автоматической очистки/ротации журналов нет.
- Pull выполняется один раз и только для web. После него сравниваются желаемый image ID и running container image ID; `up -d --no-deps --no-build --pull never web` вызывается только при различии. До up повторно проверяется image tag; после up проверяется фактический образ. Docker healthcheck ожидается до 180 секунд, команды имеют собственные timeouts.
- Нездоровый web с тем же image не пересоздаётся: возвращается ошибка, восстановление остаётся ответственностью существующего watchdog. Остановленный или отсутствующий web не запускается, чтобы не отменять намеренную остановку.
- Снимок БД включает ID и полный список mounts. Watcher не выполняет команд внутри БД. Проверки снимка доказывают отсутствие пересоздания/смены хранилища, но не содержательную корректность произвольных миграций нового приложения.
- Последнее указание пользователя: прямые действия с production DB запрещены; staging DB самообновляется существующим refresh и не меняется ради тестов. В этой фиче используются только Docker metadata и fake adapter. Другие локальные проверки CRM используют существующую локальную БД; disposable DB для этой задачи не создаётся.
- OCI revision label добавляется обоим образам в workflow. Отсутствующая метка у ранее опубликованных образов допустима для первоначального восстановления; валидная новая метка входит в журнал.
- TDD RED: один и тот же сценарий сначала запускается против модели точно прочитанного старого алгоритма, затем против нового core. Модель помечена как source-algorithm fixture, а не испытание live watcher.

## Risks / Trade-offs

- Новый образ может содержать миграции → публикация только после локальных тестов, отдельная staging-приёмка на реальных данных до продвижения в main; наблюдение ID/томов не называется проверкой бизнес-данных.
- Сторонний процесс может поменять тег между inspect и up → fail-closed проверки до/после и отказ при несовпадении; штатные watcher сериализованы.
- Недоступный registry задерживает обновление → старый web сохраняется, команды ограничены временем.
- Compose-изменения за время pull → повторное сравнение конфигурации перед up, отказ при drift.

## Migration Plan

Основной агент после ревью устанавливает watcher на staging. W07 wrapper сохраняется: обновляется проверяемый им inner watcher и его SHA. Stale image/pull-policy override исправляется точечно с сохранением healthcheck; cron восстанавливается по текущему состоянию с сохранением retired heartbeat. Нельзя просто вызвать старый pin.resume с устаревшим cron SHA. После реального staging deployment и повторного `unchanged` основным агентом проверяются web image/revision/health и прежняя БД. Только затем выполняется аналогичное восстановление production. При ошибке cron возвращается в сохранённое состояние, данные не откатываются автоматически.
