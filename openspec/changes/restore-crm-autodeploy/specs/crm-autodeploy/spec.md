# Spec Delta

## Purpose

Автоматически доставлять проверенные изменения нужной ветки в соответствующую среду CRM, сохраняя принадлежность сервисов, контейнер и тома БД и существующие защитные ограничения staging.

## ADDED Requirements

### Requirement: Публикация после успешных проверок

CI SHALL запускать тесты при push в `staging` и `main` и публиковать образы только при успехе всех обязательных проверок. Образы SHALL содержать полный Git SHA в OCI revision label. Продвижение в `main` MUST выполняться после локальной и staging-приёмки.

#### Scenario: Упавший тест блокирует публикацию
- **WHEN** обязательный тест, включая тесты watcher, завершается ошибкой
- **THEN** jobs публикации CRM и бота не выполняются, а новые moving tags не публикуются

#### Scenario: Соответствие среды ветке
- **WHEN** проверки push завершаются успешно
- **THEN** staging получает тег `staging`, production — `main`; журнал deployment позволяет сопоставить образ с SHA коммита

### Requirement: Проверка целевой среды до изменения сервисов

Watcher MUST допускать только `crm` в `/opt/crm` с проектом `crm` и образом `ghcr.io/navasiolau/pero_crm:main` либо `crm-staging` в `/opt/crm-staging` с проектом `crm-staging` и тегом `staging`. Он MUST проверять итоговую конфигурацию с override, принадлежность `web` и `db` проекту и каталогу, работающую здоровую БД и существующий том данных. Несоответствие MUST завершать запуск ошибкой до pull/up.

#### Scenario: Устаревший pin или неверный сервер
- **WHEN** hostname, каталог, project labels, образ web, pull policy или healthcheck не соответствуют контракту
- **THEN** watcher сообщает отказ и не изменяет сервисы и конфигурацию

### Requirement: Обновление по фактически запущенному образу

После успешного pull только `web` watcher SHALL сравнивать ID желаемого образа с ID образа работающего контейнера. Совпавший здоровый `web` SHALL оставаться без пересоздания. Различие SHALL приводить к обновлению только `web` без зависимостей и повторного pull; изменение локального тега во время операции MUST выявляться.

#### Scenario: Образ заранее скачан
- **WHEN** до запуска watcher локальный тег уже указывает на новый образ, а работающий контейнер использует старый
- **THEN** `web` обновляется до желаемого образа

#### Scenario: Образ уже работает
- **WHEN** скачанный образ совпадает с работающим здоровым `web`
- **THEN** watcher сообщает `unchanged` и не выполняет up

#### Scenario: Сбой скачивания
- **WHEN** pull завершается ошибкой или превышает ограниченное время
- **THEN** watcher завершает запуск ошибкой и не выполняет up

### Requirement: Ограниченная проверка здоровья и сохранности БД

Watcher MUST проверять здоровье `web` не дольше 180 секунд после up, точное соответствие image ID и неизменность ID/томов `db` до и после обновления. Он MUST NOT выполнять операции down, seed, reset, restore или команды к БД. При ошибке здоровья или смене БД watcher SHALL завершаться ошибкой без автоматического восстановления данных.

Реализация, тесты watcher и его установка MUST NOT выполнять SQL или другие прямые действия с production/staging DB. Самообновление staging существующим refresh SHALL сохраняться; watcher-тесты MUST использовать fake metadata без создания БД/фикстур. Для других локальных проверок CRM SHALL использоваться существующая локальная БД согласно указанию пользователя.

#### Scenario: БД изменилась во время обновления
- **WHEN** ID контейнера или mounts БД отличаются от исходного снимка
- **THEN** результат является ошибкой сохранности; последующих исправляющих команд к БД нет

#### Scenario: Новый web нездоров
- **WHEN** новый контейнер не становится здоровым за установленный срок
- **THEN** watcher возвращает ошибку, фиксирует image ID и состояние без выдачи успешного deployment

### Requirement: Сериализация и безопасный журнал

Watcher MUST исключать параллельные собственные запуски. На staging MUST оставаться внешний W07 lock/active-run guard. Журнал SHALL содержать структурированный результат, image ID и известный Git SHA без окружения, compose-секретов, healthcheck-output и сырого вывода команд.

Watcher SHALL применять общий deadline 200 секунд с резервом на postcheck и завершение дочерних процессов внутри внешнего timeout W07 240 секунд. При timeout всё дерево CLI в его process group MUST завершаться до возврата результата. Результат SHALL сохраняться отдельно в защищённых root-owned snapshot и append-only журнале даже при перехваченном stdout; существующие записи MUST NOT удаляться watcher.

#### Scenario: Второй watcher или staging refresh
- **WHEN** предыдущий запуск держит lock либо W07 запрещает deployment во время refresh
- **THEN** новый запуск не изменяет web и БД

#### Scenario: Команда выводит секрет в ошибке
- **WHEN** Docker-команда завершается ошибкой с произвольным stderr
- **THEN** журнал содержит только фиксированный код ошибки и безопасные идентификаторы, а сырой stderr не выводится

#### Scenario: Сумма операций превышает бюджет W07
- **WHEN** предыдущие команды израсходовали общий бюджет обычных операций
- **THEN** watcher не начинает следующий up, использует только резерв для postcheck и завершает все свои CLI-потомки до внешнего timeout

#### Scenario: W07 перехватывает stdout
- **WHEN** внешний controller не передаёт stdout inner watcher в cron log
- **THEN** результат с image/revision/health остаётся в локальном защищённом журнале и snapshot
