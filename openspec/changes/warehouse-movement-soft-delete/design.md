# Design

## Context

См. proposal.md. Учёт склада хранит точные снимки в WarehouseMovementValuation и текущую позицию в WarehouseBalance. Возвраты ссылаются на выдачу; оплаченный приход связан со StockPurchase и Payment. Денежные агрегаты вычисляются по Payment. Старые движения до нулевого запуска не формируют текущий склад. Владелец согласовал каскад, а не запрет при наличии зависимостей.

## Goals / Non-Goals

**Goals:** единая отмена с проверяемым списком и транзакцией; сохранение исходных снимков; идентичное влияние на все чтения.

**Non-Goals:** перерасчёт исторических цен, восстановление удалённого через UI, произвольное удаление платежа закупки, автоматическое исправление неполных исторических данных, production-выпуск.

## Decisions

1. WarehouseMovementDeletion хранит UUID запроса, администратора, корневое движение, fingerprint предпросмотра и время. Nullable deletionId на StockMovement и Payment связывает сохранённые строки с отменой. Общие activePaymentWhere/activeStockMovementWhere применяются ко всем операционным журналам, балансам и экономике. Синтетический денежный приход не создаётся: иначе он искажает оборот/кассовый отчёт.
2. Чистый планировщик повторяет существующие функции warehouse-cost, используя снимки поступлений и исходных выдач. Сначала проверяет активную цепочку текущего runId и конечную позицию. Затем исключает корень; последующие выдачи, для которых недостаточно запаса или изменился точный снимок стоимости, включаются в каскад. Возврат удалённой выдачи также удаляется; возврат, чья доля после отмены предыдущего возврата изменилась, включается в каскад. Независимые приходы остаются. Это вычисляет транзитивную зависимость без выдумывания FIFO и без переоценки оставшихся строк.
3. Новые движения сохраняют accountingRevision позиции под существующей блокировкой материала. Старые записи текущего запуска без revision допускаются только при однозначном порядке времени и успешной сверке полной цепочки. Движения до запуска/без точных снимков дают понятный отказ «недостаточно данных для безопасной отмены»; ручное предположение о текущем складе запрещено.
4. Предпросмотр и подтверждение используют один планировщик. Подтверждение сначала проверяет receipt, затем заново считает план под денежной блокировкой, складским gate и Material/Product locks. Fingerprint включает состояние склада, связи, строки потребностей и финансовые суммы. Изменение плана требует открыть предпросмотр заново. UUID не меняется после потери ответа.
5. Транзакция помечает все затронутые движения/связанные платежи, обновляет текущую позицию и derived purchasePrice, отменяет фактическое issuedQty соответствующих потребностей, пересчитывает только изменяемые счётчики возвратов исходных выдач. Нормы потребности, неизменяемые снимки и документы остаются. Аудит и событие создаются внутри той же транзакции, cache invalidation/dispatch после commit.
6. Авторизация ADMIN проверяется в server action и ядре по свежей учётной записи. DIRECTOR и PROCUREMENT не получают право. Кнопка в последней колонке/мобильной карточке использует общий компонент с ConfirmDeleteDialog; предпросмотр содержит весь каскад, изменения остатков/расходов проектов и возврат в каждую кассу в её валюте.

## Risks / Trade-offs

- Длинный журнал → выборка одного материала текущего запуска, ограничение размера с явным отказом до любых изменений; никакой молчаливой обрезки плана.
- Старые неполные/неоднозначные данные → отказ с объяснением, исходные строки и деньги сохранены.
- Конкурентная выдача/возврат/удаление → одинаковый порядок блокировок и повторная проверка fingerprint; чужие новые операции не добавляются молча к подтверждённому каскаду.
- Пропущенный финансовый reader → единый фильтр и native проверки кассы/организации/отчёта/экономики/проекции материалов; поиск всех Payment/StockMovement readers при ревью.

## Migration Plan

Аддитивная nullable миграция без изменений исторических значений. Проверка на существующем local5433, обычный merge и deploy staging; дампы не создаются. После первой отмены откат к старому коду небезопасен, потому что старый код игнорирует маркеры: выпускать исправление вперёд. Production отдельно после приёмки владельцем и разрешения на миграцию, с временным дампом и изолированной проверкой восстановления по AGENTS.md.
