# Design

## Context

См. proposal.md. Каталог ItemsView сейчас содержит общую форму create/edit. Строгая materialSchema в warehouse/actions принимает название, unitId, categoryId, sku, minStock и comment; addMaterial использует WAREHOUSE_MANAGE_ROLES, withWarehouseWrite и аудит, возвращая только ok. Канонический StockMaterialOption содержит id/name/unit/sku и необязательный stock. Оплаченная закупка использует PaymentDialog и StockMaterialFields; она доступна также чистому бухгалтеру, не имеющему права менять номенклатуру. Справочник и названия единиц уже доступны через существующие loaders.

## Goals / Non-Goals

**Goals:** общий MaterialDialog, прежние серверные складские границы, каноническая опция и сохранение родительского draft на основании №175/178.

**Non-Goals:** создание единиц или категорий из закупки, расширение прав бухгалтера, изменение алгоритма учётной цены, автоматическая закупка при создании материала, новые read endpoints и новые зависимости.

## Decisions

- Выделить MaterialDialog с open/onOpenChange, units/categories, optional editing snapshot и onCreated(StockMaterialOption). Подключить его к create/edit каталога и к созданию в закупке, сохранив поля и существующее read-only отображение учётной цены каталога. Форма не принимает цену материала как записываемый реквизит.
- Схему материала и её тип использовать из одного общего контракта; не дублировать проверки между новой формой и actions. Существующие add/update actions сохраняют серверные WAREHOUSE_MANAGE-grants. Непустая единица обязательна; дефолт единицы совпадает с каталогом: warehouse-unit-piece, затем первая доступная. Категории выбираются из активных, без вложенного создания.
- addMaterial возвращает `{ok:true, material:StockMaterialOption}` либо `{ok:false,error:string}`. Опция строится из фактической сохранённой записи и связанной measurementUnit.name, sku нормализован сервером; новый материал имеет stock:0. Существующие callers, проверяющие ok, сохраняют совместимость.
- Сохранить withWarehouseWrite и warehouseMetadataGate. Проверять существование единицы и допустимость категории при записи; создание и его аудит выполнять в этой же guarded транзакции. Сохранить purchasePrice:0 и не вызывать складской/денежный writer. Не вводить отдельную блокировку или новую политику складского lifecycle.
- Родители склада и расходов организации передают optional materialCreateOptions с уже известными units/categories только при WAREHOUSE_MANAGE-праве. Для недостающих данных использовать существующие unit/category loaders на сервере родителя, без нового read action. Каталог переиспользует свои props. Чистому ACCOUNTANT options и кнопка создания не передаются; сервер всё равно повторяет проверку прав.
- StockMaterialFields получает optional действие создания. PaymentDialog владеет вложенным открытием и локально созданными опциями; объединяет их с props по id без дублей и выбирает канонический id. Количество/цена не очищаются. Action создания доступен в согласованных purchase entrypoints, не добавляется автоматически в выдачу/возврат.
- Во время вложенного диалога родительский submit заблокирован. Не размонтировать PaymentDialog и загрузчик документа; сохранять session/actor-защиту №175, локальные статьи №178 и frozen команду. Создание недоступно при pending/loading/UNKNOWN/blocked. Base UI Dialog обеспечивает независимое закрытие и возврат фокуса.

## Risks / Trade-offs

- [Единица удалена или категория отключена после загрузки формы] → серверная проверка и обработка существующей FK-ошибки без сброса черновика.
- [Бухгалтер может оплачивать закупку, но не создавать материал] → отдельный складской grant в loader, кнопке и action; сочетание ролей объединяется.
- [Обновление каталога из revalidate сбрасывает состав закупки] → локальное объединение по id и сохранение сессии родителя; callback меняет только materialId.
- [Ошибка аудита после записи материала] → проброс из guarded callback и rollback всей записи, проверка на настоящем PostgreSQL оркестратором.

## Migration Plan

Миграции нет. Реализация начинается после интеграции №178 и GO оркестратора обычным получением staging; №175/178 не копируются и не переносятся cherry-pick. Native-проверки выполняются оркестратором последовательно на существующей local:5433 под его guards; staging принимает точную развёрнутую ревизию. Main и production этим заданием не меняются.
