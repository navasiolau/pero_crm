# Design

## Context

См. proposal.md. Создание изделий выполняет общий core, переход проекта — stage-core с FOR UPDATE проекта, CAS, receipt и outbox. Этот переход используется вебом и endpoint бота. Все операции также проходят короткую task-транзакцию; отдельная блокировка проекта нужна для устойчивости при прямых транзакционных вызовах и корректной нумерации.

## Goals / Non-Goals

**Goals:** выбирать старт изделия по актуальному этапу под общей блокировкой, переводить черновики в договоре атомарно, расширить общие отображения и сохранить исторические финансовые факты.

**Non-Goals:** менять инженерные/производственные grants, начислять проценты при подготовке, автоматически откатывать изделия после возврата проекта, менять изображения и файловые списки.

## Decisions

- Общий helper блокировки строки Project используется перед чтением stage в createProduct и stage-core; ручная смена статуса блокирует сначала проект, затем изделие. Последовательность Project → Product сохраняет сериализацию подтверждения и создания.
- Для PAUSED/REFUSED читается последняя запись stageHistory с подтверждённым обычным toStage или fromStage, с сортировкой createdAt DESC/id DESC. Обычный toStage этой записи имеет приоритет; если запись переводит в служебный статус, берётся её обычный fromStage. Без такого факта — LEAD. Неполная импортированная история не должна возвращать старый просчёт поверх более свежего подтверждённого договора.
- Начальное состояние вычисляется явно в core: LEAD/ESTIMATE → DRAFT, остальные обычные этапы → PREPARATION. База по умолчанию создаёт DRAFT для прямых технических inserts.
- При реальном переходе в CONTRACT черновики выбираются под блокировкой проекта, переводятся с отдельной историей, аудитом и product.statusChanged events в той же транзакции. Не вызываются capture/settlement/percentage-completion. Повторный receipt и no-op не меняют изделия. Сервис после commit отправляет события и инвалидирует проекты и изделия.
- DRAFT скрыт от чистого инженера и полевых ролей существующими явными grants. Ручной выход DRAFT запрещён при актуальном stage LEAD/ESTIMATE на сервере; UI ограничивает селект и drag по тому же условию. В активном заказе менеджмент сохраняет обычный выбор статусов.
- Enum DRAFT добавляется отдельной миграцией, следующая транзакционная миграция устанавливает default и переводит все изделия ранних проектов, в том числе soft-deleted, с техническими history/audit. Стандартная таблица миграций Prisma исключает повторный backfill.

## Risks / Trade-offs

- Одновременное создание и договор → общий project lock, native сценарии обоих порядков исполнения.
- Несогласованная датировка истории импорта → детерминированный порядок и fallback fromStage; отсутствие истории оставляет DRAFT.
- PostgreSQL запрет использования нового enum в одной незакоммиченной транзакции → отдельные enum и backfill миграции.
- Перенос ранее завершённых изделий ранних проектов → меняется только статус и дата статуса, сохраняются назначения, quantity, цены, файлы и append-only финансовые факты; technical history отражает прежний статус.

## Migration Plan

Local и staging без дампов, без seed/reset. После согласования с оркестратором применить две миграции на существующей local5433, проверить native rollback/fingerprints и миграционный SQL на fixtures. На staging принять фактическую ревизию, DRAFT-фильтр и переход в договор. Production не выполняется в этой задаче субагентом; production-миграция требует временного дампа и изолированного restore по правилам владельца. Возврат приложения к старой версии требует отдельной совместимой стратегии, так как старый Prisma enum не читает DRAFT; enum/history/финансовые факты не удалять для отката вслепую.
