# Design

## Context

См. proposal.md. Общие ProjectStage/ProductStatus используются не только текущими объектами, но и историей, completion-снимком и типом frozen КП. Старый оператор №193 не удаляет enum и оставляет новые исторические записи с прежними значениями.

## Goals / Non-Goals

Узкие рабочие enum при неизменных архивных фактах. Не удалять строки, причины, файлы, снимки, старые миграции и финансовые операции. Не применять schema/data migration к production в этом поручении.

## Decisions

- Сначала преобразовать четыре поля истории и statusAtCompletion в TEXT, затем нормализовать рабочие значения и пересоздать enum. Архивные types/formatters отделены от Prisma enum; новые writers принимают только активные значения.
- Одна SQL-транзакция с общим advisory mutex КП, блокировками затронутых таблиц и ограниченным ожиданием. Прямой служебный перенос вместо app status actions исключает начисления и внешние события.
- При PAUSED выбрать последний обычный этап строго по алгоритму №193. Для возврата LEAD сохранить прежние правила acceptance/retention/cancel, без очистки байтов.
- Frozen parser и точный replay старых receipts используют архивный контракт; неизвестный новый запрос остаётся ошибкой. Удалить старый планировщик переноса из runtime и оставить CLI с явным inert-ответом о замене миграцией.
- Причины рекламации сохраняются как архивные сведения; активная форма и команды больше их не принимают.

## Risks / Trade-offs

- TEXT ослабляет ограничения истории на уровне БД → все новые записи получают типизированные активные статусы; архивные строки не используются как текущие без проверки.
- Старый процесс может выполнять enum-queries к истории → миграцию применять только в окне обновления без старых web/бота/worker, затем запускать новый образ.
- Ошибка SQL/аудита → транзакционный rollback; после успеха откат схемы требует отдельной миграции, история Git не переписывается.

## Migration Plan

Сначала inventory target и каталогов. Проверить SQL на существующем local5433 с транзакционным откатом и синтетическими строками, затем применить локально после сверки отсутствия старых writers. Новые БД/seed/reset/дампы не нужны. CI и staging — существующий контур после разрешения коммитов. Production отдельно: временный дамп затронутой БД, проверенное изолированное восстановление, миграция и приёмка по AGENTS.md.
