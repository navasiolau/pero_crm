# Design

## Context

См. proposal.md. #217 уже хранит строки в sections, защищает row CAS/receipt/sourceGeneration/editRevision и заменяет список из КП. UI сейчас выводит двоеточие; при null JSON скрывает raw description. Старый proposalItemDescription соединял description/размеры/заголовки/«Каркас:»/«Фасад:»/механизмы/ящики/подсветку/примечание, ручное описание произвольно.

## Goals / Non-Goals

**Goals:** Две непрерывные колонки, тихая пустая строка, lossless совместимость старых значений и сохранение автоматического KP→JSON процесса.

**Non-Goals:** Массовая миграция/новая колонка БД, изменение цен/картинок/КП/PDF-каталога, новый конструктор, production-выпуск, диагностика общего прежнего наблюдения React 418 вне изменяемого поля.

## Decisions

1. Общий ol с нативным list marker и одинаковые grid-колонки в строках: 48%/52% на мобильном, 42%/58% от md. Единая CSS-переменная задаёт колонки и положение тонкой линии на всю высоту ol. Это позволяет словам стандартного «Внутреннее наполнение» помещаться целиком на 390 px. Поле остаётся 320 px с вертикальным resize/scroll. Удаляются только двоеточия-разделители, собственные двоеточия в значениях сохраняются. Полностью пустая строка получает muted marker. Оба режима и диалог создания используют общий компонент, stable useId и события ввода остаются.
2. Чистый shared effectiveProductSpecifications(JSON,rawDescription) используется контроллером и сервером. Ненулевой JSON приоритетен всегда, включая []. При null JSON старый текст разбирается только по явным именованным заголовкам/известным нумерованным пунктам; URLs/время не считаются произвольным названием. Неопознанные фрагменты сохраняются custom-строками с пустым названием и исходным значением. Никакого HTML-рендера и выдуманных материалов. Детерминированные legacy IDs позволяют одинаковый CAS в браузере и сервере.
3. Ничего не записывается при чтении, blur неизменённого значения или пустом вводе. Первая реальная row mutation при null JSON проверяет optional expectedLegacyDescription, который обязателен для legacy/null baseline, под существующим Product lock после receipt replay. Весь parsed snapshot materializes вместе с правкой; raw description не меняется. Поколение остаётся 0, revision растёт. Никакого частичного обновления отдельных старых фрагментов.
4. ACK первой материализации дополнительно содержит полный technicalSpecifications. Контроллер принимает его через прежний revision guard и сохраняет более свежие/параллельные черновики. Legacy raw baseline принадлежит строке и обновляется только при принятом clean receive; pending запросы сравнивают прежний baseline. Обычные JSON callers и прежние guards сохраняются.
5. Вход из КП остаётся fromProposalForProduct, не legacy resolver. Autosave редактора — input→remote timer→PUT с operationId/expectedRevision→transactional Product sync. Проверяем именно этот путь и реальный сохранённый ответ, затем читаем Product JSON/две колонки. Не расширяем правила переноса неизвестных частей/размеров/описаний из нового КП.

## Risks / Trade-offs

- Потеря произвольного текста при разборе → unknown fragments хранятся как literal values, raw description дословно сохраняется; тесты CRLF/длинных кодов/HTML/свободного текста.
- Возвращение legacy после очистки → fallback только при JSON==null, никогда при sections:[].
- Конкурирующее первое редактирование/старый открытый экран/КП sync → raw CAS + row CAS + поколения/receipt, весь snapshot в одной транзакции и revision-guarded ACK.
- Обрезка длинного имени на телефоне → перенос внутри обеих колонок и autogrow, реальный browser screenshot/CSS checks.

## Migration Plan

Новых миграций нет. Старые данные переходят постепенно при ручной правке либо штатном сохранении/восстановлении КП. Проверки — существующая local БД 5433 и guarded owned fixtures на фактическом staging после обычного merge/CI; подтверждаются SHA/образы/health. Main не меняется. При ошибке — исправление в bugfix/218 и повтор обычного цикла без переписывания истории.
