# Design

## Context

Списки, карточки, поиск, вложенные изделия и выдача файлов уже используют visibility.ts. Assigned/participant predicates также используются для технических и исполнительских прав, поэтому менять их семантику опасно. Состояние списков хранится в UserPreference с CAS, codec V2 и приоритетом явного URL.

## Goals / Non-Goals

**Goals:** отдельные инженерные read grants с проверкой этапа родителя; одинаковые статусы в сервере и UI; обратимая совместимость настроек.

**Non-Goals:** новые управленческие, финансовые, технические или исполнительские права; изменение схемы БД; переопределение независимых grants совмещённых ролей.

## Decisions

- Общие константы этапов инженерного чтения применяются в visibility и UI. Full-project и assigned helpers сохраняются для прежних потребителей. Общий read predicate объединяет самостоятельные ENGINEER/FIELD grants; чистый ACCOUNTANT не получает операционного чтения.
- Задачи продолжают читаться по прежнему назначению/участию, дополнительно пересекаются с разрешённым инженерным родителем; workspace eligibility сама проверяет только живые связи. Прямого самостоятельного read route работ нет: имеющиеся consumers сначала проверяют изделие/проект/задачу.
- Создание/правка обычных работ и preflight загрузки используют прежнюю область изделия отдельным productAssignmentWriteWhere. Новое чтение не расширяет создание у ENGINEER+WORK_COORDINATOR и загрузку у ENGINEER+FIELD; №192 отдельно расширяет только назначение/переназначение/распределение.
- Файлы читаются через свой проект и каждый заданный product/task контекст. Инженерный файловый grant проверяет product задачи, позволяя обычное техническое вложение без исполнения самой задачи. FinanceDocument имеет отдельную модель и route, права которого не меняются.
- Для ENGINEER+FIELD техническое описание доступного по инженерному grant изделия не маскируется производственной ролью. Денежная маска остаётся самостоятельной.
- Первый инженерный фильтр добавляется только к голому маршруту. Явный URL целиком имеет приоритет. Новые сохранения содержат маркер инициализации инженерного фильтра; старое сохранение без инженера и маркера получает self, сохраняя остальные настройки. Старый непустой выбор инженера сохраняется.
- UI проектов получает roles, чтобы одинаково ограничить колонки и фильтр статусов; фильтр инженера показывается. Product UI использует существующий visibleProductStatuses с расширенным инженерным набором.

## Risks / Trade-offs

- [Случайное расширение изменения] → assigned/participant, current-status и task-execution helpers не изменяются; проверяются негативные действия на читаемых чужих изделиях.
- [Файл задачи скрытого изделия] → каждый заданный контекст проверяется независимо, сохраняются live/draft guards и retired-media guard.
- [Старая пустая настройка ошибочно принята за осознанный All] → отдельный маркер в новых JSON-сохранениях без миграции БД.
- [Пересечение с №193] → №193 интегрируется обычным merge; активные статусы и legacy labels сохраняются по её контракту.

## Migration Plan

Миграции БД нет. Совместимый codec читает прежние версии и новые значения. Выпуск проходит через обычные local/staging проверки; фактическая staging/production-приёмка фиксируется владельцем отдельно.
