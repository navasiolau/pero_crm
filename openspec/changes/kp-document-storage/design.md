# Design

## Context

См. proposal.md. Владелец согласовал реализацию всей очереди №180–189; этот change реализует только аддитивный фундамент хранения. В текущей CRM нет моделей документов генератора. Действующие receipts ChangeLog и outbox DomainEvent сохраняются для последующих операций синхронизации и очередей.

## Goals / Non-Goals

**Goals:** выразить принадлежность объектов внешними ключами PostgreSQL, дать типизированный формат полного состояния без потери legacy-полей и доказать безопасность аддитивной миграции.

**Non-Goals:** публичные маршруты, новая нумерация проектов/изделий, изменение прав, цен, статусов, вызовы R2/S3 и запуск workers. Эти изменения принадлежат №181–189.

## Decisions

- Модели CommercialProposal, ProposalItem, ProposalVersion, ProposalMedia, ProposalCurrentMedia, ProposalVersionMedia, ProposalArtifact, ProposalContract, ProposalContractSource, ProposalContractVersion и ProposalJob. Файлы имеют отдельные строки, поэтому метаданные документа не превращаются в публичные проектные вложения.
- Текущее состояние — JSONB и CAS-revision; опубликованные версии — самостоятельные полные снимки с триггером PDF/CONTRACT/IMPORT, а не копии Project/Product. Исходный sourceId уникален, createdAt устанавливается из источника при импорте. Связь Project однозначна и необязательна для архива.
- Составные FK связывают принятую версию, PDF, DOCX и ссылки изображений с владельцем. В ProposalContractVersion источники сохраняются JSON-снимком без FK к очищаемым версиям КП, чтобы принятая политика очистки не разрушала договоры.
- Порядок ProposalItem уникален только для активных строк (частичный индекс PostgreSQL). Изменение уникальности Product.number относится к №181.
- Файлы принадлежат приватному пространству `kp/`, хранят SHA-256, размер, storage-binding без секретов и состояние удаления. Отдельные ссылки current/version позволяют следующей задаче очистки доказать использование оптимизированного изображения. Копии File карточек изделий будут самостоятельными объектами №183.
- Долгие задания имеют dedupeKey, snapshot, attempts, availableAt и lease. Физические побочные действия выполняются последующими consumers; миграция не запускает их. Отдельную таблицу receipts не добавляем: последующие команды используют действующий ChangeLog.
- Полный state проверяется как ограниченный JSON-объект со списком позиций. Неизвестные JSON-поля сохраняются; циклы, нечисловые значения, неоднозначные прототипы и опасные ключи отклоняются до сериализации.
- `PERO_KP_ENABLED=1` — единственный включающий флаг, отсутствие/другие значения выключают модуль. Пока нет пользовательских точек входа, чтение флага само по себе ничего не запускает.

## Risks / Trade-offs

- Частичные индексы и CHECK не выражаются полностью в Prisma → SQL хранится в миграции, поведение проверяется настоящим PostgreSQL.
- Возможные ошибки составных FK → native-сценарии чужой принятой версии, PDF, DOCX и изображения, а также нормальных принадлежащих ссылок.
- Схема существующей local БД может отставать → до постоянной миграции сверить историю. При несовпадении не применять чужие ожидающие миграции автоматически; сценарии новой миграции можно проверить целиком в откатываемой транзакции разрешённой БД.

## Migration Plan

Сгенерировать SQL diff от staging-схемы к новой схеме, добавить именованные ограничения. Сначала выполнить нативные сценарии с BEGIN/ROLLBACK на существующей local БД 5433, проверив имя БД и fingerprint существующих таблиц. Постоянное применение допустимо только после подтверждения совпадения истории; local/staging без дампов и seed/reset. Production и его миграция остаются отдельным выпуском по AGENTS.md. Откат приложения совместим с добавленными пустыми таблицами; автоматически удалять их при откате не нужно.
