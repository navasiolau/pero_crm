# Spec Delta

## ADDED Requirements

### Requirement: Физическое удаление вытесненного текущего эскиза

Система SHALL при подтверждённой замене удалить ровно прежний текущий эскиз из вложений изделия и физического хранилища, включая миниатюру, все версии и delete markers их точных ключей. Разрешённый технический доступ SHALL позволять инженеру DESIGN заменить эскиз другого сотрудника или эскиз без автора; обычное право удаления остальных вложений SHALL не расширяться. Ранее сохранённые исторические вложения SHALL не удаляться массово.

#### Scenario: Инженер заменяет чужой текущий эскиз

- **WHEN** инженер с актуальным техническим доступом к изделию DESIGN загружает новый эскиз с точным идентификатором прежнего текущего файла
- **THEN** новый файл становится текущим, прежний File отсутствует во вложениях, а его original и thumbnail не имеют оставшихся bytes, версий или delete markers

#### Scenario: Предыдущий эскиз также служит активной обложкой

- **WHEN** исходный эскиз имеет другую активную cover ссылку
- **THEN** замена отклоняется до изменения данных, обе текущие ссылки и bytes сохраняются

#### Scenario: Ошибка до подтверждённой замены

- **WHEN** upload/storage или транзакция не завершились, baseline устарел либо переданный исходный файл принадлежит другому изделию
- **THEN** прежний File, pointer и bytes сохраняются, новый текущий файл другого запроса не изменяется

### Requirement: Восстановимое завершение очистки после замены

Система MUST физически удалять прежний эскиз только после подтверждённой атомарной замены. Система SHALL сообщать об успехе загрузки только после полной очистки; сбой после COMMIT SHALL явно сообщать, что новый эскиз уже сохранён, а очистка прежнего ожидает завершения. Точное задание очистки MUST сохраняться независимо от HTTP-ответа и последующих замен; повтор той же операции SHALL завершать очистку без нового файла.

#### Scenario: Хранилище отказало после COMMIT

- **WHEN** новый эскиз сохранён, но удалить original или thumbnail прежнего файла не удалось
- **THEN** ответ503 содержит committed cleanup-pending результат, old File уже отсутствует во вложениях, клиент может явно повторить тот же запрос, а сохранившееся задание завершает только точную прежнюю очистку

#### Scenario: Конкурентная доставка одной операции

- **WHEN** два запроса отправляют одну mutation и одинаковое изображение
- **THEN** существует один новый File, один подтверждённый результат и одно точное задание старой очистки; дополнительные новые bytes второго запроса не затрагивают победителя

#### Scenario: Повтор результата, уже заменённого следующим изображением

- **WHEN** клиент повторяет прежнюю mutation после новой подтверждённой замены
- **THEN** ответ сообщает конфликт с текущим указателем, не подтверждает удалённый прежний результат и не удаляет текущий winning файл; pending очистка прежней операции остаётся восстановимой
