# Design

## Context

См. proposal.md. ChangeLog содержит и бизнес-аудит, и квитанции повторных операций; прямое изменение raw actorId/oldValue/newValue может сломать повтор денежных и других команд. Исторические payloads неоднородны: scalar field, объект полей, либо result/fingerprint.

## Goals / Non-Goals

**Goals:** чистый JSON-контракт v1, полные безопасные сравнения, точная классификация и совместимый writer для следующих задач.

**Non-Goals:** чтение БД, UI, backfill и перевод domain callers. Их реализуют №222–228; здесь нет самостоятельно применённой миграции.

## Decisions

- `presentation Json?` хранит actor, initiator, reason, entity, contexts, action/source, changes, links, technical; `searchText String?` содержит всю безопасную информацию события и исходные безопасные значения. Исходная запись остаётся источником фактов.
- JournalScope имеет global/project/product. Контексты передаются явно; контекст изделия не расширяется до родительского проекта. Исторический resolver в №222 предоставляет только подтверждённые связи.
- Два отдельных снимка hints.before/after не заменяют raw oldValue/newValue. Объектные изменения сравниваются по полям рекурсивно; массивы сохраняются полностью как одно значение, исключая вымышленные соответствия позиций без устойчивого идентификатора.
- Секреты очищаются рекурсивно по именам полей и по явно обозначенному field; парольChanged и идентификаторы токенов остаются безопасными фактами. Строки с credential URL, Bearer и private key очищаются также в свободном тексте.
- Исполнитель системы задаётся явно либо определяется только actorType system/plugin. Не применяется эвристика по actorName или source api.
- Известные технические квитанции классифицируются точным сочетанием entity/action/ID prefix. Отдельные бизнес-операции, хранящиеся в receipt, остаются событиями.
- Общий writer принимает переданный tx; старый writeChangeLog вызывает его на том же Prisma delegate. Преобразование unknown JSON повторяет существующую JSON-сериализацию; квитанции не редактируются.
- Миграция добавляет pg_trgm, GIN searchText и expression GIN contexts. Новые поля nullable, старое приложение совместимо со схемой; откат приложения не требует удаления новых данных.

## Risks / Trade-offs

- Неполные старые снимки → beforeKnown/afterKnown и отсутствие выдуманных контекстов.
- Новые неизвестные коды → русская родовая подпись, сохранённые исходные коды в техническом блоке, событие остаётся доступным.
- Исторические секреты → очистка при построении и повторной валидации persisted presentation, тесты на вложенные и scalar значения.
- Отдельный массив как полное значение → более длинное сравнение, но без потери информации и ложного сопоставления элементов.

## Migration Plan

Root применяет штатную миграцию на разрешённых local/staging после проверки цели. Не запускать seed/reset/дампы. Проверить старые поля до/после, доступность расширения и индексов. Rollback приложения допускает сохранение двух nullable колонок. Production вне разрешения задачи.
