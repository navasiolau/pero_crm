# Spec Delta

## Purpose

Обеспечить частичные асинхронные правки проекта с защитой от конкурентной перезаписи и одинаковыми серверными правилами статуса, сохранив права сотрудников, историю и файловые вложения.

## ADDED Requirements

### Requirement: Частичные правки проекта

Система SHALL редактировать разрешённые название, клиента, менеджера, адрес, общий телефон клиента и суммы доставки/выгрузки/монтажа одним полем за запрос, используя ожидаемое прежнее значение и ID мутации. Деньги SHALL передаваться десятичными BYN-строками; пустые existing optional поля SHALL сохранять null, подтверждённый ноль SHALL отличаться от null. Обязательные название/телефон SHALL возвращать field error на пустое/пробельное значение. Currency/initialPrice/служебные даты/вычисляемые суммы SHALL не приниматься новым generic patch.

#### Scenario: Malformed envelope
- **WHEN** любой transport передаёт null, примитив, массив, неизвестное поле либо отсутствующий ID
- **THEN** возвращается validation до чтения опасных свойств/DB writes, реальные metadata не подменяются вымышленными field/UUID/baseline

#### Scenario: Изменяется стоимость доставки
- **WHEN** менеджер меняет доставку с null на подтверждённый ноль
- **THEN** сохраняется ноль BYN, ответ возвращает новое значение и только лёгкую новую ожидаемую сумму; исторические платежи/снимки не переписываются

#### Scenario: Неизвестная стоимость изделия
- **WHEN** сохраняется валидная услуга проекта с хотя бы одним изделием без цены
- **THEN** услуга сохраняется, subtotal/expected total остаются неизвестными null; известная нулевая цена и отсутствие изделий не подменяются неизвестностью

#### Scenario: Поздняя денежная проекция
- **WHEN** поздний ACK услуги несёт более старую версию product subtotal, чем уже полученная проекция
- **THEN** UI сохраняет новейший subtotal и подтверждённые baselines своих трёх service полей без перезаписи соседнего поля

#### Scenario: Клиентская связь
- **WHEN** телефон сохраняется из проекта после чужой смены clientId
- **THEN** сервер возвращает менеджменту конфликт связи и актуальный target context без writes; UI сохраняет draft и ждёт явного accept/rebase, не перенаправляет запись автоматически

### Requirement: CAS и совместимость всех обычных writers

Система SHALL упорядочивать запросы поля, проверять baseline под общей транзакционной блокировкой и возвращать конфликт без перезаписи чужого значения. Повтор ID с тем же payload SHALL не повторять реальные эффекты; изменённый payload ранее применённого ID SHALL отвергаться. No-op SHALL не писать audit/outbox. Старые полные формы, web/API/бот SHALL использовать подлинный клиентский baseline и общие операции; сервер SHALL не подставлять текущие значения вместо baseline. Изменение, аудит и необходимый outbox SHALL фиксироваться одной транзакцией.

#### Scenario: Старая полная форма
- **WHEN** другой пользователь изменил поле после открытия проектной формы, а прежняя форма отправляет изменённое значение с прежним baseline
- **THEN** изменение этого поля отклоняется; неизменённые относительно формы поля не отправляются и не перезаписывают чужие новые данные

#### Scenario: Потерянный ответ бота
- **WHEN** бот повторяет прежний field payload после потерянного ACK с тем же ID и projectId в URI
- **THEN** тот же общий core/receipt возвращает подтверждение без повторного audit/outbox; несовпадение URI и body отклоняется до записи

#### Scenario: Поздний ответ
- **WHEN** пользователь ввёл второе название до завершения сохранения первого
- **THEN** ответ первого обновляет его baseline, но не сбрасывает новый draft; ошибки/конфликты не блокируют ввод соседних полей

### Requirement: Единый переход статуса

Система SHALL применять селект карточки, kanban drag, web/API/бот через одно доменное действие, проверяющее expectedStage, права и допустимый ProjectStage. Новый переход REFUSED SHALL требовать непустую refusalReason, а refusalComment SHALL оставаться необязательным. Новый переход RECLAMATION SHALL требовать непустые reclamationReason, reclamationDescription и reclamationFault. При отсутствующих данных/конфликте SHALL не меняться stage/даты/history/audit/outbox. Перед переходом UI SHALL успешно завершить dirty денежные и связанные изменения; отказ flush SHALL блокировать status request. Project status SHALL не начислять процент изделия.

#### Scenario: Отказ без комментария
- **WHEN** менеджер отправляет REFUSED с актуальным expectedStage и непустой причиной без комментария
- **THEN** переход сохраняется один раз; повтор не создаёт вторую историю, отсутствие комментария не блокирует действие

#### Scenario: Неполная рекламация
- **WHEN** любой writer отправляет RECLAMATION без причины, описания или виновной стороны, либо пустые значения
- **THEN** сервер возвращает field error до любых записей; drag/select возвращаются к подтверждённому статусу, введённые extras доступны для исправления

#### Scenario: Конкурирующие переходы
- **WHEN** два пользователя отправляют разные стадии от одного expectedStage
- **THEN** один переход сохраняется, второй получает conflict с актуальной разрешённой стадией без перезаписи

### Requirement: Порядок проекта и ролевой доступ

Система SHALL показывать название первым, затем «Статус». Поле «Инженеры назначенные в Изделиях» SHALL быть серым readonly и выводить уникальные назначения только из доступных изделий. Основные вкладки SHALL иметь порядок Общее → Изделия → Файлы → Задачи → Материалы → Финансы с прежними правами. Коммуникации/история SHALL исчезнуть из карточки без удаления данных; общий административный журнал SHALL сохраниться. Первоначальная цена SHALL не показываться в карточке/новых формах проекта, не меняя её снимки.

#### Scenario: Ограниченный инженер
- **WHEN** назначенный ENGINEER открывает родительский проект со своим DESIGN и недоступными изделиями
- **THEN** readonly список/агрегаты используют только разрешённые изделия, денег/чужих назначений не добавляется; менеджмент/совмещённые роли сохраняют свои разрешённые изменения

### Requirement: Единый список файлов

Система SHALL отображать файлы проекта одним списком без групп категорий/этапов; контекст принадлежности допустим в строке. Добавление, просмотр изображений, скачивание и подтверждённое удаление SHALL сохранять прежние серверные ACL оригиналов/превью. PDF SHALL оставаться обычным вложением; загрузка SHALL не извлекать данные, не менять цены/валюту/initialPrice/статусы и не удалять старые вложения.

#### Scenario: Два PDF-КП
- **WHEN** менеджер прикрепляет второй PDF к проекту
- **THEN** оба файла доступны в flat list по прежним правам, финансовые и технические данные неизменны; удаляется только явно подтверждённый ID

### Requirement: Компактность и фактическая приёмка

Сохранение поля SHALL не вызывать полную RSC-перезагрузку/историю/экономику/FX/генератор, включая косвенный revalidatePath/tag. Ответ SHALL содержать только разрешённое подтверждение/затронутые лёгкие производные. Приёмка SHALL проверять сеть/query profile, concurrency/rights/extras, адаптивность и фактическую staging-ревизию отдельно от local build.

#### Scenario: Медленная сеть
- **WHEN** title POST задержан/отклонён при sidebar/200% browser zoom
- **THEN** соседний ввод доступен, draft не потерян, нет полной card Flight/refresh и горизонтального выхода страницы
