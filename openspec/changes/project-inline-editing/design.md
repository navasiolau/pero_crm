# Design

## Context

Реализация №18 ведётся в feature/18 от origin/staging6edd76ef2cee0b7ce40c5df4399ea9b7570b0728. №17 фактически принят оркестратором для app source6edd; последующий docs-only ref5f не меняет приложение, поэтому integration gate №17 выполнен. №18 имеет локальные unit/native/build результаты, но окончательный compiled browser проход после PDF fix и собственная staging-приёмка ещё pending. Владелец делегировал работу до tested staging; main/production исключены. Evidence ниже и private verification отделяют local proof от hosted deployment.

Актуальные seams: `projects/core.ts` уже общий DomainActor writer web/бот; №17 добавляет contactBaseline адреса/clientId, только изменённые контакты и transactional audit. `projects/stage-core.ts` имеет status/history/audit/outbox, но фактически не проверяет обязательность extras или expectedStage; прежний комментарий не является доказательством такого правила. `projects/[id]/overview-tab.tsx` по-прежнему full form. `projects/[id]/page.tsx` загружает history/communications/economics и иной порядок tabs. `files-tab.tsx` группирует category/stage и переиспользуется в других карточках. №17 даёт inline-save-controller/hook/fields/provider primitives, product/core, shared `projects/contact-core.ts`/`clients/core.ts`, MANAGER_ROLES, required phone и exact CAS. Широкий field-save нельзя маршрутизировать через старый action с revalidatePath.

## Goals / Non-Goals

**Goals:** ProjectPatch/ProjectStagePatch с теми же надёжными primitives; полноценный baseline всех обычных Project полей; лёгкие expected totals; exact UI order/readonly engineers/flat files без изменения данных/ACL.

**Non-Goals:** новая payment/payroll экономика, финансовые snapshot migrations, initialPrice автоматика/массовое заполнение №26, изменение продуктовых процентов, PDF parsing, новые dependencies, production. Нет исторически доказанного DONE-only ограничения рекламации: №18 не вводит его по одному комментарию; поддерживает фактическую прежнюю матрицу стадий плюс новые обязательные extras.

## Decisions

### ProjectPatch и shared primitives

Закрытый discriminated contract: projectId, field, value, expectedValue, clientMutationId UUID; allowlist `title`, `clientId`, `managerId`, `address`, `client.phone`, `delivery`, `unloading`, `installation`. Phone — required nonblank string, expectedValue допускает точное legacy "", expectedClientId обязателен. Manager/address и суммы используют null по их existing schemas; manager changes проверяются по действующему допустимому списку активных менеджеров. Деньги decimal strings максимум существующего Decimal поля, не Number float. Исключены currency, initialPrice, stage из generic contract, timestamps/derived columns.

Project result повторяет №17 discriminant saved/validation/conflict/forbidden/not-found/failure, mutationId, field/currentValue, binding conflict currentClientId/label/phone только менеджменту, saved confirmed value и ограниченный derived DTO. No-op не пишет audit/outbox/новый receipt; только реальные mutations используют существующий ChangeLog receipt project-inline:UUID, actor/entity/fingerprint проверяются до replay. Права заново проверяются до conflict/replay. Схема разбирается до обращения к input.field/IDs; null/undefined/primitive/array/missing-ID возвращают typed validation без DB. Малформенный ответ содержит только действительно распознанные metadata, не фиктивные baseline или идентификаторы. Переиспользовать schema-derived подход №17.

Переиспользовать inline-save-controller/useInlineSave/маленькие fields из №17, не новый queue implementation. Проектный provider задаёт field serializers и общий dirty/flush coordinator. Независимый Server Action transport №17 (lib/independent-action-transport.ts) переиспользуется с узким project wrapper и импортированной зарегистрированной patchProject reference: current same-origin /projects/<id>, public Flight encodeReply/codec, unbound reference, no пользовательский URL/ID/API fork. Installed Next/React pin/codec, запрет redirect/revalidation/full Flight и реальные delayed neighbor ACK проверки повторяются на project странице. Не вызывать обычный router-global action proxy для каждого поля, поскольку №17 actual browser показал задержку соседнего подтверждения. Enter+blur/no-op dedupe, latest queued value, потерянный ответ повторяет тот же ID, conflict/error сохраняет draft. Переключение clientId и phone sharing следует явному rebase из №17; автоматический перенос dirty phone на нового клиента запрещён.

### Общий Project/Client core, совместимость полной формы и бота

Контактный primitive №17 обобщить на projectId (`patchProjectContactInTransaction` либо эквивалент), а product wrapper продолжает выводить projectId из Product. Проект без изделий редактируется прямо, фиктивный Product не создаётся. Общие Project.address/clientId/Client.phone используют один CAS/role/audit/outbox implementation и Project→Client locks. Existing global withTaskTransaction остаётся коротким guard; Product/Work/Material locks используются только профильными операциями, не обычной project title правкой.

Новый field action auth→core→DTO не вызывает revalidatePath/tag/router.refresh прямо или косвенно. Старый full `updateProjectCore` адаптируется к genuine baseline для ВСЕХ отправленных обычных полей: сравнить desired с captured baseline, передать только changed, затем CAS актуального значения внутри tx. Missing baseline изменённого поля — явный stale-form error; не брать server current как baseline. Старый overview transport заменяется inline, но ручной вызов старого action также защищён. Обычные bot field edits используют тот же закрытый ProjectPatch через существующий PATCH /api/v1/bot/projects/:id, с проверкой body.projectId==URI и тем же persisted receipt. UUID создаётся при открытии диалога и сохраняется для retry потерянного ACK; {ok,...typed result} остаётся совместимым ответом. Legacy full-baseline путь сохраняется для существующей compatibility. Bot dialog/API передают сохранённые значения, полученные при открытии диалога/карточки; не запрашивают новое значение непосредственно перед write для маскировки конфликта. Stale historical initialPrice payload относится к compatibility №26, не расширять новым inline allowlist или возвращать hidden snapshot в DTO.

Для изменения поля data/audit/необходимый существующий outbox сохраняются одной транзакцией. Внешние FX/notify/plugin dispatch не удерживают lock. Reuse профильного domain helper, не старого transport с side effects; event доставляется существующим postcommit/outbox процессом. Никаких дублирующих записей поверх receipt/audit для replay.

### Лёгкие derived totals

Title/manager/address/phone читают только current scalar/access/минимальные выбранные подписи. Delivery/unloading/installation возвращают новую expected total по существующему product-quantity helper: Σ unit prices×quantity видимых/разрешённых изделий + текущие project services, Decimal строки. Для этого отдельный компактный select products(expectedPrice,quantity), без tasks/files/history/communications/Payment/PayrollEntry. Не возвращать paid/margin и не вызывать getProjectEconomics/NBRB. Если хотя бы одна Product.expectedPrice отсутствует, productsSubtotalBYN и expectedTotalBYN остаются null, но сама валидная service правка сохраняется; known zero и проект без изделий дают известный ноль. Service derived DTO включает явный productsSubtotalBYN, три подтверждённых service поля и pricingVersion — строку txid_current() из текущей короткой глобально сериализованной транзакции, без часов/миграции. UI принимает subtotal только из новейшей версии и суммирует свои подтверждённые service baselines, не переписывая соседние контроллеры поздним ACK. Initial/RSC получает такую же pricing projection через getProjectPricingProjection: свежие Project services/currency и Product prices/qty вместе с txid_current читаются под тем же short global lock. Свежая версия не приклеивается к ранее загруженным page prices. Только full money-viewers MANAGER/FINANCE получают aggregate; legacy non-BYN возвращает отсутствие BYN-проекции без перемаркировки raw prices/services, поле редактирования денег остаётся запрещённым до ручной подготовки. Это readonly business-data операция без новой схемы или API. Менеджмент получает разрешённую полную project sum; readonly limited engineer не получает hidden service/expected aggregates. Исходные финансовые снимки и frozen guards №16/17 сохраняются.

### ProjectStagePatch и новые обязательные extras

Профильный status contract: projectId, toStage, expectedStage, clientMutationId, closed extras object. REFUSED — trim непустая refusalReason, refusalComment optional (пустое→null); RECLAMATION — непустые reclamationReason/Description/Fault. Не выдумывать справочник причин/сторон: сохраняется действующая текстовая модель. Обязательность — новое явное решение текущего плана; actual old core ещё позволяет неполные запросы. Исторические стадии/пустые extras не переписываются массово.

После role/access check и receipt replay lock Project; прочитать actual stage, сравнить expectedStage, validate новый переход/extras до любых writes. Same-stage no-op не переоткрывает/не пересоздаёт историю и не требует заполнять старую историю; реальный новый transition требует полный новый contract. Status/time/history/audit/outbox атомарны, Project stage не начисляет product percentages. Перенести validation в stage-core так, чтобы web select/kanban/actions/API/бот использовали один путь. Старые writers без expectedStage получают отказ обновить форму/диалог, не свежий server baseline.

Селект/drag к REFUSED/RECLAMATION сначала открывают общий extras dialog, не фиксируют промежуточную стадийную запись. Cancel/validation/CAS conflict откатывают optimistic позицию к confirmed stage и сохраняют введённые extras. `StageFormDialog` получает field errors; optional отказный комментарий не блокирует. Existing bot отказный шаг комментария допускает «—» как отсутствие; capture expectedStage при начале диалога. Перед select/drag из карточки `flush()` проектных денежных/связанных dirty fields; failure отменяет status POST. Board без открытых drafts сохраняет свою confirmed stage baseline.

### Карточка, скрытые данные и flat files

Overview: название первым, «Статус» вторым, прочие existing fields через общие inline controls; initialPrice UI скрыт, snapshot value/data/writers не переопределяются по новым правилам №26. Инженеры — unique engineerId из доступных Product, grey readonly, label точно «Инженеры назначенные в Изделиях»; не новая Project.engineerId запись.

Tabs строго Общее/Изделия/Файлы/Задачи/Материалы/Финансы с текущими role gates. Remove communications/history card controls и ненужные загрузки данных этой карточки, сохранить таблицы/events/admin Changelog. Plugin tabs/visibility не ломать: если существующие плагины добавляют разрешённые tabs, сохранить их после основных, без подмены основных шести.

Flat project files реализовать узким режимом/компонентом поверх существующего FileRow/upload/view/delete primitives. Категория/stage остаются в stored metadata и принимаются существующими file validation rules, но не образуют видимые группы; контекст привязки Project/Product допустим в строке. Original/thumbnail/delete/upload route guards неизменны. Для PDF просмотра используется явный ?view=1 на существующем GET /api/files/:id: только mime application/pdf становится inline с nosniff после той же actor/file ACL проверки. Download URL без view остаётся attachment; HTML не становится inline. Это исправление фактического attachment-only просмотра, без нового storage endpoint или extraction. Новое PDF не вытесняет старый, extraction/FX/snapshot callbacks отсутствуют. Files mutation не должна уничтожать dirty project drafts: если существующий postupload refresh сохраняется, provider явно удерживает drafts либо перед mutation выполняется согласованный flush; не вводить full field refresh.

## Risks / Trade-offs

- [Old baseline guard №17 был только контактов] → №18 защищает каждое обычное project field и всех его web/bot/old-action consumers; тест старой формы против inline edit.
- [Mandatory extras воспринимаются как «уже существовали»] → отдельные RED текущего core с пустыми extras; старые данные не backfill, новые transitions строго validated.
- [Кеш invalidation незаметно возвращает полный Flight] → network/response bytes и server SELECT profile; запрет revalidate в обычном field path независимо от small request.
- [Список инженеров раскрывает чужие изделия] → reuse visibility filtering, unique only разрешённые IDs, roles/CAS conflict DTO не расширяют доступ.
- [Flatten files теряет ACL/metadata] → visual only aggregation, сохранность точных IDs/paths и guarded direct original/preview/delete tests.
- [Общий global lock и медленная экономика] → только scalar/minimal price select, никакого внешнего FX/полных history запросов под lock.

### Ограниченный QA и сохранность Cloud metadata

Native/compiled browser runs выполняет только оркестратор на guarded существующем local/staging. Owned fixtures имеют immutable HMAC checkpoint/observation, target proof, exact row IDs и allowed mutable fields, CAS перед cleanup и проверку original-data fingerprints; immutable/frozen бизнес-снимки не удаляются. Uploaded own PDF keys фиксируются по точному projectId/storedName; SDK HeadObject проверяет только metadata присутствия/размера этих точных ключей, не скачивает содержимое, не делает list/prefix cleanup. Возврат baseline перед cleanup и отсутствие точных owned keys обязательны; если guard/ownership mismatch — STOP и сохранение состояния. В текущем local fail-run оба own PDF keys и DB fixtures удалены/проверены, prefs CAS restore подтверждён; это не доказательство полной browser/staging-приёмки.

## Migration Plan

Official CLI planning artifacts готовы на provisional 7eb10ae. После staging17: актуализация context/requirements по accepted source и fresh feature/18 только оркестратором. RED→GREEN server contracts/status/CAS/roles/snapshot integrity и UI queue/browser/network. Existing local/staging без migration/reset/seed/дампов/restic; runtime/QA данные только в разрешённом контуре. Один атомарный №18 commit, обычный merge staging, CI и actual image/SHA/health/acceptance; release main/production не входит. Исправления повторяют этот же pipeline, общая история не переписывается.

## Open Questions

Перед implementation сверить latest accepted №17 paths/final inline/contact/independent transport DTO и новые fixes относительно provisional 7eb10ae. Эти технические обновления не меняют согласованный scope и не требуют повторного разрешения владельца.
