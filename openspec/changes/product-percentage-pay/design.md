# Design

## Context

См. `proposal.md`. Текущая схема уже начисляет инженеру процент фонда изделия через Work weights и Task shares; отдельно сохранён legacy project writer. Новое поведение заменяет обязательную привязку начисления к работам/задачам для будущих ENGINEERING/INSTALLATION этапов, расширяет монтажную часть и прекращает начислять новые проценты по движениям проекта. Существующие Work/Task allocations и исторические начисления сохраняются.

## Goals / Non-Goals

**Goals:** получить прямые доли участников этапов изделия, immutable first-completion/earning snapshots, безопасный FX retry и единый статусный handler.

**Non-Goals:** 3D viewer/import, пересчёт существующих выплат/начислений или старых Work weights/Task shares, новые выплаты из project status, disposable database, production rollout, создание live QA пользователей/проектов/задач/файлов/начислений.

## Decisions

1. **Новая отдельная конфигурация изделия.** Ввести аддитивные ProductPercentageConfig и members для отдельных ENGINEERING/INSTALLATION ставок и прямых долей активных сотрудников нужной роли. Первый участник получает 100%; передача части своей доли активному коллеге увеличивает его текущую долю либо добавляет его в этап. Сервер валидирует ровно 100% и запрещает изменение чужой доли/ставки без MANAGER_ROLES. Для существующих неоплаченных монтажных Work доступна отдельная явная менеджерская классификация источника INSTALLATION: без бюджета/весов; по `Task.type` и названию автоматически не выводить.
2. **Неизменяемая первая фиксация по этапу.** Хранить отдельный immutable completion/earning snapshot с полным набором входов и уникальностью по продукту+этапу, связанный с PayrollEntry. Значения 0 валидны. Отсутствующая конфигурация фиксируется `skipped_once` без позднего auto-accrual; временная FX ошибка создаёт distinct `pending` с полной копией frozen inputs. Retry меняет только исход внешней конвертации, не исходные значения.
3. **Один status handler и устаревшие pool actions.** Все board/dropdown/card status entry points проходят один проверенный handler. Старые pool mutation actions остаются совместимыми только как отказ до записи, чтобы обход этого handler не начислял средства и не менял старые распределения. PROJECT status больше не создаёт новых процентных записей; существующие legacy project entries остаются историей.
4. **Точная граница полномочий.** При эффективном праве ENGINEER пользователь может только DESIGN→PRODUCTION и только с B3D того же продукта либо `noModel=true`; файл сам статус не меняет. `noModel` default false, менять может только management. WORKER/MOUNTER без разрешающего совмещённого права статусы продукта/проекта не меняют; DONE монтажа подтверждает ADMIN/DIRECTOR/MANAGER. Менеджмент может менять проектные и продуктовые статусы свободно, без начисления от движения проекта. UI не должен изображать отказ сервера как успешный переход.
5. **Сохранение доступа в DESIGN.** Обновить общий policy: чистый ENGINEER видит назначенное/участвуемое изделие только в DESIGN и теряет инженерный доступ после PRODUCTION; WORKER/MOUNTER скрывают DESIGN. Совмещённые роли объединяются по обычным правилам; роль с более высоким приоритетом задаёт поведение менеджмента (M+E действует как manager). Одинаковая проверка применяется к спискам, поиску, direct links, вложенным данным и файлам.
6. **Только forward-compatible schema work.** Миграция аддитивная, nullable/default-safe, без переинтерпретации или удаления прежних финансовых данных. Перед применением — review SQL и совместимости с существующими target schemas; не использовать disposable/copy DB и не планировать DDL rollback. Production остаётся HOLD до отдельного решения владельца.

## Risks / Trade-offs

- [Параллельные завершения] → уникальный продукт+этап snapshot и серверная сериализация; тест повторов и гонок.
- [FX доступен позже статуса] → сохранить статус и pending frozen inputs, повторить только по действующему источнику курса.
- [Исторические legacy данные неоднозначны] → не конвертировать неоплаченные записи автоматически; старые Work/Task и project entries оставить без изменений.
- [Побочный endpoint обходит статусный handler] → устаревшие pool actions отказывают до записи; проверка всех вызовов одним policy.

## Migration Plan

Статический review SQL, backup/TOC и keyed fingerprint comparison выполнены до применения двух аддитивных миграций к существующему local PostgreSQL:5433. Native local acceptance читала только существующие записи и изображения; новые QA users, client/project/product/work/task/file/config/accrual rows не создавались, живые rate/share/status не менялись. Навигация может автоматически создать метаданные UI-preference: фиксировать точное исходное состояние key/value либо отсутствие строки, восстанавливать только узким compare-and-set и затем сверять полный baseline. Созданная навигацией preference и два значения Plugin.updatedAt после первоначального запуска были восстановлены в точное исходное состояние; исправленный запуск подтвердил отсутствие дрейфа business data. Staging acceptance остаётся NOT RUN. Backup restore-test, disposable/copy DB, очистка бизнес-записей и SQL fixture pipeline не выполнялись. Frozen-FX retry покрыт offline DI; live positive accrual остаётся NOT VERIFIED. Production и main — HOLD.
