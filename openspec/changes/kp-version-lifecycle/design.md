# Design

## Context

См. proposal.md. Базовая ветка ещё не содержит моделей №180; зависимости интегрируются обычными merge, без копирования файлов. Изменение этапа централизовано в projects/stage-core.ts и уже защищает CAS, receipt, историю и outbox.

## Goals / Non-Goals

**Goals:** общий транзакционный жизненный цикл с типизированными портами для renderer/storage/security, повторяемость команд и пригодность финализации для общей транзакции договоров №186.

**Non-Goals:** HTTP/UI, запуск live workers, операции с S3, очистка объектов, перезапись исторических начислений и самостоятельная интеграция веток.

## Decisions

- Использовать типизированный store и Prisma SQL-адаптер: SQL обращается к моделям №180 без временного копирования их схемы в №185. Приёмка настоящей БД обязательна после интеграции зависимостей.
- ProposalVersion.renderSnapshot хранит binding клиента/проекта, медиа и параметры renderer; дополнительная колонка не требуется. pricingSnapshot содержит JSON со строковыми Decimal. Job.payload неизменно фиксирует источник и автора до I/O.
- Порядок блокировок: общий advisory mutex №181, Project, CommercialProposal, медиа; stage-core приобретает mutex до существующей Project-блокировки. Бизнес-инвариант этапа не зависит от PERO_KP_ENABLED.
- До загрузки результата существует PENDING ProposalArtifact с неизменяемыми key/binding/hash/size. Сетевой renderer, upload и readback находятся вне транзакции. Финальная транзакция превращает артефакт в READY, вставляет Version/VersionMedia и завершает Job.
- Каждый lease имеет уникального владельца; просроченный worker не может продлить, завершить или повторить задание нового владельца. Следующая попытка использует новый ключ артефакта, исключая перезапись поздней загрузкой.
- Возврат в «Лид» очищает принятие и увеличивает retentionEpoch. Ожидающие PRUNE_VERSIONS прежней эпохи отменяются. «В работе» ставит exact-version/epoch intent; physical executor принадлежит №188.
- Restore требует исторический binding и доступные собственные медиа, затем вызывает сохранение №181 с обязательными pricing/media hooks. Уже выпущенные снимки не редактируются.

## Risks / Trade-offs

- Сетевой сбой может оставить PENDING артефакт → сохранять ledger для последующей проверяемой очистки; не удалять объекты в №185.
- DI не доказывает FK и блокировки PostgreSQL → подготовить native helper, запуск только orchestration root после нормальной интеграции.
- Отзыв API-ключа во время рендера → обязательный source-authorization callback повторяется в транзакции публикации вместе с проверкой активного пользователя/ролей.

## Migration Plan

Дополнительная миграция не требуется: используются таблицы №180 и их JSON-поля. Развёртывать после №180–184, без автоматического старта worker; настоящий staging, SHA/образ и документы принимает основной агент отдельно.
