# Design

## Context

Причина и результат описаны в proposal.md. ClientDialog используется и справочником, и созданием клиента из проекта/изделия. Серверный clients/core уже использует блокировку строки и CAS только изменяемых полей; общий адаптер формы явно передаёт семь baseline-полей. В getProjectFor есть `client: true`, listClients читает все скаляры клиента. Эти чтения после расширения схемы раскрывали бы паспортные данные ограниченным офисным ролям.

## Goals / Non-Goals

**Goals:** добавить реквизиты в существующий поток и оставить контроль доступа и CAS на сервере.

**Non-Goals:** изменение доступа к остальным контактам, импорт/шифрование исторических реквизитов, новые поля бота и API, переписывание финансовых фактов.

## Decisions

- Добавить `passportNumber String?` и `passportIssuedBy String?` отдельной аддитивной миграцией. Значения нормализуются обрезкой пробелов и пустое превращается в null как существующие необязательные контакты; формат паспорта страны не навязывается.
- Для чтения переиспользовать MANAGER_ROLES. Безопасная явная проекция прежних скаляров исключает паспорт из вложенного клиента проекта и listClients; каталог получает паспорт только по управленческому grant. Поиск запрашивает ровно поля своего ответа. Выборка паспорта во всех офисных запросах с последующим сокрытием в React отклонена как небезопасная.
- Расширить строгие input/baseline и список CAS-полей до девяти. Старый baseline отклонять сообщением устаревшей формы: подстановка null могла бы затереть неизвестный паспорт. Адаптер формы передаёт только настоящий baseline, без projects/счётчиков.
- Просмотр и редактор используют те же русские подписи; новый клиент из проекта/изделия получает те же поля. Полный редактор открывается только при наличии обоих паспортных baseline-полей в DTO.
- Изменения паспорта входят в существующий транзакционный журнал old/new; события содержат только clientId и имя поля, без новых паспортных значений. Создание фиксирует сохранённые реквизиты в журнале клиента.

## Risks / Trade-offs

- Новые скаляры могут попасть в старый `include` → проверить все чтения Client и заменить опасные явными select; поведенческие тесты вызывают реальные query/page-пути с заполненными паспортами.
- Аддитивная миграция ещё не проверена на PostgreSQL этим исполнителем → в начале работы local:5433 недоступен; оркестратор позже сообщил проверенный запуск существующего local и оставил миграции/native-проверки за собой. Новый стенд/reset/seed не создавать. Native-проверка и staging остаются незавершёнными до evidence оркестратора, типизация/DI/browser не заменяют их.
- При одновременной интеграции №174 затрагивается схема → интегрировать миграцию №171 первой и не изменять существующие миграции.

## Migration Plan

Сгенерировать Prisma Client, проверить SQL и схему, затем применить миграцию только в разрешённой существующей среде и доказать сохранность клиентов. До runtime-приёмки миграция считается неподтверждённой. При откате приложения nullable-колонки и уже введённые реквизиты сохранить; destructive down-миграцию не выполнять. Production-миграция и выпуск отдельно согласуются оркестратором.
