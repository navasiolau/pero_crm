# Design

**Execution agreement:** Номер задачи 124, ветка feature/124 согласованы владельцем 10.10.2026; OpenSpec и реализация одобрены. Одна целевая локальная проверка, затем существующий полный CI без изменений и развёртывание на staging только через него; одна целевая staging-приёмка. Повторные полные ручные проверки не выполнять без конкретного сбоя. Production/main этим запуском не разрешены.

## Context

Прямое уточнение владельца 10.10.2026: расходы рейса сразу относятся к проектам по долям, обязательная настройка расходной статьи удаляется. Исторические связи со статьями сохраняются, новые логистические проведения создаются без них.

Мотивация — в `proposal.md`, структура рейса/ТТН — в `logistics-trips-and-ttn`. Актуальная база: `origin/staging` `ab1c77f3b82cab788f206914d5b2a063e6aafe68`.

`preparePayment` фиксирует валюту кассы и FX/BYN-снимок. `createPaymentInTransaction` под общим денежным lock проверяет баланс кассы/организации и требует отчётный файл обычного расхода. `FinanceDocument.reportDocumentId` уникален на Payment; он не представляет одну ТТН для нескольких проектов. `activePaymentWhere` сейчас исключает `deletionId`, его используют кассовые/организационные суммы и проектная экономика. Оплаченная складская закупка уже имеет отдельный server-only составной контекст вместо клиентского обхода правил.

## Goals / Non-Goals

**Goals:** доказуемое кассовое проведение одного рейса и точная сумма проектных долей, повтор без второго списания, безопасные исправления и единый источник фактических затрат.

**Non-Goals:** разбивка затрат на топливо/зарплату/износ, создание фиктивного дохода для исправления, переоценка прежних курсов, перепривязка исторических расходов, новые права бухгалтера на правку рейса.

## Decisions

1. **Проведение связано с ревизией рейса.** `LogisticsPosting` содержит trip ID, revision, actor, mutation ID/fingerprint, общую сумму, валюту/кассу, rate/date и исходные документы. `Payment` связан с immutable allocation и соответствующим проектом. Исторический `expenseArticleId` остаётся nullable; новые проведения и их Payment сохраняют NULL. Одна транзакция фиксирует проведение и расходы всех проектов; до её завершения ни один из них не существует отдельно.

2. **Общее документальное основание — ТТН рейса.** Логистический writer вызывает денежное ядро через server-only проверенный контекст: проведённый состав, правильная касса, доли и минимум один `READY` документ `ISSUED` или `SIGNED` данного рейса. Один исходный файл может подтверждать несколько долей. Обычный публичный `PaymentInput` не принимает флаг отключения отчётного документа и сохраняет прежнее правило. Уникальная связь обычного `FinanceDocument` не ослабляется и его байты не копируются для каждой доли.

3. **Деньги распределяются с сохранением денежного контракта.** Общую стоимость вводят в валюте выбранной кассы. Сумма в минимальных денежных единицах распределяется по процентам методом наибольших остатков; tie-break — стабильный project ID. Сумма частей в валюте кассы ровно совпадает с общей стоимостью. Для BYN это одновременно проектные расходы. Для иной валюты все части получают один rate/date, а каждая `Payment.bynAmount` сохраняет действующее округление своей суммы по курсу. Общая BYN-сумма рейса определяется суммой этих снимков, а не отдельным округлением, способным дать расхождение. Проектные суммы отображаются по сохранённым BYN-значениям; недоступный курс блокирует операцию.

4. **Проектный расход без настройки.** Снабженец указывает стоимость, кассу и доли проектов; каждое ненулевое распределение создаёт проектный Payment с `expenseArticleId=NULL`. Отдельный server-only `prepareLogisticsPayment` формирует снимок кассы/FX. Денежное ядро разрешает отсутствие статьи только после проверки сохранённой логистической allocation, actor и готовой ТТН. Публичный обычный `PaymentInput`, `preparePayment` и обычные расходы сохраняют требования статьи и отчётного документа. Финансовые списки подписывают связанную allocation «Логистика». Прежние платежи и неиспользуемая старая настройка не переклассифицируются и не удаляются.

5. **Повтор и исправление различаются.** Повтор mutation ID с тем же actor/fingerprint возвращает сохранённый результат; другой payload даёт конфликт. Финансовая правка требует актуальную trip revision, создаёт новое проведение и помечает прежнее `SUPERSEDED` в той же денежной транзакции. Его Payment и документальные основания сохраняются. Общий active-payment предикат учитывает только текущие логистические проведения и обычные платежи без этой связи. Аудит всех текущих readers/writers, включая кассы, organization balance, проектную экономику, финансовые списки, Telegram и ограничения удаления — обязательная часть изменения.

6. **Лимиты при исправлении считают итоговое состояние.** Старая стоимость исключается только внутри успешной транзакции, новые расходы проверяются относительно итоговых остатков обеих затронутых касс и организации. Нехватка средств, смена документов или CAS-конфликт откатывают всё, сохраняя старое проведение. Обычный финансовый endpoint не может отдельно удалить логистическую долю; исправление выполняется через рейс разрешённым actor. Искусственный INCOME для возврата старой доли отвергнут, поскольку исказил бы оборот и зарплату.

7. **План и факт имеют разные источники.** Бюджет — сохранённое `Project.delivery` из КП, без выгрузки/монтажа и без разбора PDF. В первой версии это действующий согласованный бюджет проекта; отдельная заморозка раннего КП не вводится. Факт — только сумма действующих проектных Payment, связанных с allocation рейса, каждый Payment один раз. Обычные расходы проекта, материалы и зарплата остаются в общей экономике проекта; сводка доставки их не включает. Остаток = бюджет − факт; NULL/исторически неизвестный BYN не заменяется нулём. Для исторического проекта не в BYN применяется существующий guard, без автоматической конвертации. DTO не содержит `otherSpent` или состояния настройки статьи.

## Risks / Trade-offs

- Пропущенная финансовая выборка учитывает старое проведение → общие active-payment predicates плюс native тесты всех денежных consumers и запрет изменения отдельной доли.
- Части по 0 копеек при очень маленькой общей сумме → нулевая доля сохраняется в расчётной ревизии без нулевого Payment; сумма реальных Payment остаётся точной.
- Исправление меняет кассу → обе кассы проверяются под общей блокировкой, старые FX-снимки остаются историей.
- Обычная операция с похожим названием может попасть в факт доставки → принадлежность определяется только сохранённой logistics allocation, название статьи не используется для выборки.

## Migration Plan

Коррекция после первоначального внедрения добавляет отдельную миграцию `20261010163000_logistics_project_expenses`: только DROP NOT NULL для `LogisticsPosting.expenseArticleId`. Уже применённая `20261010143000_logistics_cash_allocation` не меняется, прежние финансовые строки не переписываются. Deferred-проверка использует IS DISTINCT FROM и уже сравнивает nullable статью проведения с его Payment корректно. Старые денежные/FX-снимки и история исправлений сохраняются.

После первого change аддитивно создать финансовые ревизии/FK/indexes и атомарно обновить активные predicates. Существующие Payment получают NULL-связь и сохраняют прежний учёт; денежные записи не бэкфилятся. Выполнить meaningful RED→GREEN и native PostgreSQL проверки повторов, rounding, кассовых лимитов, конкуренции и superseded-выборок. Local/staging без дампов/seed/reset; только собственные откатываемые QA-данные.

При будущей production-миграции — порядок AGENTS.md с временным дампом и изолированным restore. После появления проведённых рейсов откат на старый writer/reader недопустим: он не знает `SUPERSEDED`. Сначала закрыть новые логистические writes и сохранить reader, понимающий текущие проведения; данные и исходные файлы не удалять. В staging/main выполняются обычные merge, выпуск только отдельным указанием владельца.
