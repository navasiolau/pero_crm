# Design

## Context

Все три журнала используют `JournalWorkspace` из `components/journal/journal.tsx`. Сейчас grid выделяет поиску две доли и принудительно растягивает блок кнопок на пять колонок. Поэтому даже широкая панель занимает две строки. В `SearchableSelect` уже есть `min-w-0` и сокращение выбранной подписи; даты требуют собственной минимальной ширины.

## Goals / Non-Goals

**Goals:** уменьшить ширину поиска и держать все фильтры с кнопками одной строкой при достаточной ширине именно журнала; сохранить пригодность формы при свёрнутом меню, на узком ноутбуке и телефоне.

**Non-Goals:** менять серверные запросы, ACL, параметризацию, данные, управление состоянием, компоненты остальных форм или поведение таблицы.

## Decisions

- Использовать container query общего блока журнала, а не только ширину viewport: проект и изделие получают ту же компоновку независимо от ширины бокового меню.
- При ширине контейнера примерно 58 rem разместить шесть групп: поиск, пользователь, сущность, даты «С», «По», две кнопки. Поиск занимает одну гибкую колонку, сравнимую с выпадающими списками. Даты сохраняют ширину не менее 140 px; кнопки имеют собственную ширину и выравниваются с полями по нижнему краю.
- Ниже порога форма переносит поля на доступные строки, кнопки остаются вместе. Ошибка валидации занимает всю ширину формы отдельной строкой.
- Расширить существующий browser test реального компонента проверкой геометрии полей и кнопок на 1440/1280 px с открытой и закрытой боковой областью, а также читаемости дат и отсутствия переполнения на 1024/390 px. Существующие сценарии Apply/Reset и сохранения scope остаются регрессией поведения.

## Risks / Trade-offs

[Все поля физически не помещаются в одну строку узкого контейнера] → адаптивный перенос без скрытия полей, дат или кнопок; проверять ширину контейнера, а не только экрана.

[Слишком узкая дата на рабочем столе] → фиксировать её минимальную читаемую ширину и проверять фактическую геометрию в Chromium.

## Migration Plan

Миграция БД не требуется. После локальной проверки обычный merge в staging, штатный CI и приёмка оркестратором развёрнутого образа во всех трёх местах. Откат выполняется обычным исправлением/коммитом исходной компоновки без изменения данных.
