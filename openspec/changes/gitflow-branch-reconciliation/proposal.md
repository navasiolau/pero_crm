# Proposal

## Why

После выборочных переносов main и staging содержат разные истории одних и тех же фич. Нужно сохранить проверенную функциональность, актуальные документы выпуска и общую историю, затем установить обязательный порядок работы маленькими ветками от staging.

## What Changes

- Закрепить в AGENTS.md указание владельца от 01.10.2026: одна задача/OpenSpec change на ветку `feature/<номер>`, `bugfix/<номер>` или `hotfix/<номер>`; локальные проверки → merge в staging → приёмка фактически развёрнутого staging → merge всего staging в main.
- Согласовать ветки обычным merge main в staging. Сохранить код принятого product-quantity из staging и более свежие документы предыдущих релизов из main; не переписывать историю и не повторять cherry-pick.
- Включить уже подготовленные итоговые QA/evidence файлы product-quantity из её рабочей ветки; новые правила оформить отдельной маленькой задачей, а не новой бизнес-фичей изделия.
- Обновить прежнее указание `codex/…` в согласованном CRM_IMPROVEMENTS_PLAN.md в итоговом интеграционном кандидате; постороннюю незакоммиченную версию этого файла в исходном checkout сохранить.
- По прямому уточнению владельца исключить restic из задач и дампы local/staging. Только production-миграция требует одного временного дампа БД, проверки восстановления и удаления после успешного выпуска, когда дамп больше не нужен.
- Проверить интеграционный кандидат локально и на staging. После отдельного разрешения выпуска и конкретной production-миграции продвинуть main через fast-forward на принятый staging SHA. После выпуска обе удалённые ветки указывают на один коммит.

## Capabilities

### New Capabilities

Нет: меняются инструкции разработки и согласование Git-истории. В `.openspec.yaml` установлен `skip_specs: true`; новая бизнес-спецификация не создаётся.

### Modified Capabilities

Нет: поведение количества изделий остаётся описанным отдельным product-quantity и не расширяется этим change.

## Impact

AGENTS.md, один пункт CRM_IMPROVEMENTS_PLAN.md, OpenSpec planning/evidence, интеграционные merge-коммиты и refs main/staging. Код приложения должен остаться побайтно равным принятому staging `987787f`; итоговые QA helper/docs из рабочей ветки учитываются отдельно. Для выпуска количества изделий требуется уже существующая миграция `20261001120000_product_quantity`, новой миграции этого change нет. Владелец назначил задачу 1; согласование выполняется в bugfix/1 до проверенного staging. Main push, production-миграция, данные и инфраструктура остаются вне текущего разрешения.
