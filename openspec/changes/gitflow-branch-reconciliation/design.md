# Design

## Context

На 01.10.2026 remote main = `7c51972d4264bd10fb779638cc94c13d6533d6b7`, staging = `987787fbcba9dc17bd72113e882d4732cc4d17d0`. Истории разошлись после backport-коммитов. При этом дерево `apps/` main в точности равно базе количества изделий `a899e8e`; `.github/` также совпадает. Разница main с этой базой — 22 документа/отчёта, а не новая функциональность.

Сухой `git merge-tree` staging/main обнаружил 22 конфликта: 8 файлов приложения и 14 OpenSpec документов. Это следствие разных историй и повторного добавления одинаковых файлов. Рабочая ветка количества изделий `62415eb` добавляет поверх staging только 4 QA/evidence файла; приложение там идентично принятому staging.

AGENTS.md уже дополнен по прямому указанию владельца в исходном checkout и рабочем worktree. Эти правки не закоммичены. Новый change описывает согласование истории; бизнес-спецификации не меняются (`skip_specs: true`).

## Goals / Non-Goals

**Goals:**
- Сохранить весь проверенный код количества изделий, историю обеих веток и свежие документы main.
- Сделать main предком согласованного staging и после выпуска получить одинаковый SHA обеих веток.
- Установить единый обязательный процесс маленьких нумерованных веток.

**Non-Goals:**
- Переработка количества изделий, пересчёт бизнес-данных, новые миграции или изменение deploy/refresh.
- Переписывание опубликованных коммитов, force-push, удаление старых веток или массовое переименование чужих рабочих веток.

## Decisions

### Одна административная задача от staging

После одобрения решения создать `bugfix/<номер-задачи>` от свежего origin/staging в отдельном чистом worktree. Изменения этой задачи — правила GitFlow и согласование истории; новая бизнес-функциональность уже находится в staging. Старую рабочую ветку количества изделий сохранить как исторический источник её четырёх итоговых QA/evidence файлов и влить обычным merge. Старые имена опубликованной истории не переписывать. Все новые ветки именовать по AGENTS.md, включая hotfix.

### Явное разрешение конфликтов при merge main

В рабочей ветке выполнить обычный `git merge --no-ff --no-commit origin/main`, затем разрешить конкретные конфликтующие файлы. Для каждого файла приложения сохранить вариант проверенного staging; после разрешения проверить **всё** дерево apps, чтобы не пропустить ошибку автоматического merge в неконфликтных файлах. Оно должно быть идентично staging `987787f`, включая schema и миграции. Сравнить также пакеты, lockfile, workflow и runtime deploy: новых изменений там не должно быть.

Для 22 документов, которыми main отличается от базы a899e8e, сохранить версии main, включая его уникальные release manifests и acceptance receipts. Единственная новая правка импортируемого CRM_IMPROVEMENTS_PLAN.md — заменить прежнее правило `codex/…` ссылкой на актуальный GitFlow из AGENTS.md. Не заменять незакоммиченную версию этого файла в D:/Projects/pero_crm_v2. AGENTS.md и новые документы этого change сохранить вместе с итоговой QA-документацией product-quantity. Список исходных файлов и их выбор зафиксировать в preview/evidence; не применять общий `ours`/`theirs` ко всему репозиторию.

Альтернатива с повторным cherry-pick отвергнута: она снова раздвоит историю. Перезапись main или staging другой веткой отвергнута: потеряет документы или историю.

### Merge ветки в staging, затем fast-forward выпуска

После локальных проверок закоммитить результат с коротким описанием, например `Согласовать ветки и закрепить GitFlow`. Влить рабочую ветку в staging обычным merge с сохранением родителей. Такой staging содержит историю main, поэтому после staging-приёмки main можно продвинуть через `git merge --ff-only origin/staging`.

Слияние staging в main выполняется только после прямого разрешения выпуска и конкретной production-миграции количества изделий. Весь принятый staging продвигается целиком. После push refs main и staging должны совпасть, а приложение production — подтвердить новую ревизию отдельно. При появлении новых remote коммитов переснять baseline и проверить изменившийся состав; принятый SHA не подменять.

## Risks / Trade-offs

- Потеря изменения при автослиянии → побайтная проверка полного приложения относительно принятого staging, а не только восьми конфликтов.
- Устаревшие статусы и потеря документов main → импорт фиксированного списка 22 документов main, сохранение свежих release receipts и отдельная правка старого правила веток.
- Текущий checkout содержит чужую незакоммиченную работу → интеграция в отдельном чистом worktree, только согласованные файлы.
- Main push запускает production-деплой и миграцию → до него отдельное разрешение `20261001120000_product_quantity`, проверки production, один временный дамп БД с проверкой восстановления и контроль фактического образа. Restic не использовать; local/staging дампы запрещены.
- Откат к коду без quantity после использования партий неверно рассчитает суммы → такой откат запрещён; использовать исправление вперёд либо отдельно проверенную quantity-совместимую ревизию. Архив БД не восстанавливать автоматически.

## Migration Plan

1. Зафиксировать свежие main/staging/feature refs, чистоту интеграционного worktree и прежние app tree hashes; оформить рабочую ветку согласованным номером.
2. Влить main и рабочую ветку product-quantity в административную ветку, применить явные правила разрешения выше, добавить AGENTS.md и planning/evidence. Новых миграций сверх product_quantity нет.
3. Проверить итоговый diff, точность app tree, git diff --check, OpenSpec strict, существующие app/bot/deploy тесты, typecheck/lint/build. Никаких новых тестовых БД или production-записей.
4. Влить ветку в staging; дождаться CI и штатного watcher под W07. Проверить точный image revision/health и основные экраны изделия, проекта и задач на 360/390/1440. Предыдущий полный live QA относится к идентичному приложению 987787f; новую проверку записать отдельно и не приписывать ей прежние операции.
5. После прямого разрешения выпуска и миграции выполнить предусмотренные production-проверки и временный дамп только перед этой миграцией, проверить его изолированное восстановление, выполнить fast-forward main до принятого staging, проверить CI, deployment и одинаковые remote refs. После подтверждения успешного выпуска и ненужности дампа удалить только этот временный файл по точному пути. Restic не трогать; дампы local/staging не делать. Не переписывать историю и не изменять DB/volumes вручную.
