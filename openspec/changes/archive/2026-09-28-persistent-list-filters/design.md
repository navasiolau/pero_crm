# Design

## Context

`useListParams` сейчас независимо меняет URL в каждом компоненте. Страницы читают только `projects.view`/`products.view`; два фильтр-бара содержат дублированный debounce. Таблица `UserPreference` имеет составной ключ `(userId, key)` и строковое значение, поэтому миграция не нужна.

## Goals / Non-Goals

**Goals:** единый набор параметров для UI и серверных запросов, сохранение в профиле, безопасный сброс и отмена устаревшей навигации.

**Non-Goals:** изменение видимости бизнес-данных, поддержка новых фильтров и изменение остальных списков CRM.

## Decisions

- `projects.list` и `products.list` содержат версионированную JSON-запись: случайная ревизия и нормализованный query. В отличие от localStorage это переживает повторный вход и не разделяется между сотрудниками одного браузера. Разрешённые поля и значения ограничены текущими фильтрами; `view=kanban` явно обозначает полностью пустой выбор.
- Сервер читает сохранение только текущего пользователя. Голый маршрут восстанавливается redirect на канонический URL; любой явный query, даже некорректный, не дополняется сохранёнными значениями. Прежний `*.view` применяется только при отсутствии новой записи.
- Один `ListParamsProvider` на раздел объединяет `get/set/pending/reset`; компоненты остаются с прежним API. Управляемая очередь сохраняет последний выбор до перехода и не выполняет устаревшую навигацию после ухода. Чтение страницы не пишет настройки, поэтому prefetch не меняет выбор.
- Server action получает только раздел, query и предыдущую версию, а владельца берёт из `auth()`. Атомарный compare-and-swap по существующей строке защищает от ответов, пришедших не по порядку. При конфликте актуальный клиент повторяет запись с новой версией; неактивная страница не повторяет.
- Поиск создаёт таймер только в обработчике ввода. Отдельная ревизия отмены меняется только при сбросе, внешнем переходе и размонтировании; обычные фильтры и подтверждение собственной навигации сохраняют черновик и объединяются с ним после задержки. Эффекты синхронизации URL не порождают записи.
- Поле поиска хранит исходный набираемый текст до сброса или внешнего перехода. Нормализованный собственный URL не заменяет его: завершающий пробел после паузы остаётся доступным для следующего слова.
- Выданные внутренние переходы учитываются с ревизией. Подтверждение нового перехода удаляет все более старые отметки; popstate снимает их целиком. Внешнее возвращение к ранее использованной ссылке поэтому снова применяется как явный URL.
- «Сбросить» возвращает все параметры, включая вид и размер страницы, к значениям по умолчанию. В сохранении остаётся запись пустого состояния, чтобы прежний `*.view` не восстановился вновь.

## Risks / Trade-offs

- Сеть или БД недоступна → сообщить об ошибке сохранения, не показывать успешное сохранение; выбор можно повторить.
- Сразу несколько быстрых действий → общий контроллер объединяет их, сериализует запросы и пропускает промежуточную навигацию.
- Смена пользователя → provider привязан к пользователю, размонтирование отменяет очередь; server action не принимает userId.
- Неоднозначность визуального эффекта при задержке → элементы отражают выбранные параметры и pending, строки меняются после завершения сохранения/перехода.

## Migration Plan

Без миграции схемы и изменения бизнес-данных. Сначала локальные unit/type/lint и браузерные сценарии на существующей локальной БД владельца (уточнение 28.09); затем review и staging на штатной самообновляющейся БД по процессу оркестратора. Начальное наличие/значения четырёх настроек выбранных двух пользователей фиксируются до тестов; восстановление допускается только compare-and-swap по доказанным собственным записям. Архивирование и main только после staging. Откат кода оставляет неиспользуемые `*.list` настройки; старые `*.view` не удаляются.
