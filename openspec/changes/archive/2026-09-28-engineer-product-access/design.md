# Design

## Context

В `products/queries`, `projects/queries`, файловых routes и omnisearch продублировано правило «любая OFFICE_ROLES видит всё». Server actions используют отдельные проверки; вложенные include и агрегаты не ограничены. См. `proposal.md`.

## Goals / Non-Goals

**Goals:** одна actor-aware политика для Prisma, проверка текущего состояния, отсутствие утечек во вложенных данных, сохранение объединения ролей.

**Non-Goals:** дашборд и навигация, схема оплаты, новые назначения, пересчёт истории или инфраструктурные изменения.

## Decisions

- Чистые функции строят Prisma where для Product, Project, Task, Work, File и Client. Actor содержит id/roles. Полная офисная роль возвращает свободный просмотр; ENGINEER и FIELD образуют OR, неизвестный/пустой набор запрещает доступ через `id in []` (пустой OR внутри AND Prisma может опустить).
- Пользовательские фильтры и идентификаторы объединяются с политикой через AND. Нельзя spread-объектом перезаписать engineerId, status, products или OR политики.
- Вложенные include, filtered counts, суммы, shortage и подсказки получают того же actor. Задачи/работы инженера требуют доступного изделия; общие файлы и коммуникации доступны через видимость проекта.
- Файлы учитывают как productId, так и taskId: оба контекста должны быть разрешены. Загрузка проверяет существование задачи и совпадение проекта/изделия до записи в хранилище. Скрытая зависимость блокирует действие общим сообщением.
- Серверные действия повторно проверяют доступ по актуальной БД. История зарплаты не фильтруется по текущему статусу изделия.
- Права объединяются отдельно по операциям: бухгалтерский просмотр не расширяет инженерную правку; инженер правит техблок только своего DESIGN, менеджмент — любого изделия. Сохраняется прежний производственный upload-доступ к проектам со своими задачами; если передан taskId, производственный grant требует собственного исполнителя. Прежние assignee/uploader-права сотрудников без ENGINEER сохраняются.
- Первоначальная цена и общие денежные поля проекта обнуляются в ответах ограниченному инженеру. UI не представляет частичную сумму как полную стоимость проекта; цены доступных изделий остаются.
- Уведомления ограниченного инженера проверяют текущую видимость entity-ссылки. Legacy `/my` и недоступные сущности маскируются при чтении, без перезаписи истории. Зарплатные и собственные account-события сохраняются.
- Регрессионный набор использует `node:test`/`tsx`, in-memory relational adapter и реальные экспорты server actions/routes с подменёнными auth/storage/audit boundaries. Это исключает сетевые подключения и запись в БД из unit/DI тестов. Первоначальные RED и SQL/HTTP GREEN записаны в evidence как исторические результаты до уточнения владельца.
- По уточнению владельца приёмка на реальных данных проводится на существующей локальной БД и затем staging; новые одноразовые БД больше не создаются. Runtime/DB-проверки координирует root с проверкой целевого окружения; production DB не используется, seed/reset/legacy migrations запрещены.

## Risks / Trade-offs

- [Вложенная связь обходит основной where] → явные фильтры include и adversarial fixtures для зависимостей/файлов/счётчиков.
- [Сортировка количеством раскрывает скрытые изделия] → для ограниченного просмотра сортировать по доступному количеству перед пагинацией.
- [Старая открытая форма] → проверять доступ на каждом серверном действии.
- [Staging ещё не проверен] → не архивировать change и не переносить в main до независимого review и локальной/staging приёмки.

## Migration Plan

Миграций БД нет. После локальных тестов root публикует отдельный feature-коммит в staging, подтверждает ревизию и изоляцию данных, выполняет runtime-проверки ролей. В main переносится только проверенная ревизия. Откат — возврат предыдущего образа без изменения данных.
