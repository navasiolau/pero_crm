# Design

## Context

См. proposal.md. CRM использует Tailwind 4, Base UI и dnd-kit. Пользовательские фильтры реализуются отдельным change; мобильный слой не меняет их URL и серверное сохранение. 3D-просмотрщик будет добавлен позже и должен использовать эти правила при собственной приёмке.

## Goals / Non-Goals

**Goals:** общие мобильные правила в UI-примитивах; реальная браузерная проверка CRM на существующей локальной базе владельца с сохранностью данных.

**Non-Goals:** изменение доменных действий, ролей, расчётов, истории или схемы БД.

## Decisions

- Мобильные CSS-переменные меняются в media query <768 px, rem корня не меняется: десктоп и размеры сетки сохраняются. Общие зоны нажатия задаются на data-slot компонентов, включая малые размеры.
- DataTable получает необязательный renderMobileCard; серверные сортировка/пагинация общие с таблицей. Выбор сортировки в мобильном режиме доступен отдельно.
- Мобильный breakpoint определяется `matchMedia.matches`, а не innerWidth, который mobile Chromium способен увеличить из-за переполнения. Проверки сравнивают реальный scrollWidth с заданным viewport; длинные URL в h1 и flex-ссылках переносятся с ограничением ширины, не скрываются.
- ResponsiveFilterPanel использует единственную копию дочерних полей: на телефоне Sheet, на десктопе прежний блок. Значения продолжают принадлежать URL/persistence hook.
- Диалог учитывает visualViewport при мобильной клавиатуре, ограничивает доступную высоту; формы прокручиваются, завершающие кнопки доступны внизу. Колонки мобильных форм становятся одноколоночными.
- Только ручка dnd имеет touch-action:none; сама карточка и её текст сохраняют прокрутку. Смена статуса нажатием использует существующие детали изделия/проекта и кнопки задачи.
- Playwright работает против явно заданного локального либо staging URL; сервер не запускается автоматически с потенциально рабочей .env. Автоматическое создание аккаунтов, seed/reset/schema push не входят в мобильные тесты. Доступные аккаунты и существующие сущности передаются явно через окружение; формы открываются и заполняются без сохранения бизнес-данных. Фото проверяется открытием выбора файла и наличием capture, без загрузки на существующую БД.

## Risks / Trade-offs

- Большой текст может вскрыть переполнение старых экранов → проверка длинных названий и минимальной ширины, исправление конкретных контейнеров.
- Эмуляция viewport не равна физическому телефону → отдельно фиксируем, что камера проверена наличием capture и взаимодействием файлового input, а реальная камера устройства не эмулируется.
- Параллельная ветка фильтров меняет те же filter-bar файлы → мобильные изменения ограничены оболочкой и JSX, persistence-логику сохраняем при интеграции.

## Migration Plan

Миграций нет. После локальных тестов на существующей локальной БД независимый review, затем exact-revision staging на её штатных данных. Выпуск и возможный откат UI-коммита координирует основной агент; production-БД не изменяется. Первоначальные проверки на одноразовой БД — только исторические диагностические результаты: после уточнения владельца runtime и тесты остановлены, они не заменяют требуемую локальную приёмку.
