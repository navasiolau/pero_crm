# Design

## Context

Auth.js использует Node middleware и проверяет актуального пользователя/версию сессии через `createSessionCallbacks` до `authorized`. Страница дашборда повторно вызывает `auth()` и пока разрешает все OFFICE_ROLES. Навигация использует те же OFFICE_ROLES; вход отправляет на `/`.

## Goals / Non-Goals

**Goals:** единая стартовая страница по текущим ролям, серверный запрет до запросов статистики, согласованное меню.

**Non-Goals:** изменение доступа инженеров к изделиям, переработка авторизации, миграции, изменение финансовых прав и инфраструктуры.

## Decisions

- Ввести чистую `homePathForRoles` в отдельном `lib/home-route.ts`, используя существующие ролевые наборы и приоритет. Функцию используют route callback, серверные страницы и логотип. Дублирование условий в каждой точке отвергнуто: иначе маршруты могут расходиться.
- Корневой route callback перенаправляет неуправленческие роли сразу; серверная страница независимо повторяет проверку до Prisma-запросов. Одного скрытия меню недостаточно для запрета прямых обращений.
- Успешный credentials-вход сохраняет `redirectTo: "/"`; последующий запрос уже проходит обычную проверку сессии и выбирает маршрут. Это избегает отдельного чтения роли до завершения входа. Активный `/login` и логотип используют стартовую страницу напрямую.
- Для ENGINEER + ACCOUNTANT стартовая страница `/products`: существующая лестница ставит инженера выше бухгалтера. Финансы остаются в объединённой навигации.
- Тесты выполняются существующим `node:test`/`tsx`; стандартная команда `tsx --test tests/*.test.ts`. Начальный RED проверяет реальный route callback и навигацию, а не отсутствие нового файла. Регрессии Auth.js запускаются вместе.

## Risks / Trade-offs

- Расхождение middleware и страницы → общий выбор маршрута плюс отдельная проверка обеих точек в локальной/staging приёмке.
- Возврат старых прав из JWT → не менять `auth.ts` и session callbacks; добавить тест перенаправления с актуальными ролями и отзывом сессии.
- Несовместимое изменение прав других разделов → не менять существующие ограничения finance/settings/changelog/payroll, проверять старые auth-тесты.

## Migration Plan

Изменение не содержит миграций и не изменяет данные. Оркестратор проводит независимое review, локальную приёмку и staging на точной ревизии с реальной копией данных. Архивирование change и продвижение в main выполняются только после staging. Откат — возврат предыдущего образа приложения; данные не затронуты.
