# Design

## Context

Мотивация и область изменения: [proposal.md](proposal.md). На этапе планирования исходники исследованы на `f5c0cdb1`, общем SHA main/staging после fetch 10.11.2026. Последующие фактические runtime-проверки приведены в verification.md.

- `apps/web/src/components/kanban-scroll-area.tsx` хранит только текущие DOM-позиции и синхронизирует доску с нижним scrollbar. Запоминания между размонтированиями нет.
- В глобальных досках колонкам не задана собственная вертикальная область прокрутки: горизонталь принадлежит `[data-slot="kanban-scroll"]`, вертикаль — странице. Сохранять отдельные вертикальные позиции колонок не требуется.
- `apps/web/src/lib/list-params.tsx` и серверные страницы восстанавливают канонические параметры через UserPreference и URL; это не включает прокрутку. Голый маршрут переадресует на канонический URL.
- `apps/web/src/hooks/use-kanban-search-focus.ts` при монтировании заново создаёт запрос центрирования непустого поиска. Возврат с восстановлением должен завершать этот запрос без повторного перемещения.
- `projects/kanban-board.tsx` открывает `/projects/<id>`, а карточка проекта возвращает на `/projects`. У изделий уже есть проверяемый `returnTo`, сохраняющий параметры глобального списка.
- В `globals.css` мобильная доска использует `scroll-snap-type: x proximity`. Существующий поиск временно отключает snap и возвращает его перед ручным жестом; восстановление должно использовать совместимый механизм.
- Имеются браузерные проверки поиска, карточек, синхронизации полосы и list-state. Они используют настоящие client components, но часть навигации подменена. Для новой задачи нужен также реальный переход App Router туда и обратно.

## Goals / Non-Goals

**Goals:** общий включаемый механизм для двух глобальных досок, независимый от серверного сохранения фильтров; отсутствие перерисовки дерева карточек на каждом scroll; явная координация восстановления, поиска и ручного управления.

**Non-Goals:** глобальная замена управления историей браузера, сохранение DTO карточек, изменение бизнес-действий, CSS-компоновки или функций остальных экземпляров `KanbanScrollArea`.

## Decisions

### 1. Временный снимок в пределах вкладки

Добавить небольшую типизированную утилиту хранения и hook восстановления. Использовать `sessionStorage` с версией формата и раздельными ключами пользователя/раздела; хранить только последний снимок каждого раздела. Снимок содержит канонический query, горизонтальную координату доски, вертикальную координату страницы, размеры viewport, ID последней открытой карточки и её смещение относительно видимой области. ID нужен только для сопоставления с уже разрешёнными сервером DOM-карточками.

ID пользователя передаётся из серверной сессии: у изделий он уже приходит в `ProductsView`, у проектов его нужно добавить в адаптер. Совпадение userId, section, query и вида обязательно. Отсутствие/запрет storage, неизвестная версия, невалидные числа или слишком большой снимок обрабатываются без исключения в UI. Для текущего жизненного цикла страницы допускается резервный снимок в памяти; он не даёт гарантий после полной перезагрузки. Вкладки не обмениваются обновлениями позиции.

Альтернативы: UserPreference потребовал бы серверных записей на прокрутку и переносил бы координаты между устройствами; localStorage связывал бы вкладки; React state страницы теряется при уходе. Поэтому используется временное хранилище вкладки.

### 2. Снимать позицию до перехода

Подключить опциональный контекст восстановления к `KanbanScrollArea`; остальные вызывающие компоненты сохраняют прежнее поведение. Пассивные обработчики доски/страницы обновляют refs с ограничением через requestAnimationFrame. Запись в storage не вызывает React-render.

Оба `onOpen` глобальных досок перед `router.push` синхронно фиксируют актуальные координаты и ID открываемой карточки. Один и тот же путь используется при клике по телу и обложке. Для ухода через меню, историю или pagehide сохраняется последний валидный снимок из refs; cleanup не перечитывает нулевые координаты уже заменённой страницы. События программного восстановления и начальное монтирование не перезаписывают сохранённые данные.

### 3. Восстанавливать после готовности с ограниченным ожиданием

Признаки готовности берутся из существующих пар `query/resolvedQuery` и source/rows в адаптерах досок; текущая выборка и DOM должны относиться к одному контексту. Ожидающее восстановление не выполняется при незавершённой навигации, открытой панели фильтров или DnD.

На возврате прочитать валидный снимок, дождаться измеримой доски, выполнить мгновенное восстановление обеих осей и синхронизировать нижнюю полосу. Координировать это с фактическим commit навигации App Router, а не с произвольным timeout. DOM/ResizeObserver и ограниченные RAF используются только для текущего запроса; завершение, отмена и предельный срок ожидания отключают все подписки. Не менять `history.scrollRestoration` глобально.

При неизменной геометрии использовать точные координаты. Если карточка сместилась, вычислить поправку из её сохранённого экранного смещения и текущего DOM-прямоугольника. При изменённом размере окна ограничить результат допустимыми диапазонами и видимой областью. Если актуальные строки уже подтверждают отсутствие ID, сразу использовать clamped-координаты без ожидания карточки. Пустая актуальная доска также завершает восстановление.

Ручное колесо/свайп/управление полосой или клавишами прокрутки отменяет ещё ожидающее восстановление. После завершения или отмены фоновые обновления и resize не запускают этот запрос заново. Для нового ухода записывается новое фактическое положение.

### 4. Один приоритет для поиска, восстановления и snap

На том же подтверждённом query восстановление имеет приоритет перед поисковым центрированием. Успешное восстановление или его отмена ручной прокруткой помечает первоначальный поисковый переход уже обработанным. Изменение/очистка query отменяет восстановление и возвращает обычную семантику нового поиска.

Общее управление временным отключением мобильного snap не позволяет двум hooks независимо возвращать конфликтующие стили. Snap восстанавливается перед следующим ручным жестом или при cleanup; дальнейшие touch, Shift+wheel и клавиатура работают штатно. Не использовать постоянное отключение snap и не центрировать карточку при обычном возврате с неизменными данными.

Это уточняет приоритет на возврате относительно changes `kanban-identity-search-focus` и `product-kanban-search-centering`: новое пользовательское действие поиска по-прежнему центрируется один раз, повторное монтирование оставленной доски — восстанавливает позицию. Основная `persistent-list-state` дополняется требованиями к viewport; серверные настройки не расширяются.

### 5. Проверяемый адрес возврата для проектов

Добавить построение ссылки проекта с исходным каноническим query доски и серверное разрешение `returnTo` только в `/projects` либо `/projects?<нормализованные параметры>`. Ограничения длины, управляющих символов, обратных слешей, fragment, массивов и посторонних путей взять по образцу `product-return-navigation.ts`. Фолбэк — действующий `/projects`; ACL проекта выполняется независимо.

Передавать проверенный href в существующую ссылку «К списку проектов». Это сохраняет нужную выборку при изменении общих UserPreference в другой вкладке. Существующий возврат изделия в глобальный список или изделия родительского проекта остаётся совместимым. Изменение ограничивается открытием с доски; остальные способы входа сохраняют фолбэк.

Альтернатива `router.back()` для всех ссылок не подходит: при прямой ссылке предыдущая страница может быть посторонней; обычная ссылка должна иметь определённое внутреннее назначение.

## Risks / Trade-offs

- Сброс вертикали со стороны навигации после раннего эффекта → проверить реальный App Router с browser Back/Forward и ссылками, применять восстановление после готовности маршрута.
- Короткая промежуточная доска обрезает координаты → не сохранять промежуточный clamp как окончательный снимок до подтверждения актуальных строк и layout.
- Mobile snap и отложенное событие нижней полосы могут сдвинуть позицию → общий контроль snap, проверка совпадения двух полос после завершения событий; допуск измерения два CSS-пикселя.
- Ручной жест во время ожидания → отмена текущего запроса, включая связанное повторное поисковое центрирование.
- Данные изменились за время просмотра → координаты и идентичное место карточки могут быть несовместимы; приоритет получает доступная карточка, исчезнувшая карточка даёт безопасный clamp.
- Браузер запретил sessionStorage → навигация продолжает работать; отсутствие восстановления фиксируется как graceful fallback, без ошибок интерфейса.

## Migration Plan

Миграции БД и дампы не нужны. После согласования — реализация в `bugfix/212`, локальные проверки и запись фактического результата в `verification.md`. Приёмка включает реальный local UI на разрешённой существующей БД 5433, без seed/reset и создания стенда: 1440×900, 390×844, 360×800, исходный/конечный скриншоты и координаты.

После прямого разрешения на коммит — обычное слияние в staging и приёмка фактического SHA/образа/сценариев. Main и production — только по отдельному прямому поручению, через принятый staging. Откат приложения не требует восстановления данных; неизвестная версия временного снимка игнорируется. Не выполнять инфраструктурные операции или команды restic.
