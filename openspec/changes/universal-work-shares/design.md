# Design

## Context

Task.quantity выделяет количество из Work, executorShare — старый коэффициент сдельной оплаты. Формула закрытия: priceSnapshot × quantity × executorShare; результаты округляет денежная колонка БД. Задачи без Work не начисляют деньги. Простое копирование количества переполнит Work, а уменьшение и количества, и процента применит долю дважды. См. proposal.md.

## Goals / Non-Goals

**Goals:** точное деление любой доступной задачи, сохранение оплаты и занятого объёма, безопасные повторы и одновременные операции, повторное использование математики распределения будущими фондами изделий.

**Non-Goals:** начисление новых процентных фондов, изменение payScheme, участники инженерии, авансы, 3D, изменения реальных данных или применение миграций.

## Decisions

- Additive `TaskAllocationGroup` хранит workId, исходное quantity (null без Work), budget Decimal(12,2), currency (null без Work), автора и дату. Task получает nullable allocationGroupId, shareUnits Int, shareAmount Decimal(12,2) и splitRevision Int default 0. Существующие строки не получают группы автоматически.
- 100% группы = 1 000 000 целых единиц доли. Ввод процента: 0,01–99,99 с двумя знаками. При передаче новые единицы и копейки вычисляются целочисленно вниз; остаток остаётся исходной задаче. Слишком малая доля, округляющаяся до нуля единиц, отклоняется. Повторное деление использует текущие units/amount, не исходный бюджет всей группы.
- У частей сохраняется исходное quantity общей работы; фактическая занятость Work считает каждую allocationGroup ровно один раз. UI явно показывает общий объём и долю, не суммирует общий объём каждой части. Для сдельного начисления группы используется shareAmount напрямую, без дополнительного executorShare. Старые задачи без группы сохраняют прежнюю формулу.
- Первая группа получает бюджет из существующей формулы, округлённой до копейки один раз; legacy executorShare не переписывается. Без Work quantity=null, budget=0, currency=null. Неоднозначная старая задача с Work и отсутствующим quantity не делится до явной правки менеджером.
- Все изменения задач/зависимостей и удаление Work используют общий короткий PostgreSQL advisory transaction lock домена задач. Это сериализует create/update/delete/status/split и предотвращает гонку копирования зависимостей; внешние уведомления/доставка событий выполняются после commit. Альтернатива с блокировкой отдельных задач потребовала бы упорядочивать весь граф межпроектных зависимостей и усложнила бы корректность без пользы для текущего размера CRM.
- Закрытие задачи переносится в ту же транзакцию: статус, таймер/факт и PayrollEntry. Повторное закрытие не создаёт второй PayrollEntry. Деление атомарно записывает исходную часть, новую задачу, группу, зависимости и ChangeLog.
- `splitRevision` увеличивается при делении и правке задачи; форма передаёт ожидаемую ревизию. UUID запроса используется в уникальном id ChangeLog деления как receipt: повтор с теми же актором/задачей/получателем/процентом/ревизией возвращает прежний childTaskId. Receipt проверяется только после актуального доступа к исходной задаче.
- Предшественники копируются в новую часть; каждый существующий dependent получает дополнительное ребро. При создании/редактировании зависимости выбранная доля разворачивается во все части группы. Менеджер может менять назначение, название, сроки и описание части; менять её Work/product/quantity или удалять отдельную часть нельзя. DONE и любые начисленные части неделимы.
- Исходный исполнитель, статус, фактическое время, таймер и файлы остаются; дочерняя задача NEW без факта и файлов. Оценка времени делится пропорционально в целых минутах с минимумом 1 минута на часть (для исходной оценки 1 новая оценка тоже 1); это прогноз, не объём/денежный бюджет.
- Список назначений включает все активные роли. Чистый инженер и ENGINEER+ACCOUNTANT по текущей политике получают только своё DESIGN; FIELD/менеджмент сохраняют свои независимые права. Деление не добавляет инженеру доступ к чужому изделию.
- Server actions берут actor из auth; split options и итог перепроверяются на сервере. TaskDetails содержит долю, снимок суммы/валюты, splitRevision и canSplit; общий мобильный диалог используется в TaskDialog и MyTasksView.
- На UI-границе остаток количества, прибавление собственного объёма при редактировании и кнопки ±1 считают целые сотые через общие helpers. «Все» передаёт точную decimal-строку, например 10,30−10,00=0,30. Настоящие дополнительные знаки (0,301) отклоняются, а не округляются; строгие серверные bounds не ослабляются.
- Extension point для отдельно согласованной фичи №6: менеджер распределяет единый процентный фонд изделия между работами весами суммарно 100%; сотрудник затем делит назначенную работу и её бюджет. Текущие группы умеют распределять точную сумму работы, но здесь источником остаётся обычный Work snapshot. Процентные pools, веса работ и их начисление в этой фиче не добавляются.

## Risks / Trade-offs

- [Округление и повторное деление] → целые units/копейки, остаток у исходной задачи, проверки суммы на каждом делении и числовые RED/GREEN.
- [Legacy код не знает групп] → после первого реального деления откат на старый код, рассчитывающий полную цену каждой части, небезопасен; root должен остановить новые деления/начисления и использовать совместимую версию. Миграция без данных сама по себе обратимо совместима со старым кодом.
- [Глобальная блокировка домена] → транзакции не содержат сетевых вызовов/доставки плагинов, timeout ограничен; нагрузка текущей CRM мала. Нативную конкурентность PostgreSQL проверить только после разрешения миграции.
- [Новая схема ещё не применена] → нельзя запускать приложение на существующей БД с новым Prisma Client до отдельного разрешения. Генерация клиента идёт только в независимом node_modules этого worktree.

## Migration Plan

Подготовить только additive SQL (новая таблица, nullable поля/FK/index, revision default 0) без backfill начислений/групп. Все DDL включены в один BEGIN/COMMIT для полного rollback при ошибке. Не выполнять SQL/migrate/db push на любой БД этим субагентом. На этом этапе — unit/DI, статическая проверка миграции, typecheck/lint/build. Root отдельно принимает design и выполняет разрешённую миграцию и local/staging QA; пользователь разрешил там ограниченный набор: один помеченный проект, одна работа, до четырёх задач и два QA-сотрудника PIECE с точным cleanup и проверкой сохранности. Production не входит. Один итоговый feature-коммит включает OpenSpec, код и тесты после приёмки.
