# Spec Delta

## Purpose
Расширить полевое создание работ и назначение задач с WORKER на MOUNTER с кросс-ролевыми назначениями WORKER↔MOUNTER внутри живого изделия в производстве, сохранив все прежние ограничения оплаты, остатков и идемпотентности.

## ADDED Requirements

### Requirement: Полевое создание работы монтажником
Система SHALL разрешать активному MOUNTER создавать работу на тех же условиях, что активному WORKER: только живое изделие в статусе PRODUCTION, обязательный productId этого проекта/изделия, только существующий активный PriceItem, серверный снимок цены/единицы/количества. Создание и правка PriceItem остаются менеджерскими. При пустом списке расценок полевой пользователь SHALL видеть подсказку «обратитесь к менеджеру», кнопка добавления остаётся недоступной без выбранной расценки.
#### Scenario: Монтажник создал работу в производстве
- **WHEN** активный MOUNTER добавляет работу в живое изделие PRODUCTION по действующей расценке
- **THEN** работа создаётся с серверным снимком цены и атомарной записью аудита, как у WORKER
#### Scenario: Пустой прайс
- **WHEN** список активных расценок пуст
- **THEN** полевой пользователь видит подсказку «обратитесь к менеджеру» и не может добавить работу
#### Scenario: Изделие не в производстве
- **WHEN** статус изделия DESIGN (или иной, кроме PRODUCTION)
- **THEN** создание работы полевой ролью отклоняется; кнопки «Работа»/«Назначить задачу» не показываются

### Requirement: Кросс-ролевое назначение задач
Система SHALL разрешать актору с активной ролью WORKER|MOUNTER назначать свободное количество обычной работы (paymentKind LEGACY, stagePayPoolId NULL, priceSnapshot задан) того же проекта/изделия получателю с активной ролью WORKER|MOUNTER, включая назначения WORKER→MOUNTER, MOUNTER→WORKER, MOUNTER→MOUNTER и самоназначение. Проверки остатка через allocatedWorkQuantity (группы — один раз), запрет при NULL-количестве старой задачи, обязательная оценка времени, атомарные task/audit/event/receipt и идемпотентность по clientMutationId с fingerprint SHALL сохраняться без изменений.
#### Scenario: Монтажник раздал работы двум сотрудникам
- **WHEN** MOUNTER распределяет свободное количество работы пятью назначениями двум активным исполнителям (WORKER и MOUNTER)
- **THEN** создаются пять задач с корректными количествами и получателями; шестое назначение сверх остатка отклоняется с конфликтом
#### Scenario: Повтор с тем же clientMutationId
- **WHEN** запрос повторяется с прежним UUID и неизменным содержимым
- **THEN** вторая задача не создаётся, возвращается прежний результат с признаком repeated
#### Scenario: Неактивный или чужеролевой получатель
- **WHEN** получатель неактивен либо не имеет ролей WORKER|MOUNTER
- **THEN** назначение отклоняется без создания задач, аудита и событий

### Requirement: Неизменные границы
Классические createTask/updateTask/deleteTask SHALL оставаться только менеджерскими; начисление обычной сдельщины LEGACY PIECE при DONE (включая исполнителей-MOUNTER с payScheme PIECE) SHALL работать как раньше без изменений completion-core.ts; боковое меню SHALL NOT открываться для полевых ролей (nav.ts и redirect в tasks/page.tsx неизменны).
#### Scenario: Дизайн без кнопок и закрытый сайдбар
- **WHEN** изделие в DESIGN либо роль не имеет офисного доступа
- **THEN** полевые кнопки отсутствуют; в боковом меню нет пунктов «Работы»/«Задачи» для MOUNTER; tasks/page.tsx перенаправляет неофисные роли
#### Scenario: DONE начисляет PIECE
- **WHEN** задача обычной LEGACY-работы переходит в DONE у исполнителя со сдельщиной
- **THEN** начисление считается по снимку цены работы, как до изменения
