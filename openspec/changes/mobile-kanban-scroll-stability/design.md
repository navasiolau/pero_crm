# Design

## Context

Обе глобальные доски используют `KanbanScrollArea`: основной нативный scroll-контейнер и нижняя полоса отражают `scrollLeft` друг в друга. На телефоне CSS включает `scroll-snap-type:x proximity`. Запись позиции нижней полосы порождает отложенное событие, которое сейчас может перезаписать более свежую позицию основного контейнера во время нативного движения.

В Chromium CDP touch на настоящем общем компоненте и CSS воспроизведены обратные записи до15 CSS px и пять обратных отклонений при одном наборе свайпов. Сильное визуальное дрожание пользователя на его физическом устройстве не воспроизведено; исправляется подтверждённая обратная связь. DnD уже ограничен отдельной `touch-none` ручкой; менять sensors не требуется. Доска задач не использует общий контейнер.

## Goals / Non-Goals

**Goals:** различать программное отражение и новое движение пользователя; сохранить нативную прокрутку, snap и поведение задачи №212.

**Non-Goals:** изменение CSS snap, DnD-бизнес-действий, серверных данных, мобильного меню или архитектуры хранения позиции.

## Decisions

### Пометка отражённой координаты

Узкая общая утилита хранит последнюю программно отражённую координату каждого target в WeakMap. Событие target на этой же координате является эхом и не отражается обратно. Если координата отличается, это новое движение и оно синхронизируется обычным путём. После записи запоминается фактический `scrollLeft` target: браузер может округлить или ограничить requested value.

Тем же путём помечаются записи из измерения размеров и восстановления №212. Сами правила восстановления, поиска, приоритетов жеста и ожидания DOM не меняются. Альтернатива таймеру, отключающему обратную связь на произвольное время, не нужна: она теряет быстрое ручное управление второй полосой. Постоянно отключать snap или скрывать нижнюю полосу также не требуется.

### Проверяемый браузерный сценарий

Regression запускает настоящие touch-события Chromium CDP на общем компоненте с настоящим Tailwind CSS. Инструментирование `scrollLeft` считает обратные программные записи в доску во время обычного свайпа; такие записи запрещены, а движение и совпадение итоговых координат обязательны. Отдельно проверяются нижняя полоса, клавиатура и Shift+wheel. Старые browser-сценарии поиска/возврата выполняются без переименования их evidence в физическую проверку телефона.

## Risks / Trade-offs

- Округление координат → запоминать фактическое readback после записи с прежним допуском0,5 CSS px.
- Несколько отложенных событий → каждый handler читает актуальную позицию, хранится последнее отражение target, новое пользовательское движение отличается от пометки.
- Прямые записи восстановления → использовать общий путь отражения без изменения алгоритма №212.
- Эмуляция не доказывает поведение iOS/Safari или физического телефона → указать точные браузер/размер/ограничения в evidence; root отдельно принимает действующий staging.

## Migration Plan

БД и миграции не затрагиваются. После local RED→GREEN и review root выполняет обычный merge/CI/staging и проверяет точный SHA/образ/сценарии. Main и production в задачу не входят.
