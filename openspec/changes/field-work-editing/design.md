# Design

**Execution agreement:** Номер задачи 120, ветка feature/120 согласованы владельцем 10.10.2026; OpenSpec и реализация одобрены. Одна целевая локальная проверка, затем существующий полный CI без изменений и развёртывание на staging только через него; одна целевая staging-приёмка. Повторные полные ручные проверки не выполнять без конкретного сбоя. Production/main этим запуском не разрешены.

## Context

Мотивация — `proposal.md`, доступ к изделиям — `field-product-status-visibility`. База `origin/staging` `ab1c77f3b82cab788f206914d5b2a063e6aafe68`: `addWorkCore` использует текущий активный PriceItem, блокирует Product/PriceItem и сохраняет нормы, единицу/цену/total. Actions содержат добавление и удаление, но не update. Worker allocation core/queries также жёстко требуют PRODUCTION; исполнитель по умолчанию — текущий пользователь.

## Goals / Non-Goals

**Goals:** самостоятельные обычные работы и собственные задачи в разрешённом производственном контексте, без ручных тарифов и повреждения распределённого объёма.

**Non-Goals:** создание позиций прайса обычной производственной ролью, свободные работы вне каталога, изменение процентных фондов, ставок оплаты или уже начисленной зарплаты; новое право удаления работ не вводится.

## Decisions

1. **Один доменный Work writer.** Создание и новый update проверяют актуального actor и изделие по общей матрице вместо жёсткого PRODUCTION. Поля: действующая позиция прайса при создании, количество/норма; ручные title/unit/priceSnapshot/total запрещены строгим контрактом. UI и сервер получают общий operation grant. Уже существующее manager управление сохраняется.

2. **Снимок расценки остаётся серверным.** При создании и смене позиции у ещё не распределённой работы берутся название/единица/цена активного прайса. Смену позиции можно выполнять только до связанных задач, времени и начислений. После назначения задач редактируется только плановый объём с прежним price/unit snapshot; изменение каталога не переоценивает существующие работы.

3. **Нормы и задачи согласуются атомарно.** Под общим порядком Product→Work→Task locks норма пересчитывается в объём партии, total — по сохранённой цене. Новый объём не ниже уже распределённого, включая завершённые задачи и исторические группы. Неизвестный старый объём/цена даёт понятный отказ, а не нулевую стоимость. Цена/количество существующих задач, их выплаты и процентные completion snapshots не переписываются.

4. **Редактируются обычные работы.** Строки ENGINEERING/INSTALLATION и прочие процентные/замороженные фонды не становятся обычным Work через новую кнопку. Для них сохраняется текущий специальный процесс. Обычный LEGACY не означает изменение старых начисленных фактов; валидные прежние снимки используются как сохранённые данные.

5. **Получение своей задачи использует существующее распределение.** У любого WORKER/MOUNTER в доступном изделии есть «Взять себе»/создание собственной задачи из свободного количества работы. Actor для собственного назначения берётся с сервера; role WORK_COORDINATOR не требуется. Сохраняются обязательные срок/тип/оценка времени, receipt/replay, остаток и автоматический таймер. Существующее разрешённое назначение другому сотруднику не расширяется; получатель должен иметь допустимый рабочий контекст.

6. **UI переиспользует одну форму.** «Добавить работу»/«Редактировать» доступны по операции и статусу; после правки обновляются Work, свободное количество и собственные задачи. PriceItem selector и QuantityStepper остаются общими. Действующие персональные денежные DTO не раскрывают оплату коллег.

## Risks / Trade-offs

- Два сотрудника одновременно правят объём и забирают задачи → единые row locks, optimistic revision/receipt и native конкурентные проверки.
- Правка уже распределённой цены → запрет смены позиции после связи с задачами, неизменяемые task/payroll snapshots.
- Старый клиент посылает ручной тариф или другую product связь → strict payload, актуальные FK/role/status проверки до записи.

## Migration Plan

Используются текущие денежные/quantity поля; миграция исторических Work/Task не требуется. После принятой матрицы — отдельная feature с согласованным номером, meaningful RED→GREEN и native проверки на БД 5433 без dump/seed/reset. Принять на фактическом staging WORKER(PRODUCTION/STORAGE), MOUNTER(INSTALLATION) и совмещённую роль, включая правку объёма и свою задачу. Существующие выплаты/начисления должны совпасть до и после QA; production отдельно.
