# Design

## Context

№106 добавил длительность, №107 — единый summarizeCalendarEntries/PlanHoursSummary. Личный доступ уже централизован через resolveCalendarActor и ownerId в calendar core. См. proposal.md.

## Goals / Non-Goals

**Goals:** диапазон и детализация без параллельной формулы часов/прав.
**Non-Goals:** отчёт по сотрудникам, фактические трудозатраты, право администратору читать чужой план, новые мутации/уведомления.

## Decisions

1. Из существующего listCalendarMonthCore выделяется общий interval reader, который в одной транзакции перечитывает actor и выбирает ownerId+startsAt. Month и новый date range используют его. Диапазон — calendarDateRange из105: обе даты включительно MSK.
2. Строгий контракт from/to принадлежит server/calendar. Analytics core получает только actorId из сессии, читает общий диапазон и вызывает summarizeCalendarEntries. ownerId из входа запрещён. Completion date/updatedAt не участвуют.
3. GET /plan/analytics с URL датами, по умолчанию текущий месяц до сегодня. Кнопка в календаре открывает выбранный месяц. Общий PlanHoursSummary + дневная таблица и список записей с поиском/сортировкой/статусами и переходом к дню. Дневные полосы визуализируют указанные минуты; числовая подпись остаётся доступной.
4. Итоги строятся по полному выбранному набору, таблицы листаются на клиенте без скрытого ограничения количества строк. Минимальные DTO — личные CalendarEntryView. Статусные названия выносятся в общий справочник вместо дублирования.
5. Пропуски/отменённые/нулевые часы наследуют107. Даже при позднем выполнении запись считается по дате в плане. Часы нигде не называются фактическими.

## Risks / Trade-offs

- Большой диапазон → дневная/списочная пагинация; сервер не обрезает общие итоги.
- Неполная длительность → общий компонент107 явно показывает сумму известных и пропуски.
- Подделка владельца или отозванный доступ → строгий контракт и свежий actor до чтения данных.
