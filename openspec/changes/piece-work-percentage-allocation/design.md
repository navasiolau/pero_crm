# Design

## Context

`share-core.ts` сохраняет только replay старых `task-split` receipts. `remove-task-payment-shares` ранее запретил новые распределения; №191 является согласованным узким исключением исключительно для обычных работ. `work-shares.ts` уже умеет точные копейки, передачу текущей доли и учёт объёма группы один раз. `TaskAllocationGroup` и `shareAmount` сохраняют бюджет, а completion использует его при начислении PIECE.

## Goals / Non-Goals

**Goals:** Новые версионированные команды создания N долей и передачи текущей доли, сохранность всех соседних задач и истории, общий transaction lock, UUID/fingerprint, проверка актуальных ролей и PIECE внутри транзакции.

**Non-Goals:** Фонды ENGINEERING/ASSEMBLY/INSTALLATION, `stagePayPoolId`, `poolWeightUnits`, конверсии/settlement, смена финансовых долей изделия, изменение старого закрытого API и схемы БД. Переназначение целой задачи относится к №192.

## Decisions

- Использовать существующие `TaskAllocationGroup` и миллион целых единиц. При начальном распределении каждый участник получает общий quantity; `allocatedWorkQuantity` считает его один раз. Новая параллельная сущность назначений не нужна.
- Сумму рассчитывать существующим `taskPieceAmount`, затем целыми копейками: пол каждого произведения, остаток последнему. Проценты ограничены существующей точностью 0,01. Бюджет/валюта/quantity группы не меняются при передаче. Смена цены не влияет на `shareAmount`.
- Передача сохраняет исходную задачу и создаёт дочернюю. Уже существующая группа проверяется по ВСЕМ её задачам, включая DONE/начисленные; сумма единиц ровно миллион, сумма копеек равна budget, контекст/quantity согласованы.
- Внутри общего `withTaskTransaction` загружать свежего active actor, доступное изделие, работу без специальных связей, source/recipients. Полномочия управляющих дополняют видимость, WORKER/MOUNTER ограничены собственным source. Получатель должен иметь PIECE и роль, подходящую к изделию.
- Новые receipts имеют отдельный namespace `piecework-v1`, UUID и SHA256 канонического входа, actor и результат. Неудача после неизвестного ACK допускает повтор прежнего payload; UI фиксирует поля и UUID до разрешения исхода. `splitRevision` исходной задачи проверяется и увеличивается. Общий advisory lock предотвращает переполнение свободного объёма и гонки с завершением.
- Начальная форма отправляет ревизию `workPlanRevision` вместе со снимком расценки в едином hash: существующий общий hash плана не включает денежный снимок. Сервер проверяет эту ревизию после receipt replay под lock до создания группы; смена плана, назначенного объёма или расценки требует нового предпросмотра.
- Backend/actions/queries и диалог создаются отдельно. Подключение карточек задач/работ выполняется после слияния №190 оркестратором. Оценки/таймеры не добавляются; `estimateMinutes=null` для новых задач, старое значение source сохраняется как история.

## Risks / Trade-offs

- Исторически противоречивая группа → отказ без исправления существующих данных.
- Несколько участников и копейки → последний участник получает целый остаток; preview использует ту же арифметику.
- Неизвестный результат транзакции → UI предлагает повтор с тем же UUID; события/уведомления только после подтверждения.
- Нативная и визуальная приёмка требует разрешённых сценариев → результаты unit/DI не обозначаются как runtime-приёмка.

## Migration Plan

Миграция не требуется. Локальные code/DI проверки, браузерная приёмка разрешённого сценария, затем обычная интеграция staging по отдельной координации оркестратора. Рабочие БД и инфраструктуру данный этап не изменяет.
