# Design
## Context
Административная форма уже управляет User; shell строится из серверной сессии. JWT проверяет актуальные роли, но calendar grant в нём хранить нельзя.
## Goals / Non-Goals
Goals: единый effective-флаг, независимый от ролевого приоритета, live actor guard и понятное наследование.
Non-Goals: записи, уведомления и Telegram задач64–66; расширение других прав.
## Decisions
Nullable User.calendarEnabled выбран вместо UserPreference: это административная настройка доступа. NULL наследует наличие PROCUREMENT среди любых ролей; boolean всегда имеет приоритет. Серверный helper получает только actor из auth и повторно читает active/roles/override. Shell получает актуальный effective boolean из БД; nav вставляет План после dashboard или первым. Форма имеет наследование/включён/выключен, обновление без поля сохраняет ранее заданный override.
## Risks / Trade-offs
Открытый sidebar может оставаться видимым до обновления → каждый серверный вход повторно проверяет flag. Напоминания ещё отсутствуют → будущая доставка обязана использовать тот же effective guard без удаления записей.
## Migration Plan
Аддитивная nullable колонка без backfill; существующие пользователи получают NULL. Координатор применяет миграцию и native rollback-check; разработчик не пишет БД. Откат приложения возможен при сохранении колонки; удалять значения override автоматически нельзя.
