# Design

## Context

Material.unit сейчас хранит строку; номенклатура выбирает фиксированный MATERIAL_UNITS. Складские/финансовые DTO используют строковые unit и materialUnit. Складская номенклатура меняется через withWarehouseWrite и сохраняет существующие ролевые наборы. План задачи 110 уже согласован владельцем.

## Goals / Non-Goals

**Goals:** поддержать каталог с FK-защитой и ADMIN-настройкой, сохранить обозначения и количественные/денежные факты.

**Non-Goals:** изменение PriceItem.unit, пересчёт единиц и количества, изменения production или работа с restic.

## Decisions

- MaterialUnit содержит id, уникальное name и createdAt/updatedAt. Material получает unitId и relation measurementUnit; строковый столбец unit после backfill удаляется. Отдельная relation исключает дублированное обозначение, которое могло бы устаревать после переименования.
- Стандартным единицам миграция выдаёт фиксированные идентификаторы; нестандартным — детерминированные идентификаторы от исходной строки. «шт» сохраняет прежний внутренний default через стабильный unitId. Экранный селектор всегда отправляет выбранный id и работает даже после удаления неиспользуемого прежнего default.
- FK ON DELETE RESTRICT защищает все Material, без фильтра active. Предварительная проверка даёт понятное сообщение, FK защищает гонку назначения с удалением. В server actions и core строго ADMIN; текущий пользователь повторно проверяется внутри транзакции. Аудит catalog CRUD пишется в той же транзакции.
- На чтении справочник присоединяется в складских/финансовых запросах; DTO сохраняют unit:string. Номенклатура передаёт unitId, сервер валидирует наличие единицы внутри складской транзакции. Назначение иной единицы не меняет purchasePrice, warehouse balances, движения или ProjectMaterial.
- /settings/warehouse-units разрешён только ADMIN также в общей settings access policy; вход в прямой URL не обходит серверный guard. Селектор номенклатуры использует SearchableSelect и значения справочника.

## Risks / Trade-offs

- Удаление строкового столбца требует обновления всех его чтений → typecheck после генерации Prisma и регрессии складских/финансовых DTO.
- Гонки удаления и назначения → обязательный внешний ключ и перевод constraint error в понятную ошибку.
- Исторические нестандартные значения содержат пробелы или иные варианты → миграция сохраняет исходную строку без нормализации.

## Migration Plan

Миграция создаёт каталог, наполняет стандартами и DISTINCT Material.unit, заполняет unitId, добавляет NOT NULL, index/FK и удаляет прежний unit. Native harness проверяет миграцию, реальные FK/unique constraints, числовые инварианты и rollback в транзакции существующего local PostgreSQL 5433 под guard контейнера, без дампа и создания окружения; запуск согласуется с оркестратором. Local/staging миграции не запускаются этим субагентом. Для production применяется установленный процесс с отдельно разрешённой миграцией и одним временным дампом; откат схемы требует согласованного forward fix или восстановительного решения, а не автоматического reset.
