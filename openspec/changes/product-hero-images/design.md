# Design

## Context

См. `proposal.md`. `getProductFor` уже выбирает `sketchFile` через `fileVisibilityWhere`; список изделий и вложенные изделия проекта пока не передают его. На странице изделия `ProductSketch` показывает ограниченный preview отдельно от описания. Каждая из двух kanban-досок содержит собственные карточку и DragOverlay, поэтому image display сейчас отсутствует и реализации могут разойтись.

## Goals / Non-Goals

**Goals:**
- Добавить к двум list DTO и карточке изделия минимальные безопасные поля `id`, `fileName`, `mimeType`, `hasThumb`.
- Использовать одну визуальную карточку на обеих досках и в их DragOverlay.
- Сохранить защищённые `/api/files/<id>` и `/api/files/<id>?thumb=1`, существующий FileViewer и права на цену, открытие и перетаскивание.

**Non-Goals:**
- Не менять схему, загрузку, storage/S3, ролевые правила, содержимое или существование файлов.
- Не добавлять импорт, viewer 3D/B3D, обрезку изображений, новые изображения или fixture rows.

## Decisions

1. **Общая presentation-карточка для досок.** Оставить DnD и status callbacks в существующих экранах, но передавать их одинаковые card data в один новый компонент, которым пользуются и обычное представление, и оба DragOverlay. Это сохраняет досочные действия отдельно, устраняя расхождения в разметке карточек.
2. **Высота kanban-card задаётся по информационному блоку.** Измерять фактическую высоту нижнего content через `ResizeObserver`; блок изображения получает удвоенную высоту, а общая высота становится суммой этих блоков. Image stage содержит абсолютное изображение с `object-contain`, поэтому у него нет влияния на intrinsic height. Обычный `grid-template-rows: 2fr 1fr` без заданной высоты не гарантирует требуемое отношение и потому не выбран.
3. **Единый preview source с защищённым fallback.** Если `hasThumb` true, kanban запрашивает thumbnail по защищённому API route; иначе оригинал по тому же route. Ошибка загрузки переключает содержимое image stage на текстовую заглушку. Preview использует `object-contain`; клик на детали по-прежнему открывает оригинал через FileViewer, а не миниатюру.
4. **Адаптивный блок detail без изменения FileViewer.** Объединить в одном responsive grid описание и эскиз: при ширине от 1024 px — равные desktop-колонки, описание слева; ниже — порядок изображение, затем описание. Если один элемент отсутствует, оставшийся использует всю ширину. У preview не будет прежнего контейнера 128×96.
5. **Малые file projections на сервере.** Для `getProductFor`, списка изделий и вложенных изделий `getProjectFor` выбрать только `id`, `fileName`, `mimeType`, `hasThumb` через relation filter `fileVisibilityWhere(actor)`. Полный File record в client DTO не передавать; не обращаться к sketch relation без существующего ACL-фильтра.

## Risks / Trade-offs

- [Смена текста может менять пропорции карточки] → наблюдать нижний блок по фактической высоте и применять одно измерение к image stage; тестировать длинное название и метки.
- [Поздний ответ изображения содержит ошибку] → заменить `<img>` нейтральной заглушкой, не менять сведения или доступ к карточке.
- [Один запрос отфильтровал эскиз иначе, чем другой] → общий минимальный DTO, одинаковый `fileVisibilityWhere(actor)` во всех трёх projections и тесты запросов/visibility.
- [Изображение загружено, но браузер не может декодировать файл] → `onError` переводит компонент в явное состояние ошибки; повторный файл ID сбрасывает ошибку.

## Migration Plan

Миграции и перекладка storage не нужны. Изменения UI и query projections поставляются вместе; прежние данные и API доступа к файлам остаются совместимыми. Проверить RED→GREEN helper/component/query tests, затем выполнить root CUA review на 360×800, 390×844 и 1440×900 с существующими sketch images. Не создавать изображения, тестовые записи, менять роли/статусы/ставки/доли или запускать browser/native QA из этой задачи. Если релиз откатывается, вернуть UI и selections к прежним значениям; никакого восстановления БД или файлов не требуется.
