# Design

## Context

См. proposal.md. Схема №180 хранит текущий договор, источники, версии, артефакты и задания. №184 переносит неизменённые ContractModel/генератор, №185 предоставляет замороженные источники, аренду и выпуск PDF. Эти задачи разрабатываются в отдельных ветках; прямого копирования их реализации в №186 нет.

## Goals / Non-Goals

**Goals:** реализованные typed ports, координатор и PostgreSQL-store, которые после обычных merge подключаются к существующим lifecycle/template примитивам.

**Non-Goals:** публичные маршруты, самостоятельный запуск workers, миграция/запись БД/S3 во время разработки, изменение DOCX/шаблонов/денежных формул и запись клиента из договора.

## Decisions

- CP.clientId определяет заказчика. SHA-256 baseline охватывает текущие выбранные связи и данные клиентов всех источников и адреса проектов. Он проверяется при сохранении/подготовке/публикации; существующее отличие Project.clientId от CP.clientId допустимо и фиксируется.
- Настройки хранят собственную служебную обёртку с value и ручными исправлениями autofill-полей, привязанными к клиенту. Импортированные исходные settings читаются обратно совместимо. Доступные свежие CRM-поля заполняют defaults, явные ручные значения имеют приоритет; неизвестные CRM банковские/юридические поля остаются ручными.
- Нормализация, валидация и расчёты договора делегируются исходной ContractModel. Модуль не содержит альтернативных формул платежей или скидки.
- GET не создаёт договор. Save draft создаёт/обновляет его и источники с CAS и receipt ChangeLog, не изменяя этапы. Подготовка CONTRACT job использует только сохранённые настройки и ожидаемые ревизии.
- Общий порядок блокировок: проекты по ID, затем договор. Payload совместим с №185: schema/actor/requestFingerprint/frozenSources/extra. Длительный рендер, PDF→PNG, DOCX и приватная загрузка выполняются вне БД. Финализация повторно блокирует проекты и договор, проверяет текущее состояние и публикует всё в одной транзакции.
- Каждый новый PDF принадлежит своему КП; DOCX — договору. Для locked-источников используется принятый READY PDF. Снимки ContractVersion самостоятельны и не имеют зависимости от очищаемых ProposalVersion.
- После commit отдельные outbox events передаются существующему диспетчеру; их записи транзакционны. Ошибка диспетчера не отменяет уже подтверждённый выпуск.

## Risks / Trade-offs

- Клиент изменился во время долгого рендера → baseline и повторное чтение под блокировкой перед публикацией.
- Частично опубликованы несколько проектов → одна общая финальная транзакция и исключение при любой ошибке примитива этапа.
- Шаблонные зависимости пока вне ветки → обязательные порты без заглушек поведения; composition и native/visual приёмка после обычных merge фиксируются отдельными незавершёнными задачами.
- Исходный renderer удаляет неизвестные поля строк услуг → №184 сохраняет crmKind при хранении; печать использует прежние подписи/арифметику.

## Migration Plan

Новых моделей не требуется. Существующая local5433 и реальные хранилища этим субагентом не изменяются. Подготовленный native-helper запускается только оркестратором внутри guarded rollback после интеграции №180–185. Staging и production принимаются по AGENTS.md с фактическими SHA/образом и документами.
