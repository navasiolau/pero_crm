# Design

## Context

См. proposal.md. Основные writers уже сохраняют ChangeLog внутри транзакции. Квитанции выплаты, платежа, процентной настройки и логистики проверяют исходные поля и fingerprint; их формат нельзя менять. Создание кассы, складские категории/редактирование номенклатуры, расценки и валюта зарплаты имеют вынесенные записи аудита.

## Goals / Non-Goals

**Goals:** Полные снимки, точная принадлежность событий и атомарность аудита без изменения денежных результатов. Документированное покрытие живых путей web/API/Telegram.

**Non-Goals:** Пересчёт финансов, расширение ролей, изменение квитанций, внедрение в production, журналирование чтения и личного плана.

## Decisions

- Общий writer №221 принимает исходную запись и отдельные hints. Используем before/after для полного бизнес-снимка, не расширяем старые oldValue/newValue. Это сохраняет проверки повторов и позволяет сравнивать реальные поля вместо fingerprint/result.
- Метки и контексты формируются из данных, уже прочитанных внутри защищённой транзакции. Событие изделия получает только product context; проект — прямые project contexts. Рейсы имеют набор прямых связанных проектов, а строки отгрузки позволяют включить затронутые изделия.
- Общие справочники остаются глобальными. Загрузка ещё не прикреплённого финансового документа глобальна; привязка документа отражается полным событием платежа.
- Автоматические начисления/составные платежи имеют executor «Система» и инициатора. Исходный actor остаётся неизменным. Ручная настройка ставки остаётся пользовательским действием.
- Вынесенные аудит-записи переносим в ту же существующую transaction boundary. Снимок before читается там же; внешние уведомления и инвалидация остаются после commit.
- Для удаления складского движения сохраняем отдельные события каждого затронутого движения/платежа с контекстом и полным снимком до пометки удаления.
- Читаемое представление долей использует подтверждённые шкалы: `percentBps / 100` только для logisticsTrip/logisticsPosting/logisticsDocument; `shareUnits / 10000` только для product/payrollEntry/task/taskAllocationGroup/work. Источники — `logistics/allocation.ts`, `PERCENTAGE_SHARE_UNITS` и `FULL_SHARE_UNITS`. Деление строковое без округления; неизвестные домены/поля и невалидные значения не переинтерпретируются. Raw значения и денежная арифметика сохраняются.

## Risks / Trade-offs

- [Квитанции используются повторно] → regression tests сравнивают их исходные поля и повторный результат, без новых событий.
- [Неизвестная историческая связь] → не выдумывать контекст; задача №222 обрабатывает старые строки отдельно.
- [Дополнительные чтения замедляют транзакцию] → переиспользовать загруженные данные, добавлять только необходимые selected fields и пакетные чтения.
- [Моки скрывают ошибку SQL] → root выполняет guarded local/staging проверку на существующей БД; локальные unit/DI не объявляются DB/runtime приёмкой.

## Migration Plan

Изменение зависит от миграции №221 и не добавляет свою. После local-проверок root обычным merge интегрирует задачу в staging, принимает штатный CI и развёрнутый runtime. Исторические raw строки и денежные таблицы не переписываются.
