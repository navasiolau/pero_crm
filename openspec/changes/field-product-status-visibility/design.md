# Design

**Execution agreement:** Номер задачи 119, ветка feature/119 согласованы владельцем 10.10.2026; OpenSpec и реализация одобрены. Одна целевая локальная проверка, затем существующий полный CI без изменений и развёртывание на staging только через него; одна целевая staging-приёмка. Повторные полные ручные проверки не выполнять без конкретного сбоя. Production/main этим запуском не разрешены.

## Context

Мотивация — `proposal.md`. База исследования: `origin/staging` `ab1c77f3b82cab788f206914d5b2a063e6aafe68`. Статусы PRODUCTION/STORAGE/INSTALLATION уже существуют. Текущие product/file/assignment grants используют широкий `POST_DESIGN_PRODUCT_STATUSES`, включая DONE и RECLAMATION; Work глобально открыт WORKER только на PRODUCTION.

Main spec `engineer-product-access` содержит исторические ссылки на «прежние производственные права» и старое описание общего доступа ACCOUNTANT. Для производственной ветки применяется новое прямое указание владельца; прежняя бухгалтерская офисная видимость не восстанавливается, поскольку текущая принятая роль имеет финансовую область. Инженерные редактирования этим change не расширяются.

## Goals / Non-Goals

**Goals:** единая матрица производственного grant для UI/queries/прямого чтения и актуального статуса изделия.

**Non-Goals:** новые статусы или их массовая смена, глобальное сужение менеджмента/снабженца, изменение начислений или удаление прежних назначений.

## Decisions

1. **Права задаются наборами статусов.** Общий helper возвращает WORKER→PRODUCTION/STORAGE, MOUNTER→INSTALLATION, оба→объединение. Это разрешённая выборка, пользовательские фильтры только сужают её. Повторение списков в каждом UI/действии отвергнуто: текущие broad grants уже разошлись.

2. **Union применяется к независимым grants.** Базовые ADMIN/DIRECTOR/MANAGER/PROCUREMENT сохраняют текущий полный доступ. ENGINEER сохраняет собственную инженерную ветку. Ограничивается именно производственная ветка, включая прежние assignment/participant shortcuts: задача или assembler/mounter ID не дают WORKER право INSTALLATION. Дополнительный WORK_COORDINATOR не предоставляет продуктового grant.

3. **Дочерние проекции имеют тот же разрешённый продукт.** В product/project lists, search/select, Work и file queries используются актуальные статусы и live/draft ограничения. Смешанный проект не возвращает закрытые дочерние изделия, файлы, названия/счётчики или ссылки. Общие разрешённые проектные данные не становятся источником закрытого технического содержимого. Колонки/фильтры скрывают статусы вне реального grant, но сервер остаётся источником прав.

4. **Работы читаются для самостоятельного распределения.** WORKER/MOUNTER видят обычные работы доступных изделий и свободный объём даже без прежнего назначения на задачу. Фонды и чужие персональные суммы не раскрываются этим разрешением. Существующие личные начисления/выплаты остаются в расчётнике после смены статуса изделия; статус карточки не является фильтром финансовой истории.

5. **Изменения повторно проверяют текущий статус.** Перед Work/task/file действием сервер внутри транзакции проверяет свежие роли и доступ; UI с ранее разрешённым изделием не сохраняет grant после PRODUCTION→INSTALLATION для чистого WORKER. Исторические задачи/таймеры не удаляются и не переassignяются автоматически.

## Risks / Trade-offs

- Старая OR-ветка сохраняет лишний grant → проверить assignment, percentage participant, общий project task и прямой file ID отдельно.
- Скрытие карточки удаляет зарплату из истории → отдельные личные финансовые запросы сохраняют существующий actor scope без статусного фильтра.
- Сужение родителя теряет инженерные права → native mixed-role сценарии проверяют независимое объединение, а не отрицательный запрет на весь аккаунт.

## Migration Plan

Без БД-миграции и пересчёта данных. Реализовать до `field-work-editing` в отдельной ветке с согласованным номером. Проверить реальные SQL-предикаты всех статусов/назначений и прямые HTTP/файловые запросы на существующей БД; QA откатывается. После разрешённых ordinary merge/push/CI принять фактический staging на трёх вариантах производственных ролей. При sync спецификаций историческое «прежнее» производственное разрешение должно ссылаться на эту новую матрицу, не возвращая прежние broad grants.
