# Design

## Context

Зависимость #214: nullable Product JSON, общий FurnitureSpecifications и pure legacy projection. Старый редактор изменяет products, а общий sheet-render используется preview/PDF.

## Goals / Non-Goals

**Goals:** единый канонический источник КП, изделия, печати и агентских команд.

**Non-Goals:** массовая перезапись старых КП/версий, правки исторического генератора, production.

## Decisions

- items[].specifications — массив Section из #214. Отсутствие означает legacy; [] — явную очистку. При обычном сохранении legacy переводится общим адаптером один раз, исходный products остаётся неизменным источником истории. Чтение/открытие не записывает КП.
- Каталог и нормализация используются из @pero/kp-template FurnitureSpecifications; JSON schema явно описывает sections в proposal contract/OpenAPI/MCP. Description/size/note остаются самостоятельными полями item.
- ID обозначает жизнь раздела, а type — его смысл: новые строки получают UUID; повторное добавление не использует ID удалённой строки. Product sourceGeneration остаётся внутренним guard #214 и не входит в items[].specifications.
- ID сохраняется на протяжении жизни раздела. Добавление раздела после удаления получает новый ID, стандартный тип остаётся уникальным. Legacy-адаптер назначает детерминированные ID. Fingerprint receipts рассчитывается по первоначальному принятому payload, случайная нормализация не участвует в идентичности retry. Сохранённый state и ACK совпадают.
- Редактор использует структурированные строки, добавление из каталога либо custom с группой, удаление и обычный draft autosave. ACK обновляет структуру формы только без более нового draft; более свежая работа сохраняется с её ID. Старый клиент не может незаметно менять products после перехода: отсутствие canonical либо изменение устаревших blocks при canonical источнике отклоняется с просьбой обновить редактор. Restore legacy версии — отдельный разрешённый путь через тот же адаптер.
- После обновления редактора выбранный более свежий legacy-черновик переносит явные правки старых полей в структурированные разделы для проверки. Сохраняются архивные products с сервера и ID однозначно сопоставленных разделов. Если меняется состав неразличимых разделов, редактор показывает результат переноса и требует явного действия без диалога. Открытие и перенос черновика не выполняют серверную запись.
- Renderer предпочитает specs по наличию, не truthiness. Старые выпущенные snapshots без specs продолжают старое отображение; новые показывают ordered заполненные разделы. Оба layout и приложения договора используют общий renderer. Новая UMD-зависимость входит в asset allowlist и template identity.
- После готовности шрифтов общий DOM-пагинатор переносит переполненный список на листы A4 продолжения, дробит длинный пункт по фактической высоте и сохраняет нумерацию. Цена/количество/изображения остаются в исходной карточке. Короткие и legacy карточки сохраняют прежнюю геометрию. Preview отменяет устаревший расчёт после смены HTML; оба renderer пути используют ту же функцию.
- Новый редактор умеет перенести выбранный более свежий legacy-черновик после обновления вкладки. Не связывать произвольные блоки по индексам: однозначные сопоставляются по названию/содержимому, неоднозначные дубли требуют видимого немодального действия переноса после просмотра нового состава. Исходный локальный черновик сохраняется до этого действия; открытие не делает PUT.
- Репозиторный skill/references, установленный skill и E:/KP инструкции требуют канонические названия, порядок, краткий текст, только подтверждённые сведения. Цены/количества/доставка/монтаж и остальная коммерческая логика сохраняются.
- Перед новым структурированным write агент проверяет GET /api/v1/openapi.json именно целевого сервера. Поддержка требует явной схемы specifications в POST и PUT. На старом сервере используется совместимый legacy-формат с теми же названиями, не specs-only; клиент не позволяет незаметно записать новый единственный источник на старый сервер. Это сохраняет рабочий навык до отдельно разрешённого production-выпуска.

## Risks / Trade-offs

- Старый редактор и новый source расходятся → включать editor/API/renderer вместе и проверять stale tab.
- ACK уничтожает текущий draft → сохранять более свежую работу, тестировать поздний ответ.
- Старый snapshot меняется при чтении → адаптер только при явной записи, исторические версии неизменны.

## Migration Plan

Ветка создана от свежего staging; после принятия #214 обычный merge актуального staging в #215 без копирования/cherry-pick. Local проверки, обычный merge/push staging, фактическая приёмка SHA/образа/UI/PDF/API. Новая DB migration не требуется. Production вне задачи.
