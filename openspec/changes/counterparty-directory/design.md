# Design

## Context

Причина и согласованный результат — в proposal.md. На базе `origin/staging=e8886cc3` отдельной модели контрагента, страницы и навигации нет. `Client` относится к заказчикам проектов; логистика имеет самостоятельные рейсы и финансовые факты. Навигация живёт в `lib/nav`, проверка операционных маршрутов — в `lib/operational-access`, действия и страницы используют auth/requireRole. Для таблиц и диалогов уже есть общие компоненты. Задача №171 изменяет ту же Prisma-схему и должна войти в staging первой.

## Goals / Non-Goals

**Goals:** независимый справочник с минимальным набором деловых данных, единым ролевым разрешением и транзакционным аудитом.

**Non-Goals:** расширение Client, новые API/бот-команды, глобальный поиск, кассы и балансы контрагентов, дублирование полей старой CRM, удаление/архивирование/импорт и связи с рейсами или закупками.

## Decisions

- Ввести `CounterpartyType { SUPPLIER, CARRIER }` и `Counterparty`: `id` cuid, обязательные `type`/`company`, nullable `phone`/`comment`, технические `revision Int @default(0)`, `createdAt`, `updatedAt`. Имена компаний не уникальны: согласованного идентификатора для объединения разных организаций нет. Миграция только создаёт enum/таблицу, не переносит записи и не меняет существующие таблицы.
- Выделить `COUNTERPARTY_ROLES = ADMIN/DIRECTOR/MANAGER/PROCUREMENT` в общем наборе ролей. Добавить пункт «Контрагенты» после клиентов в группе «Управление» и явную проверку `/counterparties` в центральной политике. Страница, запросы и мутации проверяют это разрешение самостоятельно до чтения/записи; скрытие меню не считается защитой.
- Строгий input: `type`, `company`, необязательные `phone`/`comment`; строки обрезаются по краям, пустые необязательные значения превращаются в null. UI нового контрагента явно выбирает «Поставщик» по умолчанию; сервер всё равно требует допустимый тип. Телефон остаётся текстом, чтобы сохранять плюс, пробелы и добавочный номер.
- Серверные create/update возвращают сохранённую карточку. Update требует `expectedRevision`; условный update по `id+revision` увеличивает версию. Неизменённый input не создаёт лишний аудит, устаревшая версия возвращает конфликт. Вместе с изменением в одной существующей mutation-транзакции создаётся ChangeLog old/new, источник web. Новых внешних событий не требуется.
- `/counterparties` — одна динамическая страница с DataTable и обычными Base UI-диалогами просмотра/редактирования. Колонки: компания, тип, телефон, комментарий; полный комментарий в карточке. Поиск DataTable включает компанию/телефон/комментарий; фильтр типа применяется к строкам перед таблицей. Смена фильтра сбрасывает страницу. Успешный ответ обновляет локально подтверждённую карточку и инициирует обновление серверного списка; ошибка оставляет редактор и ввод открытыми.

## Risks / Trade-offs

- Общее имя «контрагент» может привести к присоединению к существующим финансовым сущностям → в этой задаче модель не имеет внешних ключей на Client/Payment/LogisticsTrip, формы этих сущностей не меняются.
- Новый маршрут иначе попадает в разрешающий fallback центральной политики → добавить явную проверку и тестировать прямые страницу/чтение/действия для запрещённых ролей, включая комбинированные.
- Параллельные правки могут потерять контакты → optimistic revision и понятный конфликт вместо перезаписи устаревшим редактором.
- Ветви №171 и №174 затрагивают Prisma-схему → до кода получить GO оркестратора после включения №171 в staging, обновить ветку обычным FF/merge и сохранить поля №171.

## Migration Plan

Зарезервирована `20261017000200_counterparty_directory`, после `20261017000100_client_passport_details`. Генерация клиента и Prisma validate выполняются без изменения зависимостей. Применение миграции и native-проверки — только оркестратором на существующей разрешённой БД с guards и доказательством сохранности. Новый стенд, reset, seed и дампы не создавать. Staging принимается по фактическому SHA/образу и сценариям. При откате приложения таблицу и внесённые контакты сохранить; production-миграция отдельно согласуется владельцем.
