# Design

## Context

См. proposal.md — Why. Текущее состояние: `getProductPercentageView` считает `draftTotal` только при активном и подходящем `assignee`, иначе прогноз null; `total` для не-финанса всегда null, строка суммы в `SinglePercentageRow` рендерится только при `canViewAll`; `historicalRate` в дефолтах допускает только 1 знак и нормирует `toFixed(1)`; форма настроек использует plain `Input` с шагом 0.1; новые изделия уже получают 3 конфига из одного снимка дефолтов. Ограничения: TS strict, только pnpm, UI и комментарии по-русски, без коммитов/пушей, без restic/E:/PVE/CT/VPS/prod-БД/seed, работа только внутри worktree feature/82.

## Goals / Non-Goals

**Goals:** прогноз DRAFT без исполнителя по ставке+цене; поле видит только свою сумму BYN и имена, проценты скрыты; менеджер видит всё и получает подсветку при `rate==null`; точность настроек 2 знака с общим `PercentageRateInput` и шагом 0.5.

**Non-Goals:** изменение формулы `calculateWholeProductPercentage` и версий расчёта; backfill старых изделий; запрет null в настройках (null остаётся «без оплаты»); переименование DELIVERY→STORAGE (это делает feature/81); изменение прав MANAGER/PROCUREMENT и FINANCE_ROLES на странице.

## Decisions

- Прогноз без исполнителя: убрать из `queries.ts` проверку `assignee?.active && assignee.eligible`, оставить `currency BYN`, `pool` не SETTLED/LEGACY_PROTECTED, `rate!=null`, `productTotal!=null` (цена×количество). Альтернатива — требовать получателя — отклонена: противоречит требованию «сумма видна ДО назначения».
- Видимость не-финансу: `members` только своя строка (`ownMember ? [ownMember] : []`), `ratePercent`/`currentRatePercent`/`unitPrice`/`price`/`productTotal` — null, чужие суммы скрыты фильтром, имена оставлены через `assignee`, `total` (прогноз `draftTotal` или замороженная сумма) виден всем для строки своей суммы. Альтернатива — скрыть `total` тоже — отклонена: поле тогда не увидит прогноз без назначения.
- Карточка: `%`-инпут рендерится только при `canViewAll`; строка суммы рендерится всегда в DRAFT (для поля — `ownMember.amount ?? total`, для менеджера — превью `singleProductPercentagePreview` с фолбэком на серверный `total`); при `rate==null` менеджеру показывается предупреждение. Альтернатива — readOnly-инпут для поля — отклонена: требование «% никому кроме canViewAll не рендерить».
- Точность: `historicalRate` — regex `^(?:0|[1-9]\d?|100)(?:\.\d{1,2})?$` + `refine <=100` + `transform Number.toFixed(2)`; старые «5.1» проходят regex и читаются как «5.10». Альтернатива — обрезка без округления — отклонена: `toFixed(2)` сохраняет канон Decimal и совместим с `parsePercentageRate` (всегда 2 знака).
- Форма: заменить plain `Input` на общий `PercentageRateInput` с `commit`-заглушкой (реальное сохранение кнопкой формы), подсказку обновить. Альтернатива — оставить `Input` с новым regex — отклонена: требование явно просит общий компонент со стрелками 0.5.
- Новые изделия: `createProductCore` уже создаёт 3 конфига из одного снимка; изменений логики не требуется, добавляется только проверка и подсветка null; зависимость STORAGE фиксируется комментарием.
- STORAGE: новый код не вводит DELIVERY; где нужен статус доставки — строковый литерал "STORAGE" с комментарием о зависимости от feature/81, мерж после feature/81. Существующие DELIVERY в `core.ts`/`product-statuses.ts` не трогаем, чтобы не конфликтовать с feature/81.

## Risks / Trade-offs

- [Поле увидит целое при нескольких долях] → в текущем потоке доли одиночные (transfer retired, `shareUnits 1000000`), `total` равен своей сумме; при будущих долях потребуется вернуть `ownMember.amount` вместо `total`.
- [Старый «5.1» станет «5.10» и CAS сравнит строки] → `readProductPercentageDefaults` парсит через ту же схему, обе стороны каноничны; конфликт покажет актуальную версию, данные не теряются.
- [`PercentageRateInput` в форме зовёт commit на стрелках] → commit-заглушка возвращает true без записи, реальная запись кнопкой с тем же `clientMutationId` и CAS.
- [Прогноз без получателя скрывался `recipientEligible===false`] → карточка для поля/менеджера использует серверный `total`, а не только клиентское превью, поэтому прогноз виден.
