# Design

## Context

См. proposal.md. В ArticlesView уже есть поля кода, названия и комментария, клиентская проверка числового кода и сообщение о конфликте. createExpenseArticleCore проверяет FINANCE_ROLES, принимает необязательный code, назначает следующий код при его отсутствии, пишет запись и аудит. addExpenseArticle сейчас скрывает созданную статью, возвращая только ok. PaymentDialog используется обычными расходами и оплаченной складской закупкой. Реализация №175 защищает его инициализацию сессией открытия и автором.

## Goals / Non-Goals

**Goals:** одна форма статьи, каноническая опция из сервера, локальный выбор без сброса денежного черновика, сохранение существующих прав и числовых кодов.

**Non-Goals:** новый read API для подсказки кода, изменение справочной схемы, прав финансов, истории платежей или протокола неподтверждённых команд. Редактирование номенклатуры относится к №179.

## Decisions

- Выделить ArticleDialog с open/onOpenChange, optional suggestedCode и onCreated(ExpenseArticleOption). Справочник продолжает предлагать следующий код по существующему полному списку; inline показывает пустой код как «автоматически». Пустой код передаётся как undefined, ручной непустой проверяется существующим parseExpenseArticleCode. Дополнительный серверный запрос ради подсказки не нужен.
- addExpenseArticle возвращает discriminated result `{ok:true, article:ExpenseArticleOption}` либо `{ok:false,error:string}`. Опция строится из фактически созданных id/name; существующие callers, проверяющие ok, сохраняют совместимость. Не возвращать полный ORM record в клиентский callback.
- Сохранить requireFinance, createExpenseArticleCore, withTaskTransaction, серверную уникальность code и обработку P2002. Автоматические коды выбираются сервером под существующей общей блокировкой; ручной конфликт остаётся ошибкой формы. Создание не вызывает денежный writer.
- В PaymentDialog хранить добавленные опции локально и объединять их с полученными props по id без дублей; успешный callback добавляет каноническую опцию и выбирает её. Список статей не является зависимостью сброса draft; родитель остаётся смонтированным. Реализацию основывать на принятой №175 после обычной интеграции из staging.
- Предоставить действие у выбора статьи только в расходе/закупке, включая пустой справочник. Блокировать его при pending, actor loading, blocked/UNKNOWN command; не давать отправлять денежную форму во время вложенного создания.
- Использовать существующие Base UI Dialog и SearchableSelect. Закрытие child не закрывает parent, после отмены или сохранения фокус возвращается к действию создания. Сохранение статьи не сбрасывает выбор кассы/валюты, курс, документы или mutation ID.

## Risks / Trade-offs

- [Два пользователя выбрали одинаковый ручной код] → серверный unique constraint и существующее сообщение; родительский ввод сохраняется.
- [Обновление props после revalidate] → локальное объединение опций и защита сессии из №175 без переоткрытия родителя.
- [Escape или click вне вложенного диалога] → проверка реальных компонентов в Chromium на независимое закрытие и возврат фокуса.
- [Сохранённая денежная команда] → controls остаются заблокированы; новый callback не меняет её frozen payload.

## Migration Plan

Миграции и новых зависимостей нет. Код реализации начинается только после GO оркестратора и получения №175 обычным merge из staging. Staging-проверка выполняется на точной развёрнутой ревизии, main и production этим заданием не изменяются.
