# Design

## Context

См. proposal.md. На базе 81ec6e85 контакты проекта используют общий CAS-контракт и контроллер, Project → Client locks и общий advisory-координатор мутаций. Создание проекта, в том числе из КП, проходит через один доменный writer. Журнал использует writeChangeLogInTransaction.

## Goals / Non-Goals

**Goals:** собственный текст проекта, совместимость старых вызовов клиента, атомарное разовое заполнение и согласованная замена при смене клиента.

**Non-Goals:** справочник контактных лиц, постоянная связь с ФИО, дополнительные каналы связи и изменение шаблонов документов.

## Decisions

- Client.isContactPerson Boolean default false и Project.contactPerson String?; добавочная миграция без заполнения прежних проектов. Источник текста отдельно не хранится: после подстановки текст живёт самостоятельно.
- Флаг optional в ClientInput; create применяет false, update без флага сохраняет настройку. Форма передаёт boolean и baseline; CAS сравнивает только изменённые поля.
- Подстановка при create и clientId change находится в общих writers. Смена на прежний clientId остаётся no-op; реальная смена заменяет contactPerson одной записью со связью клиента.
- При false → true клиентский writer заполняет только пустые живые проекты, с аудитом и событием на каждый. Используется существующий общий координатор, без нового протокола блокировок.
- contactPerson входит в группу контактных контроллеров и версионную проекцию. PATCH содержит expectedValue, expectedClientId и clientMutationId. Смена клиента сначала flush всех трёх контактных полей; ответ включает подтверждённое contactPerson. На реальный clientId change все контактные контроллеры перепривязываются.
- UI использует текущие InlineTextField и Checkbox. На sm+ телефон и контактное лицо в двух равных колонках, ниже адрес; форма клиента сохраняет галочку обычной кнопкой «Сохранить».
- Новые поля получают русские подписи в действующем журнале; автоподстановка записывается с причиной и инициатором. Частичное сохранение остаётся компактным без полной перезагрузки карточки.

## Risks / Trade-offs

- Конкурентные флаг/проект/правка → общий координатор, CAS и guards клиента; проверка на реальной разрешённой local БД.
- Старые fixtures/DTO не знают boolean → обновить типы редактора и fixtures, а отсутствие флага на старом input не считать false при update.
- Устаревшая проекция после смены клиента → clientVersion и групповой контроллер, сохранение dirty/conflict черновиков.

## Migration Plan

Добавить два столбца через Prisma migration; проверить на разрешённой local БД штатным deploy без reset/seed. По поручению 19.11.2026 перенести на staging штатным CI/watcher с автоматической миграцией и проверить фактический runtime. Local/staging дампы не создавать. Production-миграция и выпуск отдельно согласуются владельцем; при будущем откате приложения столбцы сохраняются. Никаких операций restic.
