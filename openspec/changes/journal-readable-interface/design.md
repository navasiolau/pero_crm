# Design

## Context

Список сейчас строится из raw ChangeLog и локально фильтрует 200 записей. №221 предоставляет безопасное русское JournalPresentation v1, №222 — async actions listJournal/getJournalEntry/listJournalFilterOptions и DTO query-contract.ts. Здесь меняется только представление. Общий DataTable уже поддерживает server state и мобильные карточки, но desktop-строкам недостаёт клавиатурной активации.

## Goals / Non-Goals

**Goals:** один повторно используемый Journal с scope и начальными фильтрами; одно окно деталей; полное сравнение; настоящие браузерные проверки событий, фокуса и переполнения.

**Non-Goals:** изменения прав других разделов, записи БД, обработка старых событий, покрытие доменных writers, размещение журнала в проекте/изделии (№224).

## Decisions

- Journal получает scope (`global` либо project/product с постоянным ID) и initialQuery. Полные данные остаются на сервере до клика. Фильтры и номер страницы передаются actions №222; DataTable получает server state и не выполняет второй локальный поиск.
- Таблица содержит пять колонок; источник доступен только в подробностях. Сущность в строке — текст, не ссылка. Ссылки в карточке используют server-provided href и постоянные ID.
- Используем Base UI Dialog, уже обёрнутый в проекте. Dialog имеет фиксированный заголовок с закрытием и отдельную прокручиваемую область. Кнопка сравнения меняет начальную позицию того же диалога.
- Последовательный номер каждого запроса исключает замену актуального результата поздним ответом. При закрытии состояние details очищается; после ошибки доступны повтор и закрытие. Сообщение ошибки не содержит сырого backend error.
- Фокус возврата сохраняется в ref до открытия. DataTable получает новый опциональный rowAriaLabel; tabIndex и Enter/Space активируются только для opt-in таблицы, остальные таблицы не меняют поведение. Встроенная кнопка останавливает всплытие клика.
- Проверка UI исполняет реальные React-компоненты, DataTable, SearchableSelect и Dialog в Chromium; заменяется только серверный transport на управляемые synthetic ответы. Продуктовые БД и сеть приложения не используются.

## Risks / Trade-offs

- Поздний ответ после смены события → проверять request generation перед каждым setState.
- Длинные ключи и текст → min-width:0, переносы и отдельный scroll; проверять отсутствие переполнения на 390 px.
- Фокус без DialogTrigger → явный finalFocus на сохранённый элемент, при размонтировании строки возврат к контейнеру журнала.
- Зависимости №221/222 отсутствуют до интеграции → общий контракт согласован с авторами, файлы не копируются; штатный merge принятого staging выполняется по команде root.

## Migration Plan

После приёмки №221/222 обычным merge перенести принятый staging в ветку №223, выполнить local проверки, передать diff root. Root интегрирует штатным merge и CI, проверяет реальный staging. Main и production этой задачей не изменяются.
