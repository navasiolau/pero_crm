# Design

## Context

См. `proposal.md`. Исследована рабочая №10 в `product-composition`: ревизии DRAFT/CONFIRMED, клонирование с новым row ID и прежним lineage ID, общий advisory lock `(18435,55001)`, проверка `draftVersion`, серверный Product ACL и SQL guards. Сейчас покрытия отсутствуют. `File` принадлежит проекту и необязательно изделию; действующий `deleteFile` сначала удаляет метаданные, затем содержимое. Это требует проверки ссылки до удаления, чтобы история образцов не потерялась.

## Goals / Non-Goals

**Goals:** небольшой ручной реестр назначений внутри ревизии состава; сохранение исходных кодов и образцов; общая транзакция с существующим жизненным циклом; независимость от 3D.

**Non-Goals:** глобальный каталог материалов/колеров, получение HEX по RAL, автоматическая геометрия/ориентация сторон, новый загрузчик, складские списания и калькуляция стоимости покрытий.

## Decisions

### Строка назначения внутри состава

Добавить `ProductCompositionFinish`: id, revisionId/itemId с составным FK принадлежности, surfaceKind FACE/EDGE/WHOLE, surfaceLabel и нормализованный ключ, layerOrder, finishKind ENAMEL/VENEER/COATING, name, code, nullable colorHex/sampleFileId, даты. Unique `(itemId,surfaceKind,normalizedSurfaceLabel,layerOrder)`. Подпись поверхности до 80 символов, название/код до 160, порядок слоя 1–20, до 120 назначений на позицию и 10 000 на ревизию. Для WHOLE подпись каноническая «Целиком». Несколько слоёв поддерживают шпон с лаком без скрытой подмены одного материала другим. Автонаследование от родителя исключено: количество модулей не сообщает, какие поверхности детали покрыты.

### Жизненный цикл и блокировки

Перед каждой записью общий advisory lock, Product/revision lock, свежий ACL и optimistic version. SQL trigger назначения разрешает INSERT/UPDATE/DELETE только в DRAFT, блокируя родительскую ревизию; смена принадлежности существующего назначения запрещена. Клонирование состава копирует назначения через карту old→new item IDs. Удаление поддерева и отмена черновика сначала удаляют его покрытия, затем строки. Подтверждение проверяет все назначения внутри общей транзакции до фиксации ревизии. Черновик без покрытий остаётся допустим: данных пока нет, а не «все поверхности покрыты».

### Образцы через существующие файлы

Опциональный sampleFileId — FK RESTRICT на существующий File, который сервер проверяет по `file.productId === product.id`, общему projectId и актуальному file ACL. Только JPEG/PNG/WebP, без SVG и внешних URL. Выдача изображения идёт через действующий защищённый `/api/files/[id]`; никаких публичных bucket-ссылок. Интерфейс выбирает уже загруженный образец из файлов изделия. HEX — необязательный `#RRGGBB`; сохраняется uppercase, рисуется рядом с кодом и подписью. Названия и текстуры не выводятся из HEX автоматически.

`deleteFile` проверяет ссылки под тем же замком и возвращает доменную ошибку; FK RESTRICT закрывает гонку с назначением. Содержимое удаляется только после успешного удаления метаданных. Пока существует ссылка хотя бы из черновика, файл нельзя удалять; снять такую ссылку можно правкой черновика. Подтверждённый образец сохраняется в истории.

### Интерфейс и ошибки

Разворачиваемый блок покрытия каждой позиции, список поверхностей и слоёв. Редактирование отдельно от формы геометрического состава: доступны тип поверхности, подпись, порядок, тип материала, название, код, HEX и выбор образца. Существующие формы/диалоги и зоны нажатия ≥44–48 px; поле HEX не является единственным способом узнать цвет. Сохранение при прежнем draftVersion либо succeeds один раз, либо возвращает понятную ошибку обновления. Новый пустой слой не создаётся при открытии формы.

## Risks / Trade-offs

- [Потеря изображений старой ревизии] → FK RESTRICT и проверка удаления до storage delete.
- [Дубликаты после потери ответа] → уникальный адрес поверхности/слоя, optimistic version и чтение обновлённого состава перед повтором.
- [Большой состав] → явные лимиты и пакетное клонирование, без запроса на каждый слой при чтении.
- [Неверная ориентация сторон] → ручные видимые подписи; автоматические 3D-соответствия отложены.

## Migration Plan

Разработка опирается на локальный коммит №10 `374abea`, уже прошедший unit/DI/build, но ещё не native/staging приёмку. До выпуска №12 обязательно принять №10 на обеих средах. Новые enum/таблица аддитивны, без backfill и без правки существующей истории. Миграция не выполняется до review SQL, protective backup и разрешения конкретных QA fixtures для local/staging. После появления назначений откат на код без поддержки покрытий запрещён: старый clone/delete не умеет сохранять их. Только совместимый forward fix. Main/production HOLD.
