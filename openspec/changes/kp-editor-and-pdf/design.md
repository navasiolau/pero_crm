# Design

## Context

Источник — текущий рабочий каталог `D:/Projects/pero_kp` с локальными доработками договора. SheetRender отвечает за исходные округления, HTML печати и состав страниц. Web CRM работает на Node 22 Alpine без Chromium. Foundation №180–183 интегрируется обычными merge; её код между ветками не копируется.

## Goals / Non-Goals

**Goals:** сохранить редактор и результат печати, предоставить закрытые интерфейсы CRM и ограниченный рендер.

**Non-Goals:** публикация выпусков, принятие КП, переходы этапов и HTTP handlers session/API v1 относятся к №185–187. №184 не объявляет эти сценарии готовыми и не применяет миграции.

## Decisions

- `@pero/kp-template` содержит выбранные исходные ресурсы и SHA-манифест; изменяются только адаптер CRM, сохранение `crmKind` и URL локальных шрифтов. Печатные CSS, шаблон DOCX и расчёт SheetRender сохраняются. Общий пакет исключает отдельные реализации шаблона в web и worker.
- Серверный Webpack явно оставляет exact bare import `@pero/kp-template` внешним CommonJS-модулем до правил Next. В Next15 `serverExternalPackages` проверяет resolved путь через `/node_modules/`, а workspace realpath находится в `/app/packages/`; одного списка недостаточно. Обычный Node loader сохраняет package `__dirname` для manifests/assets. Клиентский compiler и browser-subpath не меняются.
- Редактор открывается в iframe `/kp/frame` со своей CSS-средой. Родительская React-панель использует существующий SearchableSelect клиентов и управление курсом/версией. Обмен — только с тем же origin и конкретным iframe, без API-ключа в браузере.
- Session-клиент использует `/api/kp`, `operationId`, `expectedRevision` и серверный ID КП. Экспорт сначала сохраняет редактор, затем запускает задание по ревизии и скачивает результат по приватному URL, выданному CRM. Сетевой сбой сохраняет UUID и тело незавершённой операции для повтора. Ответ 409 требует обновления; произвольное `state` в экспорт не отправляется.
- Изображения хранятся в state как `kp-media:<id>`; только отображение заменяет токены защищёнными session URL. Загрузка передаёт исходник и подготовленный текущим алгоритмом JPEG 1600/0.82. Строка услуг хранит `crmKind` отдельно от печатной подписи.
- Renderer — отдельный Node 22 процесс/образ с закреплёнными Chromium 141 и Puppeteer Core 24.43.1. Один worker, ограниченная очередь, лимиты тела/изображений/страниц/времени; после каждого задания процесс завершается. Сетевые запросы Chromium запрещены; шрифты и допустимые изображения подставляются из проверенных байтов. Внутренний HTTP требует отдельный секрет и не доступен через proxy.
- Снимок PDF приходит от вызывающего серверного модуля после чтения сохранённой ревизии. Renderer не обращается к БД и S3 и не публикует выпуск. Для договоров после удаления изображений поддерживается растеризация сохранённого PDF в PNG через ограниченный Poppler worker.
- Свежий договор получает bundle: PDF при исходном DPR1 и исходные screenshots DPR2 из того же Chromium page/context, без второго рендера HTML. DOCX собирается в том же ограниченном worker исходным генератором; templateHash покрывает шаблон, код, font-face CSS и закреплённые байты шрифтов.
- CI job `kp-renderer-tests` строит один Linux/amd64 OCI и его Docker projection на закреплённом Node22 base digest. Проверка исполняет реальный Chromium141 и исходные эталоны в контейнере без сети/БД с теми же ресурсными ограничениями. Native web build зависит от испытанного renderer и фиксирует его digest в OCI label. Публикация web/renderer/bot требует всех unit/native/renderer gates; regctl переносит исходный OCI без rebuild. Release packet фиксирует пару web@digest + renderer@digest одного SHA/run/attempt.
- Opt-in watcher сохраняет W07/locks/автоматический GitFlow: branch tag используется только как discovery, затем оба immutable образа проверяются по protocol/revision/run/attempt/source/font/template. Actual up использует собственный временный override; health failure откатывает оба локальных image ID без DB restore. При выключенном флаге исполняется прежний web-only путь. Исходные bytes шаблона/font manifests и fixtures закреплены через `-text` в `.gitattributes`, чтобы Git EOL filters не меняли SHA на Linux.
- Component cohorts запускаются сразу; backend и native jobs оба ждут renderer и стартуют параллельно после него. Backend display name/receipt identity сохранены; YAML steps alias исключает расхождение наборов проверок. Types budget20 минут отсчитывается от начала backend без включения renderer prefix; прежние poll/job limits не расширяются. Publication требует обе unit-группы.
- Общий `KP_RENDER_LIMITS` задаёт DOCX budget1000 PNG-страниц/1000 источников, PNG16 MiB/128 MiB суммарно, JSON192 MiB/результат128 MiB; реквизиты до4 MiB. Сохранённый PDF допускает1000 страниц при общем64 MiB PNG. PDF/bundle остаются64 страницами/64 MiB и JSON96 MiB. Все режимы сохраняют CPU/deadline/memory/PID caps; исчерпание ресурса не публикует результат. Legacy не имел page/PNG caps, только45-секундный рендер/60-секундную функцию; согласованные generous guards сохраняют обычные много-КП договоры.
- Навигация, страницы, HTML и assets доступны только активному ADMIN/DIRECTOR/MANAGER и при `PERO_KP_ENABLED=1`. Остальные запросы возвращают 404; приватные ответы не кешируются. Отдельный service worker генератора не регистрируется.

## Risks / Trade-offs

- Различия Chromium/шрифтов → закреплённые бинарники/шрифты и попиксельная сверка всех страниц исходного и перенесённого шаблонов на одном движке; отдельная серверная приёмка образа остаётся обязательной.
- Задания ещё не объединены с №185–187 → интерфейсы описаны явно; UI показывает ошибку реального HTTP, не имитирует сохранение/экспорт.
- Непривязанные/внешние изображения → renderer отвергает их до Chromium; session backend проверяет принадлежность КП/версии, не доверяя `scope` из query.

## Migration Plan

Приложение рендера и UI поставляются выключенными. После обычного объединения зависимостей — типизация, native DB/runtime и сквозная staging-приёмка по точным SHA/образам; затем отдельное согласованное включение. Изменений рабочих данных в №184 нет.
