# Design

## Context

Загрузка использует assignedProjectVisibilityWhere/productAssignmentWriteWhere, удаление дополнительно требует авторство. Эскиз зависит от техправки; обложка проекта — только от MANAGER. Мотивация и матрица согласованы в proposal.md.

## Goals / Non-Goals

Самостоятельная файловая политика без расширения прав описания, статусов, начислений и задач. Финансовые документы остаются отдельным контуром. Новых файловых endpoint и схем БД нет.

## Decisions

- Общая политика этапов и server-side context resolver проверяют видимость родителя и каждого переданного идентификатора. Task-only запрос наследует productId задачи; чужой исполнитель не ограничивает новый ENGINEER grant.
- Для ENGINEER авторство удаления не требуется только при действующем инженерном файловом grant. Другие роли и прежнее удаление собственных файлов сохраняют свои правила.
- Эскиз/обложка используют ту же матрицу, сохраняя существующие locks, expectedFileId, receipts и cleanup intents. UI получает отдельные canManageFiles/canDelete, технический флаг не расширяется.
- REFUSED добавляется в централизованный инженерный read grant. CONTRACT остаётся читаемым без прав общих проектных файлов.

## Risks / Trade-offs

- Смена этапа во время передачи → повторная авторизация в существующей финальной транзакции загрузки и при каждом удалении/replay.
- Смешанные роли → инженерный grant вычисляется отдельно от прежних FIELD/MANAGER grants.
- Новое право делает прежние отказные fixtures положительными → отрицательные сценарии сохраняются на запрещённых этапах, неверных связях и ролях.

## Migration Plan

Без миграций. Проверки локально, затем полный существующий CI и реальный staging после отдельного разрешения коммитов. Main/production в этот шаг не входят.
