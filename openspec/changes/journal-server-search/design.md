# Design

## Context

См. proposal.md. №221 определяет JournalPresentation v1 и безопасные чистые преобразования. Существующий ChangeLog также хранит идемпотентные receipts. Task.productId изменяемый, поэтому текущая связь не доказывает историческую принадлежность.

## Goals / Non-Goals

**Goals:** единые защищённые чтения для №223–224, полная серверная фильтрация и совместимость незаполненной истории.

**Non-Goals:** UI, новые business events, изменение raw receipts, фоновая служба и запись при обычном чтении.

## Decisions

- Async server actions listJournal/getJournalEntry/listJournalFilterOptions вызывают ADMIN-first queries. DTO списка не содержит raw values, detail возвращает проверенное безопасное presentation.
- Для заполненных событий SQL использует presentation/searchText, JSONB contexts и параметризованный escaped ILIKE. Московский период преобразуется в UTC полуоткрытый интервал. Сортировка дополнена createdAt/id для стабильности.
- Незаполненные legacy записи читаются ограниченными keyset-пакетами, безопасно нормализуются и включаются в общие count/sort/page. Это дороже индекса, но исключает невидимый хвост истории до завершения backfill. Чтения не пишут БД.
- Resolver использует явные снимки связей и доказуемые неизменяемые отношения. Современное имя может использоваться как справочный label; его происхождение и исходные ID сохраняются в technical.referenceResolution/references без повторяющихся подписей в таблице. Оно не заменяет реально отсутствующий исторический before. Переносимые/неизвестные связи не подставляются из текущего состояния.
- Contexts — явное включение в ленту, links — справочные связи. Reader проверяет exact membership; обычное событие изделия не содержит контекст родительского проекта. Явный перенос общей задачи в изделие или обратно включает оба затронутых old/new контекста. Legacy projectId+productId сохраняет приоритет изделия без родительского fan-out.
- Backfill выполняется отдельным reviewed runner с явной local/staging целью, проверкой системного идентификатора PostgreSQL и пакетным compare-and-set только новых колонок. Весь пакет транзакционен, исходные колонки проверяются после записи.
- Старый listGlobalChangeLog сохраняется до №223, чтобы №222 можно было принять отдельным атомарным выпуском.

## Risks / Trade-offs

- Незаполненная история требует последовательного чтения → выполнить backfill перед итоговой приёмкой; не вводить скрытый предел истории.
- Повторное использование номера изделия → ссылки и контексты только по постоянным ID, номер — подпись.
- Удалённый объект без снимка принадлежности → запись доступна в общем журнале, scoped принадлежность не выдумывается.
- Изменение пользователя или объекта после события → исторический snapshot имеет приоритет, происхождение current label явно указано в технических подробностях.

## Migration Plan

Принять №221, штатно влить принятый staging в feature/222, выполнить локальные поведенческие проверки и reviewed backfill dry-run/apply на существующей разрешённой БД. Root подтверждает PostgreSQL guard, неизменность исходной истории, query plan и actual staging. Откат приложения сохраняет дополнительные колонки и исходные receipts; очистка данных не нужна.
