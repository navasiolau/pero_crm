# Spec Delta

## Purpose

Журнал позволяет Администратору найти и открыть любое сохранённое безопасное событие независимо от возраста записи, длины значений и текущей страницы.

## ADDED Requirements

### Requirement: Administrator-only event reading
Система MUST проверять актуальную роль ADMIN перед чтением списка, подробностей события и вариантов фильтров. DIRECTOR и остальные роли SHALL не получать ни данные, ни их счётчики.

#### Scenario: Director requests details directly
- **WHEN** Директор вызывает чтение списка, конкретного события или фильтров напрямую
- **THEN** запрос отклоняется до обращения к данным журнала

### Requirement: Complete server-side search
Система SHALL искать подстроку без учёта регистра по всем безопасным полям события, русским названиям и полным старым/новым значениям, включая вложенные поля и источник. Система MUST возвращать реальное число совпадений и стабильную серверную пагинацию без ограничения 200 последними записями.

#### Scenario: Long value in an old entry
- **WHEN** совпадение находится после 60-го символа вложенного значения в записи старше 200 последних
- **THEN** поиск находит событие и возвращает его полную карточку

#### Scenario: Literal search and Moscow dates
- **WHEN** строка поиска содержит SQL-метасимволы либо задан диапазон дат
- **THEN** метасимволы ищутся буквально, а даты включают только заданные календарные сутки по Москве

### Requirement: Exact event context
Система SHALL предоставлять общий журнал, журнал проекта и журнал изделия. Проектный контекст MUST исключать события, принадлежащие изделию. Подробности MUST проверять принадлежность запрошенному контексту. Личный план и технические дубли SHALL не попадать в пользовательскую ленту.

#### Scenario: Another product and unknown historical ownership
- **WHEN** запрашивается журнал изделия, а запись принадлежит соседнему изделию либо её принадлежность достоверно неизвестна
- **THEN** запись отсутствует в этой ленте; непривязанное бизнес-событие остаётся доступным в общем журнале

#### Scenario: Explicit ownership transfer
- **WHEN** общая задача проекта переносится в изделие либо обратно и событие сохраняет точные старый и новый контексты
- **THEN** событие изменения принадлежности доступно обоим затронутым владельцам; обычная ссылка на родительский проект не включает события изделия в проектную ленту

### Requirement: Historical actors and safe full details
Фильтры SHALL включать исторических и неактивных авторов и «Систему». Список SHALL содержать краткие сведения без полных значений, а отдельная карточка SHALL предоставлять полное безопасное представление события. Секреты MUST отсутствовать в поиске, списках и подробностях.

#### Scenario: Deleted user and secret payload
- **WHEN** автор уже отсутствует в справочнике, а исходный payload содержит секрет и длинное публичное значение
- **THEN** исторический автор доступен для фильтрации, публичное значение сохраняется полностью, секрет не раскрывается и не влияет на поиск

### Requirement: Resumable additive historical backfill
Заполнение представления MUST менять только presentation/searchText, проверять точную разрешённую цель до записи и допускать повторный запуск. Исходные ID, actor, oldValue, newValue и createdAt MUST сохраняться. Отсутствующие исторические значения и связи MUST не выдумываться.

#### Scenario: Interruption and repeated application
- **WHEN** заполнение прерывается между пакетами и повторяется
- **THEN** завершённые записи не переписываются, оставшиеся обрабатываются, исходные события байтово сохраняют свои данные

#### Scenario: Target guard mismatch
- **WHEN** адрес, БД, серверный идентификатор или staging stamp не совпадают с разрешённой целью
- **THEN** выполнение прекращается до изменения журнала
