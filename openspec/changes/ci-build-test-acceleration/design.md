# Design

## Next workers и ранний PostgreSQL — утверждённая фаза12

Next config получает только webpackBuildWorker/parallelServerBuildTraces=true. Root дополнительно разрешил одну проверку `test -s apps/web/public/sw.js` в существующем Docker build RUN после Next: успешный worker build должен действительно выдать Serwist PWA asset; нового test/helper файла нет. Ранний PostgreSQL runner не подделывает MinIO/image identity: отдельный закрытый PG-only guard требует реального CIjob/PostgreSQL контейнера, network/tmpfs, synthetic role/database и текущего checkoutSHA. После host dependencies/generate и host migrate deploy основная pero_ci исполняет пять имеющихся PG-only файлов последовательно в owned process group одновременно с Bake. Existing atomic GO/PID birth/status/timeout/always cleanup переиспользуются. После полного OCI proof обязательный join этой группы предшествует HTTP writers; три оставшихся HTTP/S3 файла исполняются однажды с прежними target guards/main+fault runtime.

Host migration не заменяет свежую image migration. Испытанный immutable image ID после полного OCI proof запускается one-shot только с Prisma migrate deploy на уникальную пустую temporary DB внутри того же owned CI PostgreSQL service/tmpfs. До запуска проверяются fresh DB/role/current ownership; после — полный список текущих migration folders, SHA256checksums и completed records. Exact container/network/labels/image guard, finally/always cleanup обязательны; auxiliary DB исчезает со штатным owned PostgreSQL service. Основной image production CMD не меняется и продолжает migrate deploy+boot основной CI-БД; fault branch сохраняется. Root DESIGN_GO зафиксировал closed all|postgres|http в existing runner: postgres вызывается после install/generate внутри существующей deps group и её atomic300с result, HTTP запускается после успешного waitDependencies join. Ранняя ветка не вызывает shared cleanup; образы/services принадлежат только parent finally/always. Private migration-purpose URL не расширяет main/fault/default guard. Новых файлов/jobs/фреймворков нет.

## Исправление повторной установки, обнаруженной CI273

CI273 прошёл все6gates за428с (+68 к CI272): install26.4с, затем build RUN неожиданно повторил `Recreating /app/node_modules` и install16.8с/726 downloads. После явного `--store-dir /pnpm-store` последующие pnpm команды использовали иной default store. Установленный pnpm11.10.0 config reader принимает `pnpm_config_`/`PNPM_CONFIG_`, а npm_config_store_dir не учитывает; read-only CLI подтвердил PNPM_CONFIG_STORE_DIR=/pnpm-store. checkCompatibility сравнивает modules.storeDir с opts.storeDir, mismatch вызывает UnexpectedStore и force purge; packageImportMethod не входит в workspace-state setting keys/этот compatibility check.

Однострочное исправление добавляет PNPM_CONFIG_STORE_DIR=/pnpm-store в существующий build-only ENV после COPY/install. Install RUN byte-unchanged, node_modules остаётся независимым copy import, дополнительный mount в build RUN не нужен для уже установленных байтов; verify-deps-before-run/supply-chain проверки не отключаются. Runner FROMbase не наследует новый ENV. Эффект и отсутствие reinstall проверяются следующим ordinaryCI, оправданным найденной регрессией; cache/layer экономия заранее не заявляется, warm rerun запрещён.

## Слои и compiler compatibility v2 после CI272

Dockerfile читается с CRLF/CR→LF normalization и строго делится ровно на две части regexp `^FROM base AS runner\s*$` в multiline; отсутствие/повтор границы fail closed. SHA256 compatibility включает весь base/build prefix, config hash прежних glob без Dockerfile, actual node base digest, platform linux/amd64 и effective GITHUB_ACTIONS=true/PERO_CI_EXTERNAL_CHECKS=1. Prepare выдаёт один compat output; exact compiler key добавляет прежний source hash, restore prefix и mount ID используют тот же compat без run/SHA/legacy aliases. Все build commands остаются в conservative prefix. Первый переход v2 может дать MISS.

Только frozen filtered install получает `--mount=type=cache,id=pero-web-pnpm11-musl,target=/pnpm-store,sharing=locked` и `--store-dir /pnpm-store --package-import-method=copy`: store не попадает в dependency layer, node_modules сохраняется; нового store exporter/importer нет. Actual shrink414MB не измерен. Existing Bake web-runtime/minio exporters используют `type=docker` без dest для прямого Engine load; убираются только два tar/load, не original web-oci tar и не attestation max. Full config/diff_ids proof, never-started metadata finally/always cleanup, publishers и dependency verification не меняются. Нет новых repo files/jobs/helpers/tests/deps/DB/host операций; после source freeze один affected static bundle/review, Root — ordinaryCI/actualstaging.

## Утверждённая перестройка после CI271

Metadata читается через `docker cp` из immutable image ID принадлежащего текущему run never-started контейнера (network none, readonly, no mounts); loaded config сверяется с Bake, полный старый OCI verifier выполняется один раз до приложения/image migrations/HTTP/tsc. Единственное исключение новой фазы12 — ранняя host migration основной owned CI-БД под PG-only guard; fresh migration proof испытанного image остаётся после OCI verifier. Exact-name/labels/config cleanup работает и при отмене до возврата CID. Полный `.next/types`, включая package-файлы, копируется в standalone в прежнем build RUN; scratch target/cache удаляются.

Ранний types artifact содержит все file SHA-256, repository/run/attempt/SHA/BUILD_ID/index/config digests. Existing target helper имеет только purposes types|bot-dist: types ждёт successful upload step Native, bot-dist — весь backend SUCCESS. API archive digest проверяется явно до безопасного stdlib ZIP extraction; файлы/пути/symlinks/identity проверяются после extraction. Backend не получает DB env и использует отдельный hosted artifact identity guard, assertCiJob не ослабляется. Types доступен также PR. Poll 5 с, request <=10 с; types <=18 мин ожидания и <=20-й минуты backend, bot-dist <=180 с и <=23-й минуты Native. Producer failure/cancelled/ошибка types/tsc блокируют bot-dist и прежние publishers.

Detached deps group ждёт GO после записи PID/start identity, сохраняет RUNNER_TRACKING_ID; atomic status и проверка отсутствия live owned group обязательны до использования dependencies. Timeout300с, ошибка или смерть без status fail closed. Existing process state merge сохраняет deps при записи tests; finally/always cleanup проверяет ownership до сигналов. Сохраняются pnpm frozen install и generate. Browser navigation целиком переносится components-1→0 с прежними isolation/concurrency. Bake diagnostic summary/record upload отключены; provenance/OCI/логи сохраняются. Измерение только обычным CI, baseline299с, цель180 OPEN.

## Metadata cache follow-up after CI269

Принятый `e0ae9a10`/CI269: all6 SUCCESS, 283 с; native 100 raw registrations = 96 leaf + 4 parent groups, web884/bot38/Python53/guards2, cleanup и tested/promoted OCI подтверждены. Цель менее 180 с OPEN. В том же сохранённом Bake log три metadata COPY CACHED, но vertex `#52` материализует 414,58 MB builder layer (28,5 с download + 20,4 с extract) и дополнительные 64,85 MB; всего vertex 53,2 с, Bake 60 с.

Коррекция ограничена metadata cache records: dedicated `pero-web-metadata` importer идёт перед production fallback, а exporter меняет `mode=min` на `mode=max`, включая промежуточные build/COPY dependency records. Общее production cache/provenance max не меняется. Это не прямое восстановление готовых `.next/types`/BUILD_ID: прежний shared build graph и проверки текущих inputs/revision/run/attempt/config/diff_ids/manifest продолжают связывать metadata с испытываемым OCI. Dockerfile и compiler BUILD_CONFIG byte-unchanged; cold miss остаётся корректным. Увеличение metadata cache export может стоить времени и места, поэтому чистая экономия и цель180 подтверждаются только следующим обычным required CI.

## Tested bot OCI packaging after CI270

Подтверждённый CI270 bottleneck: `docker buildx inspect --bootstrap` в bot publisher ждёт141,5с pull BuildKit image; binary уже установлен. Следующий шаг использует native builder для no-push bot OCI packaging и оставляет прежний gated bot publisher с registry write только для verify/promote original OCI. Producer readiness проверяется явно по текущим repository/run/attempt/SHA, exact backend job SUCCESS и artifact ownership; ожидание ограничено и fail-closed, готовность не выводится из timings. Все unit/native/type/lint/cleanup gates остаются, native не сериализуется за unit matrix. Root разрешил только existing `runtime/target.mjs` для optional закрытого kind web|bot: общий blob/index/config/provenance verifier сохраняет прежний web default/BUILD_ID/action-manifest, bot получает distinct service/path/env и truthful tested-dist/producer manifests+hashes. Новая validator/helper система не вводится. Native203с и первые cache fills не дают обещания180с.

Реализация ограничивает readiness180с, каждый fixed-repository API GET10с/оставшимся deadline, redirects запрещены. Проверяются exact attempt run, backend job SUCCESS и уникальный unexpired artifact ID/name/digest; read-only automatic token доступен только push readiness-step, native permissions contents/actions read. Download выполняется по проверенному artifact ID; реальные plain JS hashes должны совпасть с backend tested.json. OCI config labels связывают tested/producer manifest hashes, общий reader повторяет проверку до promotion. Оба publisher используют один YAML run alias без merge keys: pre-extract archive SHA256, прежний pinned regctl, общий verifier и exact immutable index/referrers; bot не создаёт второй Buildx и не пересобирается. Дополнительных bot runtime/контейнеров/staging probes нет.

## Context

Исходная ветка №170 создана от `origin/staging=e986e290`; там ещё нет runtime №169. Мотивация описана в proposal.md. В установленном Next 15.5.20 встроенная типизация исключает `*.test.*` и `__tests__`, поэтому она не заменяет полный web `tsc`.

Исторический полный private-run №238 занял 887,77 с: приложения 367,60 с, Next 141,93 с, native 232,78 с, включая source build MinIO 209,45 с. Public-run №239 attempt 3 завершился ошибкой старого pixel assertion: 261 с всего, приложения 142,102 с; Next/native не выполнялись. Из этих двух прогонов нельзя выводить полный коэффициент ускорения №170 или приписывать смену runner изменениям кода.

Прежняя цель принята; Root затем подтвердил обычный CI №249 на staging `2f6573b7b8ffe52ad12c364ac9df9e8ed1a39fdc`: 293 с против 789 с №244, 2,69× быстрее. По новому поручению владельца следующая малая итерация остаётся OPEN до фактического результата обычного обязательного CI.

Обычный CI №251 занял 485 с; Root принял staging `a3e5194d78e934f4e824675e718e6e60b2a16686`, native 73/73 и полное удаление временного стенда. Это фактическая приёмка сохранённых проверок; цель 180 с остаётся OPEN. Следующий шаг устраняет повторную подготовку runner и передачу build artifact объединением build/checks и native.

## Goals / Non-Goals

**Goals:** Сократить повторную работу и последовательный critical path существующего CI, сохранив строгие gates, свежие route types и guards №169. Цель следующей итерации — полный обычный обязательный CI не более 180 с; фиксируются фактический SHA, длительность и cache/runner условия, без гарантии такого времени при cold cache.

**Non-Goals:** Новый QA framework, дополнительные benchmark-прогоны, локальные HTTP/DB/S3-стенды, смена runner/settings/billing, зависимости/lockfile, main/production.

## Decisions

1. `PERO_CI_EXTERNAL_CHECKS=1` действует только вместе с `GITHUB_ACTIONS=true`. CI lint остаётся обязательным, полный `tsc --noEmit` запускается после production build. `.next/types` и готовая сборка не кэшируются; допускаются `.next/cache` и отдельный совместимый incremental state после проверки его поведения.
2. Next cache имеет ключи ОС, Node, lockfile, build-конфигурации и исходников. Restore fallback ограничен совместимыми зависимостями и конфигурацией; каждый run заново строит Next. Только `.next/cache` входит в архив.
3. В Docker все workspace manifest-файлы предшествуют install, а исходники следуют после install. Root `.dockerignore` исключает каталоги tests из production context; CI checkout сохраняет все suites и полный tsc, отдельный MinIO context не меняется. Отдельные scopes web/bot/MinIO сохраняются. Только web publisher после успеха полной unit matrix и native передаёт build-stage ARG `GITHUB_ACTIONS=true`/`PERO_CI_EXTERNAL_CHECKS=1`, пропуская повтор Next inline lint/types, но создавая свежий standalone. ARG defaults — false/0; обычные local/Docker проверки сохраняются, runner stage не получает flags, ABI/artifact copy не добавляется.
4. Unit suites выполняются штатным `tsx --test` с process isolation, а pnpm запускает независимые workspace scripts. Следующий YAML-шаг разделяет прежние web globs на три unit matrix группы без пропусков/повторов: `backend` — 260 TS, `components-0` — 32 и `components-1` — 31 MJS/browser TS, всего 323 файла; component files чередуются в прежнем glob order. Полный lint и прочие workspace suites выполняются один раз в backend группе. Default file concurrency не меняется, matrix `fail-fast: false`. Успех unit gate требует успеха всех трёх групп, одновременно выполняемых со свежим build/native.
5. Для разработки владелец отдельно разрешил normal merge `feature/169=8a0f0ae` в `feature/170`; это не является приёмкой №169 и не переносит его в staging. Принятая зависимость затем приходит обычным merge свежего staging. MinIO Dockerfile собирается Buildx с закреплёнными source/Go pins и отдельным GHA scope. Runtime принимает только текущий локальный image ID с проверенными labels; контейнер получает новые run/attempt labels при каждом запуске. Существующие digest-проверки, tmpfs, guard и `always` cleanup остаются.
6. CI выполняет существующие build/checks и native на одном runner: свежий production build и полный web tsc предшествуют native `next start`, без повторной сборки и передачи artifact между jobs. Независимые unit suites могут выполняться параллельно. Exact checkout SHA, repository/run/attempt, Node/OS и native target/ownership guards сохраняются. Если artifact передаётся между jobs, прежний manifest/SHA256/BUILD_ID binding остаётся обязательным. Оба publisher jobs напрямую требуют `success` полной unit matrix и native job с cleanup; только push и успех обеих зависимостей допускают публикацию, failure/skipped/cancelled блокируют её. Native files сохраняют последовательное исполнение: общий warehouse state и protected snapshots не допускают неподтверждённого параллелизма.
7. `hasExternalCiChecks` требует `GITHUB_ACTIONS=true` и `PERO_CI_EXTERNAL_CHECKS=1`; отдельный `PERO_CI_NATIVE_BUILD=1` отключает standalone только в native CI. Docker CI с внешними checks создаёт standalone; обычные local/Docker сохраняют встроенные checks и standalone. Полная `.next`, свежие route types, native `next start`, обязательные lint/полный tsc и source/run binding сохраняются. Успешная приёмка CI256 168 с остаётся историческим warm-run результатом; выигрыш нового Docker шага ещё не измерен.

## Risks / Trade-offs

- Ускорение на cache miss зависит от runner и внешних загрузок → фактическое время фиксируется только по обычным разрешённым CI-прогонам; benchmark не запускается.
- Next не проверяет все test-файлы → полный web `tsc` остаётся отдельным обязательным шагом после build.
- GHA cache может вытеснить слои → отдельные scopes; miss влияет на время, но не на корректность.
- Разработка следующей итерации идёт от принятого staging `567192b4`; прежняя приёмка №169/170 и её receipts сохраняются, новый код требует обычной staging-приёмки.

## Migration Plan

Следующая малая итерация №170 проверяется локально по затронутым конфигурациям и проходит независимый review. Корневой агент выполняет обычную staging-интеграцию и измеряет полный обязательный CI; отдельные benchmark или дополнительные QA-прогоны не создаются. Публикация требует прямого успеха полной unit matrix и native job, fresh source/run binding и `always` cleanup. Main/production и новые schema migrations в эту задачу не входят; фаза12 выполняет только существующие migrations на явно разрешённых synthetic CI целях.
