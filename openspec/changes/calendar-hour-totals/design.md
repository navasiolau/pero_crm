# Design

## Context

PersonalCalendar уже получает только собственные записи выбранного месяца от guarded core; после мутаций обновляет этот список. №106 хранит nullable plannedMinutes. См. proposal.md.

## Goals / Non-Goals

**Goals:** один чистый расчёт периодов/дней и один компонент итогов, пригодные для108.
**Non-Goals:** новые запросы чужих пользователей, учёт фактического времени и отдельный SQL-расчёт часов.

## Decisions

1. Чистый lib/calendar-summary принимает минимальный тип записи, за один проход считает общий результат и дни через calendarLocalValue/Europe/Moscow. Тип результата используется сервером108 и клиентом107.
2. Для часов учитываются PLANNED и COMPLETED; completed длительность отдельно, CANCELLED только счётчиком. Для каждого набора сохраняются число заполненных/пустых длительностей и сумма целых минут. Нет записей →0, все пустые →NULL, смешанные →сумма известных с явным количеством пропусков. Это избегает подмены пустого нулём и не скрывает полезную известную часть.
3. PersonalCalendar вычисляет summary из текущих entries; день выбирается из того же результата. После подтверждённой мутации/перехода месяца нет отдельного кэша итогов.
4. PlanHoursSummary отображает общие и выполненные плановые часы, количество выполненных/отменённых и неизвестных длительностей. №108 переиспользует модуль и компонент.

## Risks / Trade-offs

- Неполная длительность → подпись «Указанные плановые часы» и количество пропусков; полностью неизвестные часы не равны0.
- Позднее завершение → группировка только по startsAt, а не по updatedAt.
- Большие суммы → целые минуты и проверка safe integer.

## Migration Plan

Миграций нет. Local full/SSR/real component, обычный merge/CI/фактический staging; main только после владельца.
