# Design

## Context

См. proposal.md. LogisticsTrip пока не имеет маркера удаления. Расходы уже используют общий activePaymentWhere и исключают SUPERSEDED. Денежные снимки защищены SQL triggers; состав не меняет склад, статусы и зарплату.

## Goals / Non-Goals

**Goals:** отменить ровно один рейс без переписывания денежной истории, сохранить доступ только ADMIN.
**Non-Goals:** восстановление через UI, физическое удаление файлов/данных, массовые исправления или пересчёт исторических курсов.

## Decisions

1. Добавить deletedAt/deletedById как actor snapshot по образцу Project/Product. Общий фильтр платежей требует ACTIVE-проведение и живой родительский рейс. Сами Posting/Allocation/Payment не меняются: это сохраняет immutable историю и прежние снимки.
2. Использовать существующий LogisticsMutation с operation=delete, fingerprint actor/input и той же схемой UUID. Порядок locks: общий денежный → mutation → trip. После ожидания trip lock повторно проверить ADMIN. CAS требует живой рейс и expectedRevision.
3. Аудит и событие внутри транзакции; dispatch и cache invalidation после commit. Повтор не пишет повторное событие; конфликт нового payload или ревизии возвращает409. Revalidation включает проекты текущего состава и исторических allocations.
4. Центральная проверка живого рейса применяется к новым writes и money reads; документы проверяют родителя в reads и под trip lock в обеих транзакционных фазах upload. Хранилище вызывается без удержания DB lock, после него состояние проверяется повторно.
5. Capability canDelete вычисляется по свежим серверным ролям. Общий компонент кнопки использует ConfirmDeleteDialog, фиксирует UUID неизвестного результата, показывает сохранённые суммы и блокирует всплытие клика в строку.

## Risks / Trade-offs

- Пропущенный денежный reader → проверить все Payment readers и реальные кассу/организацию/отчёт/экономику/бюджет на PostgreSQL.
- Гонка с загрузкой → общий trip lock в reservation/finalization и отказ после soft delete.
- Откат на старый образ вернёт расход в учёт → после первой отмены разрешён только образ с новым фильтром или исправление вперёд; маркеры автоматически не снимать.

## Migration Plan

Аддитивные nullable колонки, проверка согласованной пары и индекс списка. Отдельная миграция расширяет CHECK LogisticsMutation.operation значением delete; она нужна по результату native RED и не переписывает уже применённую локально первую миграцию. Local/staging без дампов/reset/seed; production после отдельного согласованного выпуска с проверенным единственным dump. Указанную production-запись удалять только после повторной проверки полного allowlist, включая отсутствие проведений, через новое ядро с ADMIN. Остальные рейсы/состав/документы и денежные итоги сверить до/после.
