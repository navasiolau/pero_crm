# Design

## Context

См. proposal.md. Задача №180 добавляет модели хранения. Общий withMutationTransaction уже сериализует денежные/task записи advisory lock (18435,55001); прежнее создание проекта использует отдельную транзакцию. Product.number уникален даже у скрытых строк, но все FK используют Product.id.

## Goals / Non-Goals

**Goals:** общий in-transaction primitive для проектов и изделий, полная синхронизация состава с сохранением фактов, узкий доступ MANAGER и безопасное повторение записей.

**Non-Goals:** денежные формулы №182, S3 №183, UI/рендер №184, версии/договоры/API/очистка/импорт последующих задач. Публичный feature flag остаётся выключен.

## Decisions

- Общий allocator блокирует выдачу номера и считает MAX по всем проектам в текущей транзакции. Sequence не подходит из-за требования не расходовать номер при rollback. Существующие web/bot вызывают тот же primitive.
- Создание/сохранение КП вызывается только внутри withMutationTransaction, повторно блокирует проект и строку КП, проверяет LEAD и ревизию. Ошибки после первой записи бросают исключение, чтобы callback не закоммитил частичный результат.
- Receipt хранится в ChangeLog с детерминированным ID операции, actor и хешем нормализованного исходного запроса. Возврат receipt проверяет текущие права, живость и принадлежность, но не повторяет запись и не увеличивает ревизию. No-op также получает receipt без доменного события.
- Полное исходное JSON сохраняется; server назначает ID отсутствующим позициям и канонический номер. Поле state.client.crmSnapshot хранит структурированные реквизиты отдельно от печатного ФИО/непрозрачного contact. Каждое сохранение переиспользует clients/core со свежим заблокированным baseline и авторитетным снимком КП; частичный clientSnapshot объединяется с сохранённым снимком. При смене выбранного клиента используется его текущая карточка. Клиент по умолчанию разрешается через PERO_KP_TEMP_CLIENT_ID с проверкой имени «Временный»; автоматическое создание/переименование запрещено.
- Product creation переиспользует существующие стандартные проценты, первичную цену и statusHistory. Синхронизация изменяет только коммерческий текст/количество, вызывает recalculateQuantity и не сбрасывает назначения, статусы, начисления или файлы.
- Исключённые изделия сначала скрываются. Активные номера освобождаются временными значениями внутри транзакции, затем назначаются 1…N. Partial unique index охватывает только deletedAt IS NULL; отдельный индекс номера сохраняет alias lookup.
- Триггеры БД проверяют один projectId у ProposalItem, Product и CommercialProposal, в том числе при изменении родительских связей. Контекстные access helpers дополнительно проверяют живую связь и не доверяют неполному контексту.
- Обязательный hook applyPricing получает нормализованное состояние, стабильные ID и существующий снимок курса внутри той же транзакции; вызывается также при неизменном исходном JSON. Hook applyMedia вызывается там же перед revision CAS. Будущий публичный service обязан собрать денежный hook №182 и media hook №183; №181 не предоставляет public route.
- Audit и outbox сохраняются до commit, уведомления/dispatch/cache выполняются после commit. Кэш инвалидирует ID и прежние/новые номера; UI передаёт ID в существующий helper ссылки. Миграция переводит существующие Notification.link по текущему номеру на ID, сохраняя query/hash; read lookup сначала разрешает точный ID и не переходит к alias при отказе в доступе.

## Risks / Trade-offs

- Историческая некорректная связь → миграция сначала проверяет и останавливается без перепривязки реальных данных.
- Редактирование количества затрагивает рабочие факты → существующая проверка может отклонить всё сохранение, частичная запись запрещена.
- Потерянный ответ после commit → immutable receipt сохраняет прежний результат; смена содержимого с тем же UUID отклоняется.
- Зависимость от №180 → typecheck и native DB приёмка проводятся после обычного merge зависимости; отсутствие сгенерированных типов не считается успешной проверкой.

## Migration Plan

Обычный merge №180, Prisma generate, локальные unit/type/lint проверки и guarded native PostgreSQL проверки на разрешённом 5433. Перед изменением индекса проверить отсутствие конфликтов активных номеров и неверных связей. Незавершённый раздел выключен. Production-миграция и выпуск выполняются отдельно основным агентом; restic, новые БД, seed/reset и дампы local/staging не используются.
