# Переключение staging на ограниченного пользователя PostgreSQL

Предварительно принять ветки с мягкими удалениями, включая личный план и привязку Telegram. До отдельной приёмки оставьте прежний старт web. Изменения роли и учётных данных в production выполняются отдельным выпуском по указанию владельца.

1. Стандартно проведите `prisma migrate deploy` на существующем staging от учётной записи владельца схемы. Миграция создаёт локальную группу `pero_crm_runtime_<digest>` и проверку полномочий. Администратор определяет точное имя через `SELECT 'pero_crm_runtime_' || left(md5(current_database()), 16)` после сверки цели и владельца. Данные, содержимое рабочих таблиц, резервные копии и значения паролей при этом не меняются.
2. Создайте отдельный PostgreSQL LOGIN через защищённый административный процесс. Роль не владеет объектами, не имеет встроенных привилегированных атрибутов и состоит только в этой группе с `INHERIT TRUE, SET FALSE, ADMIN FALSE`. Пароль задайте через защищённый ввод или менеджер секретов. Мигратор по-прежнему владеет схемой. Проверьте непосредственно под новым LOGIN, что `SELECT public.pero_runtime_role_violations()` возвращает пустой массив. Проверьте фактическое подключение и область аутентификации сервера.
3. Запустите второй staging экземпляр web в существующей сети и укажите только ограниченный `DATABASE_URL` и `PERO_DB_ENFORCE_RUNTIME=1`. Для роли web предусмотрен [compose override](../deploy/docker-compose.runtime-privileges.yml). Держите URL мигратора в отдельном защищённом одноразовом окружении. Подтвердите фактический идентификатор образа, health, приватный HTTPS маршрут кандидата, read/write в согласованных изолированных сценариях и отказ проверки запрещённых операций. Основной upstream продолжает обслуживать запросы.
4. После приёмки переключите staging reverse proxy reload на уже здоровый кандидат. Дождитесь завершения запросов прежнего экземпляра и остановите его. Если проверка нового экземпляра не прошла, сохраните прежний upstream. Окна, в котором прокси направляет трафик в нездоровый экземпляр, не требуется.
5. После включения запускайте стандартный `prisma migrate deploy --schema apps/web/prisma/schema.prisma` в отдельном короткоживущем контейнере того же проверенного образа. Примените `SELECT public.pero_refresh_runtime_grants()` из миграционного подключения после завершения Prisma. В web не передавайте пароль БД владельца и `DATABASE_MIGRATION_URL`. Повторно докажите пустой массив нарушений после миграции и существующего ночного refresh до подачи трафика в обновлённый экземпляр. Если restore меняет набор ACL, этап применения грантов должен выполняться владельцем в штатном согласованном refresh. Действующие задания и схема refresh требуют отдельной приёмки.

В CI проверка выполняется на принадлежащем job PostgreSQL 17 после стандартной Prisma-миграции. Реальный LOGIN подтверждает чтение, INSERT/UPDATE, удаление черновика и отказ удаления бизнес-записей, TRUNCATE, DDL, изменения ключей, снятия READY и перехода в роль владельца. Проверка capability не меняет сборку рабочего веб-приложения до явного включения режима. PostgreSQL может удалять только записи `PENDING` без маркера публикации из двух перечисленных таблиц отложенных документов. Режим доступа к документам и срок очистки задаёт доменный сценарий.

Плагины остаются доверенными пакетами монорепозитория. В контекстах есть проекция чтения и namespaced события модуля. Проверки SDK не запускают сторонние пакеты в отдельной песочнице. Подключать бизнес-команду следует через проверенный обработчик хоста, использующий общую доменную транзакцию и полномочия действующего актёра.
