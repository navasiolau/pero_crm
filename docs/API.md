# API КП и договоров

Раздел включается только при `PERO_KP_ENABLED=1`. До сквозной приёмки значение
остаётся `0`; все маршруты раздела возвращают 404. Документ описывает контракт
реализации №187, а не подтверждение её staging-приёмки.

## Авторизация

Внешние интеграции используют `/api/v1/kp` и только заголовок
`Authorization: Bearer <ключ CRM>`. Cookie не заменяет Bearer. Ключ создаётся в
«Настройки → API и токены», хранится сервером хешированным и может быть отозван.
Для каждого запроса нужен действующий владелец ключа с ролью ADMIN, DIRECTOR или
MANAGER. Ключ без владельца, неактивный пользователь и изменение привязки владельца
блокируют доступ. Набор «ИИ-агент КП» содержит семь отдельных scopes:

| Scope | Возможности |
| --- | --- |
| `kp:read` | КП, версии, выбранные клиенты, изображения и PDF КП |
| `kp:write` | Создание и полное сохранение КП, восстановление версии, создание клиента |
| `kp:media:write` | Загрузка приватного изображения |
| `kp:export` | Запрос выпуска PDF КП |
| `kp:contracts:read` | Форма и история договора, DOCX, задания договора |
| `kp:contracts:write` | Сохранение настроек договора |
| `kp:contracts:generate` | Запрос выпуска договора и его автоматических переходов |

Общие `read`, `write`, `admin` не предоставляют доступ к этому набору данных.
`kp:read` включает полный канонический JSON КП и структурный снимок выбранного
клиента, включая имеющиеся паспортные поля. Настройки, снимки, DOCX и задания
договора требуют scopes договоров. Выдача одного scope не добавляет остальные.
Чтение результата операции требует scope исходной команды, кроме того — того же
пользователя, канала и API-ключа.

Редактор использует такие же операции через `/api/kp`, с Auth.js-сессией,
актуальными ролями и проверкой `Origin` для изменений. Маршруты `/api/v1/kp` не
используют сессию редактора. В длительных операциях пользователь, ключ, scope,
ревизия источника и владение заданием повторно проверяются на границах ввода-вывода.
URL файлов всегда приватные и требуют повторной авторизации.

## Общие правила команд

JSON-команды отправляются с `Content-Type: application/json`, размер — до 2 MiB.
Неизвестные поля верхнего уровня отвергаются. ID берутся из ответов сервера.
`operationId` — UUID; один UUID соответствует одному точному телу команды.
Клиент сохраняет UUID и тело **до** отправки, сохраняет их при тайм-ауте и сначала
проверяет `GET /operations/{operationId}`. Повтор той же команды возвращает
подтверждённый прежний результат; изменённое тело с тем же UUID даёт 409.

Ответ чтения операции:

```json
{
  "operationId": "73b34bc8-f0f7-4b62-9607-ef0b6527fd34",
  "kind": "document.save",
  "result": { "id": "<КП>", "revision": 4, "state": { "items": [] } }
}
```

`result` — неизменяемый полный ответ исходной команды, сохранённый в той же
транзакции. Он не подменяется текущим состоянием сущности. Для экспорта это ACK
задания, а актуальное выполнение читается отдельно через `/jobs/{id}`. 404 от
`/operations` означает отсутствие подтверждённого результата, а не доказанный
откат незавершённого запроса. При неизвестном исходе сохраняйте исходный UUID.

`expectedRevision` — последняя прочитанная ревизия. Сервер блокирует проект и
проверяет её внутри транзакции. Конфликт не следует устранять слепым повтором с
новой ревизией: сначала прочитайте текущее КП и согласуйте состав изменений.

Каждое полное сохранение в «Лиде» приводит связанные коммерческие поля и активный
состав CRM к снимку КП, включая клиентский sidecar и цены. Ручные коммерческие
изменения CRM могут быть перезаписаны следующим сохранением. Данные производства
и финансовые факты сохраняются. Вне «Лида» и без действующего проекта
редактирование и восстановление запрещены. Экспорт принимает только сохранённые
ID и ревизии; произвольный `state` для PDF или договора не принимается.

## КП

Пути в таблицах относительны `/api/v1/kp`; `/api/kp` имеет ту же семантику.

| Метод и путь | Запрос / ответ |
| --- | --- |
| `GET /documents` | Параметры `q`, `cursor`, `limit` (1–100, по умолчанию 50); ответ `{documents,nextCursor}` |
| `POST /documents` | Создание; ответ `ProposalDocument` |
| `GET /documents/{id}` | Текущий `ProposalDocument` |
| `PUT /documents/{id}` | Полное сохранение; ответ канонический `ProposalDocument` |
| `GET /operations/{operationId}` | Подтверждённый неизменяемый результат команды |
| `GET /rates?currency=USD&date=2026-10-18` | `{fx}` — курс НБРБ на точную дату |

Создание:

```json
{
  "operationId": "73b34bc8-f0f7-4b62-9607-ef0b6527fd34",
  "clientId": "<ID существующего клиента>",
  "state": { "currency": "$", "order": { "date": "18.10.2026" }, "items": [] },
  "fx": { "currency": "USD", "rate": "3.2", "date": "2026-10-18", "source": "MANUAL" }
}
```

`clientId` необязателен при создании: используется проверенная служебная карточка
«Временный». Сервер не создаёт и не переименовывает её. `expectedNumber` —
необязательное целое ожидание следующего номера; несовпадение откатывает создание
без расходования номера. Номер распределяет сервер, значение скопированного
`state.order.number` не является резервированием номера. Пустой состав допустим.
Создание сразу с изображениями не допускается: создайте КП, загрузите медиа,
затем сохраните полное состояние с полученными ссылками.

Сохранение имеет то же тело с обязательным `expectedRevision`, без
`expectedNumber`. Допускается необязательный `proposalId`, только совпадающий с
путём. Не меняйте полученные `items[].id` при перестановке и редактировании;
для новых позиций ID может выдать сервер. Сервер возвращает каноническое состояние
с реальным номером и стабильными ID. Полный JSON позиции, включая блоки материалов,
сохраняется без проекции на урезанную модель изделия.

`ProposalDocument`:

```text
{ id, revision, state, createdAt, updatedAt, sourceDate,
  project: {id,number,stage} | null,
  client: {id,label} | null,
  canEdit: boolean, isArchive: boolean,
  fx: {currency,rate,date,source} | null }
```

`createdAt`/`updatedAt` — серверные ISO timestamps, `sourceDate` — дата исходного
КП `YYYY-MM-DD` или null. UI показывает время Москвы. `fx.rate` — строка Decimal,
BYN за единицу исходной валюты. Поддерживаются BYN, RUB, USD, EUR. Новый документ
без `fx` получает НБРБ на дату КП. Обычное сохранение без `fx` сохраняет прежний
курс; смена валюты требует явного нового курса. Ручной курс имеет source MANUAL.
Переданный новый курс NBRB проверяется по НБРБ вне транзакции. Недоступность
источника не заменяет курс сегодняшним или приблизительным.

Строка списка содержит `id,revision,project,client,createdAt,updatedAt,
currency,name,number,printedClientName`. Последние два поля — `string|null`;
при отсутствии сопоставления `client` и `project` могут быть null. Отдельного архивного режима нет. Для следующей страницы передавайте
`cursor=<nextCursor>` до `nextCursor=null`. Не используйте первую страницу как
полный список документов.

Строки услуг `state.delivery.items` не требуют `crmKind` и не требуют выбора
категории в редакторе. При отсутствии полного корректного сопоставления вся сумма
услуг после скидки и пересчёта учитывается в `Project.servicesTotal`, альтернативные
поля доставки/выгрузки/монтажа пустые. Полные существующие сопоставления остаются
совместимыми. Названия и разбивка строк в PDF сохраняются.

## Клиенты

`GET /clients?q=...&limit=30` возвращает `{clients:[{id,label,phone,address}]}`.
`GET /clients/{id}` возвращает
`{id,label,phone,address,isTemporary,snapshot}`. В `snapshot` входят `id,name,
lastName,middleName,phone,email,address,comment,passportNumber,passportIssuedBy`.
При выборе обычного клиента редактор сохраняет `state.client.crmId=id`,
`state.client.crmSnapshot=snapshot`; печатное имя хранится отдельно в
`state.client.name`. Это предотвращает повторение фамилии при разборе полного ФИО.
Служебный клиент не заполняется данными заказчика; при его выборе редактор
оставляет печатные поля пустыми.

Если при сохранении меняется `clientId`, сервер загружает свежий снимок выбранной
карточки. Для прежнего клиента снимок из КП авторитетен при полном сохранении;
неизвестные модели поля CRM не обнуляются. Необязательный верхний `clientSnapshot`
содержит только известные структурные поля без `id`, служебному клиенту он запрещён.

`POST /clients` создаёт обычную карточку: UUID `operationId`, обязательные `name`
и `phone`, необязательные строковые поля из перечисленного снимка без `id`.
Ответ совпадает с GET карточки. Существующая карточка клиента редактируется через
обычный интерфейс CRM; автоматическое открытие формы договора её не изменяет.

## Изображения

`POST /uploads` принимает multipart: `documentId`, `expectedRevision`,
`operationId`, `file` (оригинал), необязательный `optimized` (оптимизированное
изображение). Допускается явный alias `proposalId`; при наличии обоих они должны
совпадать. Путь `POST /documents/{id}/media` принимает те же поля без обязательного
ID в форме. Максимум 15 MiB на изображение, поддерживаются JPEG, PNG, WebP.
Тип и фактические байты проверяются. Ответ `{mediaId,reference}`, где
`reference="kp-media:<mediaId>"`. Загрузка не повышает ревизию КП.

Установите reference в `items[].image` или `image2` и выполните полное сохранение.
Произвольные URL, S3-ключи и data URLs не являются ссылками на медиа API.
Чтение: `GET /documents/{id}/media/{mediaId}?variant=optimized&scope=current`.
`variant=original|optimized`; `scope=uploaded|current|version`. Для version нужен
`versionId`. Uploaded доступен загрузившему пользователю в актуальном «Лиде»;
current и version проверяют фактические сохранённые ссылки. После годового срока
исходные медиа КП недоступны (410), независимые изображения изделий не удаляются.

## Версии и PDF

| Метод и путь | Результат |
| --- | --- |
| `GET /documents/{id}/versions` | `{versions:[Version]}` |
| `GET /documents/{id}/versions/{versionId}` | `{version:Version,document:ProposalDocument}`; document только для просмотра |
| `POST /documents/{id}/versions/{versionId}/restore` | `{operationId,expectedRevision}` → восстановленный текущий ProposalDocument |
| `POST /documents/{id}/pdf` | `{operationId,expectedRevision}` → Job |
| `GET /jobs/{id}` | Актуальный Job |
| `GET /artifacts/{id}/download` | Приватный PDF/DOCX; также поддерживается путь без `/download` |

`Version={id,revision,createdAt,trigger,isAccepted,pdfArtifactId}`. Trigger — PDF,
CONTRACT или IMPORT. `pdfArtifactId` позволяет сохранить файл и его контрольную
сумму при резервировании. Метаданные не содержат storage keys или публичных URL.
Версия создаётся только после успешного выпуска. Ошибка рендера не создаёт
готовый выпуск. Восстановление является отдельным полным сохранением в «Лиде».

```text
Job={id,state,result?,error?}
state=PENDING|PROCESSING|SUCCEEDED|FAILED|CANCELLED
result при успехе={artifactId,versionId?,fileName,mimeType,downloadUrl}
```

Начальный ответ PDF содержит `result:null,error:null`, ACK договора может содержать
только `id,state`. Опрос GET jobs возвращает полную актуальную форму. `downloadUrl`
строится транспортом как `/api/v1/kp/artifacts/{id}/download`; для сессионного API —
`/api/kp/...`. При повторном запросе принятого PDF может вернуться сразу SUCCEEDED
с `id="retained_<versionId>"`; тот же ID поддерживает GET jobs. Все ответы private,
no-store. История договора не очищается правилами версий КП.

## Договоры

В путях ниже `{documentId}` — **ID основного КП**, а не ID договора. `contractId`
в ответах — отдельный внутренний идентификатор договора.

| Метод и путь | Назначение |
| --- | --- |
| `GET /contracts/{documentId}` | Форма; alias `GET /contracts?documentId=...` |
| `PUT /contracts/{documentId}` | Сохранить настройки; alias PUT /contracts с documentId в теле |
| `GET /contracts/{documentId}/versions` | `{versions:[{id,createdAt,docxArtifactId,fileName}]}` |
| `GET /contracts/history?documentId=...` | Alias истории, в том числе импортированных DOCX |
| `POST /contracts/{documentId}/generate` | Выпустить сохранённый договор; alias POST /contract с documentId в теле |

Форма возвращает `{contractId,revision,settings,profiles,sourceRefs,clientDefaults,
clientBaseline,canEdit,versions}`. ClientDefaults заполняются из текущей карточки
выбранного CRM-клиента. `clientBaseline` — SHA256 для защиты от смены реквизитов
между открытием формы и сохранением/выпуском. Старые выпуски сохраняют свой снимок.

PUT принимает `{documentId?,operationId,expectedRevision,clientBaseline,
sourceRefs:[{proposalId,expectedRevision}],settings}`. В alias без ID в пути
`documentId` обязателен. Ответ
`{contractId,revision,sourceRefs,clientBaseline}` сохраняется как receipt.
POST generate принимает те же идентификаторы и проверки **без settings и state**;
настройки сначала сохраняются PUT. Ответ `{id,state:"PENDING"}` — неизменяемый ACK.
Внутренние источники/валюты/заказчик сверяются сервером, подмена снимков запрещена.

Успешный выпуск договора фиксирует версии всех включённых КП и их PDF, сохраняет
DOCX и одним согласованным завершением переводит проекты «Лид»/«Просчёт» в
«Договор», а черновики — в «Подготовку». Более поздние этапы не откатываются.
Настройки договора редактируются после блокировки КП. Для принятого КП с истёкшими
изображениями приложение строится из сохранённого PDF. Возврат в «Лид» снимает
принятие; изменённый текущий КП не подменяется старым PDF при недоступных изображениях.

## Ошибки и запуск обработчика

Ошибка имеет вид `{error:{code,message}}`. 400 — тело/параметры, 401 — авторизация,
403 — роль или scope, 404 — раздел/сущность/результат недоступны, 409 — ревизия,
этап или повтор UUID с другим телом, 410 — удалённый/истёкший источник, 413 — лимит,
503 — временная ошибка или ещё не подтверждённый результат. При 503 и неизвестном
исходе используйте GET operations с прежним UUID. Текст ответа не содержит SQL,
внутренних ошибок хранилища, ключей объектов, токенов и stack traces.

Произвольного ограничения числа страниц PDF/bundle, растеризации и договора нет.
По уточнению владельца поддерживаются файлы до `2147483647` байт; файлы свыше2ГБ
не требуются, тип размера в БД не меняется. Прежние пороги32/64/128МиБ и общий
срок генерации сняты. Основной PDF-путь передаёт manifest и assets потоково,
возвращает бинарный PDF и использует приватные дисковые файлы с проверкой SHA/размера.
Создание/полное сохранение КП принимает JSON до этой согласованной границы;
несвязанные JSON-команды сохраняют2МиБ. Проверки доступа, структуры, снимка,
контрольных сумм и продлеваемой lease обязательны. Ошибка/потеря lease не публикует результат.

Браузер и CLI продолжают ожидать **тот же job ID** до terminal state без общего
тайм-аута. Временный сетевой сбой повторяет GET с backoff, а не создаёт новый выпуск.
CLI может задать собственный явный timeout ожидания; это не отменяет серверное задание.
Скачивание начинается после полной проверки файла в приватном spool и идёт потоком;
закрытие соединения освобождает только принадлежащие ему временные ресурсы.

Долговечная очередь рендера запускается runtime-регистрацией только при обоих
`PERO_KP_ENABLED=1` и `PERO_KP_WORKER_ENABLED=1`; импорт модулей её не запускает.
Рендер требует отдельный ограниченный Chromium-процесс и приватный S3 CRM.
Ключ/пользователь повторно проверяются после длительных операций. Все включающие
действия, staging-приёмка и production-миграция согласуются отдельно по AGENTS.md.
