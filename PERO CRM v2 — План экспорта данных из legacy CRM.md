# PERO CRM v2 — план экспорта данных из legacy CRM «Бизнес в плюсе»

> Отдельный план этапа 0. Выполняется **до начала реализации** остальных трёх планов (базовая CRM, плагины).
> Цель: достать из legacy CRM **абсолютно всё** — каждую запись, каждую связь, каждый файл — **не изменив ни одного байта** в исходной системе, и сохранить результат в двух видах: **PostgreSQL-база** (схема `legacy_*` со связями) и **JSON/файловое хранилище** (сырой архив).
> Источник знаний о legacy: `legacy_crm_structure.md` (каталог таблиц, URL-паттерны, типы полей, объёмы).

---

## 1. Жёсткие требования

1. **Read-only.** Доступ к legacy — строго просмотр и выгрузка. Только GET-запросы (навигация, схемы, карточки, файлы). Единственное допустимое исключение — встроенный экспорт (POST формы экспорта), точечно, если GET-выгрузка неполна. Никаких изменений данных никогда.
2. **Полнота.** Все ~150 таблиц, включая скрытые и служебные; все срезы: **активные + архив + удалённые** (удалённые — с флагом, для истории). Ни одной потерянной записи.
3. **Связи по ID, не по именам.** Главная ошибка v1 — сопоставление по именам. Каждая запись выгружается со своим ID и с **ID всех связанных записей** (из HTML вытаскиваем `href`/`data-*` с `table=`/`line=`), а не только с отображаемыми подписями.
4. **Файлы.** Каждое вложение скачивается с привязкой `table_id + record_id + field_id → файл` и контрольной суммой.
5. **Воспроизводимость и верификация.** Пайплайн можно перезапустить с чекпоинта; в конце — отчёт верификации, где каждая таблица «зелёная».
6. **Бережность к живым пользователям.** В legacy работают ~17 человек: троттлинг 1–2 запроса/сек, тяжёлые прогоны — в нерабочие часы и ночью.

## 2. Доступ

Учётная запись **`reviewer` — с правом просмотра всех сущностей и встроенного экспорта, без изменений и удалений** (создана владельцем). Этого достаточно для всего пайплайна: схемы (`get_value.php?show_fields`), гриды, карточки, срезы, файлы, экспорт.

**Предстартовый чек-лист (ручная проверка ~10 минут до запуска):**

1. **Поля, скрытые на уровне поля** («Оклад», «Бонус %», «Плановая ежедн. выработка» у сотрудников, table 46): в ClientBase поле может быть скрыто от всех групп независимо от прав на таблицу. Если не видны — фиксируем «не выгружено, восстанавливается вручную» (всего 17 сотрудников) либо по договорённости временно включаем видимость поля (настройка, не данные).
2. **Срезы `&archive` и `&deleted`** — открываются, счётчики сходятся (просмотр удалённых — отдельное право).
3. **Скачивание файлов** через `open_file.php` — право просмотра не всегда включает скачивание вложений.
4. **Скрытые таблицы по прямому URL** (2481, 2801 и др.) — доступ есть.
5. **Отчёты** (`report.php?id=261`) — ранее закрыт; не блокер (восстанавливается из таблиц 631/641/1141), но проверить.
6. **Полнота встроенного экспорта** на тестовой таблице: выгружаются ли вычисляемые поля и связи **в виде ID, а не подписей** (в v1 экспорт давал 83–88% пустых «Этап»/«Статус» — поэтому экспорт у нас только fallback).
7. **Сессии:** если ClientBase держит одну сессию на пользователя — выгрузка только ночью, в один поток, с автоперелогином.

Результаты чек-листа заносятся в отчёт верификации (что выгружено / что зафиксировано недоступным и почему).

## 3. Архитектура пайплайна

Скрипты на Python 3.12 (httpx + parsel/BeautifulSoup + psycopg), в репозитории `legacy_export/`. Каждый шаг — отдельный скрипт с чекпоинтами (прогресс в SQLite/JSON), любой шаг перезапускаем без потери уже сделанного.

```
01_discover_tables  → 02_dump_schemas  → 03_build_pg_schema
     → 04_dump_data  → 05_dump_files   → 06_load_postgres
     → 07_verify     → отчёт
```

## 4. Шаг 1. Инвентаризация таблиц (`01_discover_tables`)

Формируем полный список ID таблиц:

- **Сид-список** из `legacy_crm_structure.md` (все ID из карт меню + скрытые: 2481, 2661, 2671, 2681, 2801, 3081, 3091, 50 и др.).
- **Обход связей:** для каждой таблицы забираем JSON-схему (`get_value.php?&show_fields&table=N&line=any`); поля типа `связь` содержат `type_value = "<table_id>|<display_field_id>|…"` — добавляем цели в очередь. Рекурсивно до замыкания графа.
- **Контроль полноты:** сверяемся с картой меню; таблицы, найденные только через связи, помечаем `hidden: true`.

**Результат:** `tables_index.json` — все таблицы с ID, названием, источником обнаружения, счётчиком записей из UI.

## 5. Шаг 2. Схема данных (`02_dump_schemas`)

Для каждой таблицы сохраняем сырой ответ `show_fields` в `schema/raw/<table>.json` и собираем единый **`legacy_schema.json`**:

```json
{
  "241": {
    "name": "Заявки", "records_total": 630,
    "fields": {
      "49841": {"name": "Статус", "type": "связь", "target_table": 2481, "display_field": 56671},
      "4651":  {"name": "Категория статуса", "type": "список",
                "values": ["заявка","консультация","просчет","замер","договор","отказ"]}
    }
  }
}
```

Плюс **`relations.json`** — граф связей «таблица.поле → таблица» (машиночитаемый, из него генерируются внешние ключи PG и Graphviz-карта для людей). Особо фиксируем: этапы заявки — справочник 2481 (6 статусов); этапы заказа — поле 56671 таблицы 181 → справочник 2801 + даты этапов (поля 9900…9830, 56691); вычисляемые поля («Категория статуса», «old status», даты этапов) выгружаем карточками, т.к. в CSV-экспорте v1 они были пусты в 83–88% случаев.

## 6. Шаг 3. PostgreSQL-схема `legacy_*` (`03_build_pg_schema`)

Из `legacy_schema.json` генерируется DDL:

- Одна PG-таблица на legacy-таблицу: `legacy_t241`, `legacy_t47`, … Первичный ключ — `legacy_id` (ID записи из ClientBase). Все поля исходной таблицы — колонками с типами по маппингу (`число→numeric`, `дата/время→timestamp`, `текст→text`, `список→text`, `связь→integer`, `пользователь→integer`, `файл/изображение→text` — имя файла).
- Плюс служебные колонки в каждой таблице: `_slice` (active/archive/deleted), `_raw jsonb` (полная сырая строка как страховка — ничего не теряется даже если маппинг ошибочен), `_exported_at`.
- Таблица связей-метаданных `legacy_relations` (from_table, from_field, to_table) и `legacy_files` (table, record_id, field_id, path, sha256, size).
- Индексы по всем колонкам-связям — для будущих join при миграции в v2.

Итог: **полная схема данных legacy со связями живёт в PostgreSQL**, а `legacy_schema.json` + `relations.json` дают тот же контент в JSON-виде.

## 7. Шаг 4. Выгрузка данных (`04_dump_data`)

Для каждой таблицы, для каждого среза (`active`, `archive`, `deleted`, `all`):

1. **Постраничный обход** `fields.php?table=N&page=K&<срез>`; парсим грид `.fields__table`: значения колонок + **ID записей и ID связей** (атрибуты/href `line=`, `table=`). Счётчик «Всего строк: X из Y» сверяется с прогрессом.
2. **Скрытые колонки и вычисляемые поля** докачиваем карточками `view_line2.php?table=N&line=M` (инпуты `value<field_id>`) — для таблиц, где грид неполон (Заявки 241, Задания 47, Журнал ДС 300, Сотрудники 46, Работы 1141 и др. ключевые). Оптимизация: карточки качаем только для таблиц из «списка неполных», остальным хватает грида.
3. **Встроенный экспорт** (POST `op_sel=export`, `all_needed_records`) — только как fallback, если по гриду+карточкам счётчик не сходится.
4. Каждая строка пишется в `data/raw/<table>/<slice>.jsonl` (JSONL, append-only) + чекпоинт (последняя страница). Прерывание → перезапуск с места остановки.

Известные объёмы для планирования (≈211k записей): Отгрузки 58 624, Установка цен 42 177, Зарплата пр-во 9 377, Детализация ЗП 8 734, Коммуникации 8 725, Работы в заказе 6 362, Журнал ДС 4 084, Учёт движения 2 915, Лента 2 253, История изменений 2 132, План 1 912, Монтажи 1 691, Расходы 1 621, Задания 1 620 и т.д. При 1–2 зап/сек полный прогон — несколько ночей; расписание — вне рабочих часов офиса.

## 8. Шаг 5. Файлы и вложения (`05_dump_files`)

- Источники имён файлов: поля типа `файл/изображение` в гридах и карточках.
- Скачивание: `open_file.php?table=N&field=F&line=M&file=<имя>`.
- Раскладка: `files/<table_id>/<record_id>/<оригинальное_имя>` (конфликты имён — суффикс).
- Каждый файл: sha256, размер, запись в `manifest.json` и в PG-таблицу `legacy_files`. Битые/недоступные — в отчёт, не пропускаем молча.

## 9. Шаг 6. Загрузка в PostgreSQL (`06_load_postgres`)

JSONL → COPY в `legacy_t*`-таблицы (ID-first, связи — целыми ID). Срез и сырость — в `_slice`/`_raw`. Повторная загрузка идемпотентна (`ON CONFLICT (legacy_id) DO NOTHING` или пересоздание таблицы). Результат: **готовая PG-база `pero_legacy`** (дамп `pero_legacy.dump` прилагается к результату).

## 10. Шаг 7. Верификация (`07_verify`)

По каждой таблице:

1. **Счётчики:** «число записей в пагинации UI» == «выгружено в JSONL» == «загружено в PG». Расхождение → докачка; неустранимое — в отчёт с причиной.
2. **Checksums:** sha256 каждого файла на диске == manifest == `legacy_files`.
3. **Выборочная сверка:** N=5 случайных записей на таблицу — значения полей в PG == значения в UI карточки (автоматическое сравнение с скрин-парсером).
4. **Связи:** каждая колонка-связь указывает на существующий `legacy_id` в целевой таблице; висячие связи — в отчёт (в живой базе бывают, фиксируем, не «чиним»).

**Итоговый отчёт `verification_report.md`:** таблица × записей × связей × файлов, все галочки. Критерий завершения этапа: весь отчёт зелёный (или каждое отклонение документировано и объяснено).

## 11. Результаты этапа (артефакты)

| Артефакт | Формат |
|---|---|
| Индекс таблиц | `tables_index.json` |
| Схема данных + граф связей | `legacy_schema.json`, `relations.json` (+ Graphviz-карта для людей) |
| **База PostgreSQL** | схема `legacy_*` + дамп `pero_legacy.dump` |
| Сырые данные | `data/raw/**.jsonl` |
| Файлы | `files/<table>/<record>/<имя>` |
| Контрольные суммы | `manifest.json` |
| Отчёт верификации | `verification_report.md` |

Хранение: рабочая копия на машине разработчика + копия на внешний носитель (пока NAS не развёрнут). Сырые JSONL/файлы не трогаем — «холодный» архив; поверх него строится всё остальное.

## 12. Критерии приёмки этапа 0

- `tables_index.json` покрывает 100% таблиц (меню + связи); расхождений со снятой ранее структурой нет.
- `legacy_schema.json` и PG-схема описывают все таблицы и все связи.
- Счётчики записей сходятся по всем таблицам и срезам (= 0 необъяснённых расхождений).
- Все файлы на диске, checksums сходятся.
- Выборочная сверка зелёная; отчёт подписан.

**Только после этого начинаются фазы 1+ остальных планов.**

## 13. Риски

| Риск | Снижение |
|---|---|
| Скрытые/вычисляемые поля пусты в гриде (ошибка v1) | Докачка карточками `view_line2.php` для «неполных» таблиц; сверка счётчиков |
| Связи потеряны из-за сопоставления по именам | Только ID из href/data-атрибутов; колонки-связи хранят integer ID |
| Нагрузка на живую CRM | 1–2 зап/сек, ночные прогоны, только GET |
| Ограничения учётки reviewer | Выгрузка под админской учёткой (read-only договорённость сохраняется) |
| Обрыв выгрузки на 42k-таблице | Чекпоинты по страницам, JSONL append, идемпотентная загрузка |
| Файлы с одинаковыми именами/битые ссылки | Суффиксы имён; битые — в отчёт, не молча |
