# Выжимка беседы: CRM, процессы и автоматизация (запись от 17.07.2026)

> Источник: частичная запись беседы руководителя с сотрудниками (~57 мин). Транскрибация машинная, отдельные слова могут быть искажены; сомнительные места помечены *(уточнить)*.

---

## 1. Контекст и участники

Компания — производство корпусной мебели на заказ (кухни, шкафы, МДФ-панели, покраска). Упоминаются:

- **Руководитель/директор** — ведущий беседы, ставит задачи, определяет роли и доступы в CRM.
- **Рома** — заключает договоры, заносит первичное описание заказа в CRM, согласовывает запуск проектов в производство (ключевая точка согласования).
- **Веня** — менеджер; чертит только в SketchUp, Базис-Мебельщик не знает; занимается «мелочами»: спорнели *(уточнить)*, стёкла, зеркала.
- **Инженер-конструктор** (основной собеседник по техчасти) — работает в Базис-Мебельщик, ведёт собственную библиотеку модулей, готовит проекты к производству.
- **Алексей** — конструктор, чертит в Базисе, владеет полной информацией по проекту (квадратура, длины, кромки).
- **Коля** — сейчас заполняет работы/задачи и их стоимость по прайсам (ранее это делал мастер производства).
- **Юра, Пашка** — упоминаются в контексте производства/согласований.
- **IT-специалист** (автор записи) — будет строить CRM, бота и автоматизацию.

## 3. CRM: концепция и требования

### 3.1. Общий подход
- Сначала — сама CRM (структура данных), затем — **Telegram-бот** для внесения информации. Бот сделать легко, важнее правильная структура.
- Главный принцип: **внесение и перенос информации должны быть максимально простыми**. «Чем проще придумаем, тем лучше». Структуру можно смело упрощать.
- Работа — прежде всего **с телефона через бота в Telegram** (по аналогии с тем, как сейчас сотрудники скидывают отчёты/фото).
- Аналитику на первом этапе **убрать** — добавлять функции постепенно, по факту потребности.

### 3.2. Роли и права доступа (4 типа)
| Роль | Кто | Права |
|------|-----|-------|
| **Админ / директор** | руководитель | Полный доступ |
| **Менеджер** | Веня | Всё, кроме финансовой информации: может всё просматривать и изменять, заполняет данные, но финансовые отчёты/итоги ему не видны (нет нужды) |
| **Работник производства** | цех | Ничего не заполняет; только выполняет задачи, назначенные менеджером или директором |
| **Монтажник** | монтаж | Как работник + может добавлять в проект задачи (закреплять задачу) |

### 3.3. Структура данных
- Ядро системы — **Проект** (основная сущность).
- Иерархия: **Проект → Работы → Задачи** (пример: работа «изготовить шкаф» → задачи внутри неё).
- Задачи заполняются со **стоимостью по прайсам**; прайсы уже существуют — их нужно **перенести** в новую систему (сейчас заполняет Коля, раньше — мастер производства).
- Этапы заказа: упоминается **~8 этапов/видов работ**: 1) заключён договор → 2) передано менеджеру → 3) инженер → 4) … → производство → монтаж/гарантия *(полный список в записи не проговорён — уточнить)*. Ответственный инженер по завершении подготовки меняет статус и передаёт проект «в работу производству».

## 4. Текущий процесс (как есть сейчас)

1. **Рома заключает договор** и вносит первичное описание в CRM (например: «кухня 10 на 2600, высоты…»). Пустой проект с номером может создать Рома или Веня.
2. Проект заполняется: техника, материалы, фурнитура, цвет, дополнения.
3. **Инженер** получает проект: видит его в CRM (проект виден только инженеру и выше), прорабатывает конструкцию в **Базис-Мебельщик**, готовит данные для цеха.
4. Информация для производства сейчас передаётся частично вручную: инженер конвертирует файл из Базиса в **SketchUp**, чтобы «пацанам» было удобно — в SketchUp можно ставить комментарии и стрелки («эту панель клеить в такой-то цвет, здесь не клеить»).
5. Чертёж/документация хранится локально у инженера; файлы проектов сохраняются — через год можно открыть файл и отдать любую деталь на ЧПУ «один в один».
6. Запуск в производство — только после личного согласования с Ромой.

## 5. Выявленные проблемы (боли)

1. **Дублирование работы дизайнер → инженер.** Дизайнер делает 3D-модель и рендер для клиента → показывает заказчику → потом инженер чертит **ту же самую 3D-модель заново**, уже в Базисе. «Мартышкин труд»: PDF с рендером инженеру не нужен, нужны конкретные размеры и техника.
2. **Ручное внесение информации в CRM.** Данные из проекта (размеры, материалы, расход, цены) переносятся вручную — хотя в файле Базиса всё уже есть (квадратура, длины, кромки).
3. **Разнобой в инструментах.** Веня чертит только в SketchUp (Базиса «никогда не касался») — при том, что часть работ (мебель) должна идти через Базис. Пожелание: все проектировщики работают в одном инструменте.
4. **Бутылочное горлышко — согласования с Ромой.** «Без меня даже не начинать»: проект (пример — спортзал) висит месяц+, производство простаивает, инженер не может запустить работу; при этом само согласование занимает 15 минут – 2 часа.
5. **Тяжёлые клиенты и бесконечные правки.** Итерации правок приходят по выходным («у них на каждой выходной — прозванивание»), десятки уточнений по кухне (ручки, вытяжка, «волшебный уголок», фасады); до этого был аналогичный тяжёлый клиент — общение по Zoom с демонстрацией экрана.
6. **Ценообразование зависит от объёма.** Прайсы местами завышены из-за отсутствия объёма: при гарантированных 30 м²/день покраски готовы работать по 9 руб./м² *(по панелям)*; по краске в целом — «нормально, выше не сделаешь».
7. **Кривой перенос из старой системы.** При миграции данных часть информации потерялась: у заказов пустые поля «этап», данные перенесены некорректно — нужно пересмотреть, как этапы обозначены в старой системе.

## 6. Идеи и решения по автоматизации

1. **Импорт проекта в CRM из файла Базиса.** Файл проекта «скармливается» CRM → автоматически заполняются работы, расход материалов, цены по прайсам, количество (МДФ и т.д.). Ручное заполнение исчезает. Скетчап-файлы тоже не проблема — конвертируются.
2. **Перенос 3D-модели от дизайнера напрямую в Базис** вместо перечерчивания: брать у дизайнера файл проекта (а не PDF). Базис открывает практически все 3D-форматы; ограничение — фигурные детали (волны) конвертируются как прямые, их придётся повторять вручную либо доработать скриптом. Нужно изменить коммуникацию с дизайнерами (Рома считает, что «будет сложно» — тема на обсуждение).
3. **Скрипты в Базисе для ускорения проектирования.** У инженера есть библиотека заготовленных модулей (все виды ящиков, любые размеры, с фурнитурой и присадкой, ограничения по ширине ~1030 мм, авторазбиение фасадов на равные части). Идея: на основе рендера **скриптом автоматически заполнять пространство** готовыми модулями → инженер только подправляет индивидуальные места. Требует тестирования.
4. **API/MCP для Базиса** — маловероятно: публичного API у Базис-Мебельщик, скорее всего, нет, максимум — редактор скриптов. Источник скриптов и готовых решений — профильные Telegram-группы по скриптам Базиса (IT-специалист попросил скинуть ссылки).
5. **Нейрогенерация демо-видео для клиента.** Рендер проекта + референс-видео (например, «волшебный уголок») → нейросеть генерирует 5-секундное видео, как фасад/механизм открывается. Клиент видит «как это будет», без доработки проекта. Качество не критично — важна демонстрация принципа.
6. **Онлайн-просмотрщик 3D для клиентов.** Найдена новая бесплатная программа: файл из Базиса загружается в облако → по ссылке клиент на телефоне «пощёлкивает» кухню, смотрит, как всё открывается. Пока сыро и бесплатно (монетизация ожидается позже). Идея — реализовать подобное у себя / использовать для демонстраций. *(Название распознано неуверенно — «Базис Лоблок»? — уточнить.)*
7. **Единый инструмент проектирования.** Постепенно перевести всех на Базис (Веню — обучить или перераспределить задачи), чтобы не было параллельных форматов.

## 7. Ценные детали для разработки CRM

- Проект поступает в CRM **на этапе заключения договора** (Рома), наполняется по мере движения по этапам; видимость проекта зависит от роли (цех не видит проект, пока он у инженера).
- Инженеру от клиента/менеджера нужны только: **конкретные размеры + список техники** (духовой шкаф, варочная панель, холодильник, морозильник, винный шкаф, вытяжка и т.п.) с монтажными требованиями (проёмы, зазоры, тип крепления фасада — жёсткое/плавающее, тип открывания посудомойки — от этого зависит цоколь).
- Файлы проектов должны **храниться в системе** (сейчас — локально у инженера): через год по файлу можно воспроизвести любую деталь на ЧПУ.
- У инженера — собственная библиотека модулей, сделанная вручную за 1–2 года (нижние/верхние корпуса, пеналы под холодильники разных размеров, с антресолями и пр.). Готовые библиотеки на рынке — только платные.
- Пример норм: нагрузка на направляющие ящиков 30–65 кг; ящики шире ~1 м не делают (прогиб, нагрузка на крепления) — разбивают на две части.
