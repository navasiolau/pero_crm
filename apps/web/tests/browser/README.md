# Мобильная браузерная проверка

Сервер запускает ответственный за локальное окружение с существующей локальной БД владельца. В этом наборе нет seed, reset, schema push или автоматического webServer. Production не используется. Staging сохраняет штатную самообновляющуюся БД.

Перед запуском явно задаются:

- `CRM_E2E_BASE_URL` — URL проверяемого локального runtime (по умолчанию `http://localhost:3104`); для staging требуется также `CRM_E2E_STAGING=1` после проверки целевого окружения.
- `CRM_E2E_<ROLE>_EMAIL` и `CRM_E2E_<ROLE>_PASSWORD` для ролей MANAGER, WORKER, ADMIN, ENGINEER, COMBINED, MOUNTER. Общий `CRM_E2E_PASSWORD` поддерживается только как fallback; пароли не хранятся в репозитории.
- `CRM_E2E_PROJECT_PATH` — существующий проект в BYN для просмотра финансовой формы, например `/projects/<id>`.
- `CRM_E2E_PRODUCT_PATH` — существующее изделие для просмотра/открытия редактора, например `/products/<номер>`.

Для worker-сценария нужен существующий доступный сотруднику незавершённый task с возможностью добавить фото. В списках должна быть вторая страница. Если подходящих данных/аккаунтов нет, это отмечается как отсутствие условий приёмки; автоматически создавать их в рабочей локальной или staging-БД нельзя.

Команда из `apps/web`: `pnpm exec playwright test`. Набор проверяет 360×800, 390×844 и 1440×900. Скриншоты сохраняются в gitignored `test-results`; их нужно лично просмотреть, автоматические размеры не заменяют визуальную приёмку.

Для согласованного existing-local режима используется `pnpm exec tsx tests/browser/mobile-local.ts serve` (строго localhost:3104): helper проверяет точный существующий Docker container/volume и loopback5433, читает пароль только в память и выбирает существующих активных пользователей/сущности через read-only соединение. В отдельном терминале задаётся `CRM_E2E_LOCAL_SIGNED=1` и запускается Playwright. Это тестовые signed JWT под случайным локальным AUTH_SECRET с настоящими user id/roles/sessionVersion, а не доказательство входа с паролем. Состояние с тестовым секретом хранится в gitignored `.playwright-mcp/mobile-local-state.json` и удаляется при остановке runtime; секреты/cookies не выводить.

После браузера: `pnpm exec tsx tests/browser/mobile-local.ts restore-prefs` возвращает только собственные `my.view` WORKER/MOUNTER по compare-and-swap и сравнивает counts/hash 13 бизнес-таблиц со снимком до запуска. `verify-data` выполняет только сравнение. Другие данные не меняются. При отсутствии активной задачи worker-сценарий явно skipped; пустой рабочий экран всё равно снимается. Runtime оставляется ответственному агенту для review.

Тесты открывают формы, заполняют поля, но не сохраняют проекты, изделия, платежи, статусы и файлы. Выбор вида и фильтров может сохранить пользовательские предпочтения через штатный UI; используемые аккаунты и допустимость таких изменений согласует ответственный за окружение. Само приложение при старте синхронизирует реестр плагинов: это также необходимо учесть до запуска.

## Отдельно разрешённый owned-action прогон

Для проверки отсутствующих исходно активных задач владелец 28.09.2026 отдельно разрешил ровно один помеченный Project и две Task в существующей local DB. Этот режим не включён автоматически: `mobile-owned-fixtures.ts prepare` пишет UUID manifest до INSERT, `CRM_E2E_OWNED=1` разрешает сценарии `mobile-owned-actions.spec.ts` только на manifest tasks. Используются существующие WORKER/MOUNTER/client/manager, workId=null, отрицательный numberInt, никаких новых пользователей/касс/работ.

Перед timer-действиями проверяются чужие активные/нулевые записи времени и неизменный plugin set. Фото идёт только в local uploads. После UI нужно `mobile-owned-fixtures.ts capture`, затем `cleanup`: exact-ID/ownership/hash/realpath checks и транзакционная сверка 18 таблиц. Завершающее `mobile-local.ts restore-prefs` возвращает собственные настройки. Повторное prepare не перезаписывает manifest; новый прогон с новыми записями требует отдельного разрешения владельца. Staging/production этим helper недоступны.
