# Приёмка сохранения фильтров

Сервер запускает оркестратор на существующей локальной БД владельца после проверки подключения. Тест не запускает сервер, не подключается к БД напрямую, не создаёт пользователей/сущности, не выполняет seed/reset/schema push. Production запрещён. Staging проверяется отдельно на штатной самообновляющейся БД.

Перед запуском согласовать использование существующих аккаунтов: тест меняет только их настройки списков через UI. Для проверки изоляции нужны два разных аккаунта с доступом к спискам. Начальное состояние их фильтров следует сохранить и после приёмки вернуть через UI.

Переменные окружения (пароли в Git не сохраняются):

- `CRM_E2E_BASE_URL` — локальный runtime, по умолчанию `http://localhost:3103`; staging допускается только для `staging-crm.peromebel.by` с `CRM_E2E_STAGING=1`.
- `CRM_E2E_MANAGER_EMAIL`, `CRM_E2E_MANAGER_PASSWORD`, `CRM_E2E_OTHER_EMAIL`, `CRM_E2E_OTHER_PASSWORD`. Общий `CRM_E2E_PASSWORD` допустим как fallback.
- `CRM_E2E_PROJECT_PATH`, `CRM_E2E_PRODUCT_PATH` — существующие доступные карточки.
- `CRM_E2E_ENGINEER_ID` — существующий инженер, доступный в фильтре.
- `CRM_E2E_PRODUCT_SEARCH` — реальный поисковый текст для доступного изделия.
- Необязательные `CRM_E2E_PROJECTS_QUERY`/`CRM_E2E_PRODUCTS_QUERY` — полный набор фильтров для конкретных имеющихся данных. Нужны минимум 11 совпадений для второй страницы; по умолчанию используются все статусы, сортировка названия и размер страницы 10.

Из `apps/web`: `pnpm exec playwright test --config tests/list-filters.playwright.config.ts`.

Артефакты сохраняются вне приложения в gitignored `.playwright-mcp/list-filters`. Для review сохраняются все traces; их содержимое не включать в Git.

Локальный helper `tests/existing-local-list-acceptance.ts` запускается только по поручению оркестратора с явно заданным `CRM_E2E_LOCAL_CONTAINER_ID` существующего `pero_crm_pg`. Он проверяет exact ID/volume/loopback5433/DB/роль, читает пароль только в память, выбирает два существующих пользователя и создаёт подписанные временные local JWT (без смены паролей/учёток). Перед UI сохраняет наличие и точные значения четырёх `UserPreference`, после него выполняет только CAS-восстановление доказанных собственных ответами записей. При конфликте — STOP и отчёт, без перезаписи.

Для browser profile helper передаёт `CRM_E2E_MANAGER_STATE`/`CRM_E2E_OTHER_STATE` вместо входа паролем и `CRM_E2E_OWN_WRITES` для приватного журнала сетевых ответов. Runtime создаётся с отдельным secret, S3 отключён; рабочие env-файлы запрещены. Приложение при запуске синхронизирует реестр плагинов, это действие учитывается оркестратором до разрешения запуска.

Первый approved-прогон на существующей локальной БД: 5/5 сценариев зелёные, counts бизнес-таблиц неизменны. Два исходных CAS-конфликта оставлены как default `view=kanban` по решению root; побайтовый возврат первого прогона не утверждается. Новый baseline включает эти значения.

Последняя версия кода прошла все восемь сценариев в двух прогонах (базовые пять + три новых проверки). После каждого нового прогона **4/4 prefs возвращены точным CAS**, бизнес-счётчики совпали, runtime остановлен. Последний helper result — `passed`, `restoreConflicts=[]`. Подробности и пути traces — в OpenSpec evidence.

Для прицельного TDD-прогона helper принимает необязательный `CRM_E2E_GREP`; по умолчанию запускаются все восемь тестов. Каждому запуску выделяется собственная gitignored папка с checkpoint, журналами запросов/ответов, traces и результатом, чтобы следующий прогон не затёр evidence.
