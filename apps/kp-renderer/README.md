# Приватный renderer КП

Node 22, `puppeteer-core@24.43.1`, `@sparticuz/chromium@141.0.0`, фиксированные WOFF2 исходного шаблона и Poppler. Процесс не читает БД/S3 и не публикует выпуски. Его вход — сохранённый сервером снимок с `templateHash` и проверенными байтами `kp-media:<id>`; внешние URL отклоняются до запуска Chromium.

`POST /v1/render` требует `x-pero-renderer-key` из отдельного `PERO_KP_RENDERER_SECRET` длиной не менее 32 символов. Секрет не является пользовательским API-ключом и не передаётся браузеру. `GET /health` также требует этот секрет. Клиент CRM находится в `apps/web/src/server/kp/renderer-client.ts`; типы — `packages/kp-template/transport.d.ts`.

Поддерживаются PDF (A4,794×1123,фон,поля0), `bundle` (PDF при DPR1 и исходные DPR2 screenshot-страницы одного page/context), `rasterize` (PNG1588×2246) и `docx` (исходный генератор договора). Основной PDF-путь — потоковый `application/vnd.pero.kp-pdf.v1`: u32BE длина manifest, UTF8 manifest и точные бинарные assets. HTTP возвращает application/pdf с Content-Length и заголовками x-pero-template-hash/x-pero-render-page-count/x-pero-content-sha256. Legacy JSON режимы сохраняются для совместимости; свежий договор использует bundle, после очистки изображений — сохранённый PDF.

Произвольных page/count/time потолков нет. По уточнению владельца файлы свыше2ГБ не нужны: размер2147483647 байт соответствует существующему Int БД. Прежние32/64/128МиБ и deadlines15/30/60/90/120с сняты. Сохраняются положительные целые счётчики, точные byte/SHA/array/path проверки, общий секрет и закрытая сеть. Родитель пишет assets в принадлежащий UUID spool, worker создаёт PDF через createPDFStream, IPC содержит только метаданные. Отключение HTTP/потеря lease отменяет queued work либо завершает принадлежащий worker/browser; слот освобождается после завершения. Оформление и расчёт страниц не меняются.

DOCX собирается тем же `docx@9.6.1` и неизменным шаблоном вне web-процесса. Один worker за раз, очередь до четырёх, крайний срок 60 секунд; ограничения тела, снимка, изображений, PDF/DOCX и числа страниц заданы в `validation.cjs`. Ошибка не является успешным выпуском.

Пример локального запуска без контейнера: установить зависимости frozen lockfile, задать отдельный приватный секрет и выполнить `pnpm --filter @pero/kp-renderer start`. На Windows для проверки указываются существующие `PERO_KP_CHROMIUM_PATH`, `PERO_KP_PDFINFO_PATH` и `PERO_KP_PDFTOPPM_PATH`. Это диагностический override; production использует упакованный Chromium 141. Значения секретов не помещаются в команды, логи или Git.

Dockerfile запускается непривилегированным пользователем. Overlay не публикует порт, сохраняет internal network/read-only root/cap-drop/no-new-privileges. PDF/assets/browser scratch находятся в приватном UUID на отдельном дисковом томе `/spool` без квоты веса; `/tmp`512МиБ остаётся только для закреплённого Chromium. Custom heap384МиБ и CPU/RAM/PID-потолки сняты; oom_score_adj1000 отдаёт приоритет сохранению CRM/БД при исчерпании физических ресурсов. В WEB приватный spool — disk-backed `/tmp`. Применение профиля идёт после CI/staging по точным digest; БД и бизнес-тома не изменяются.

В `.github/workflows/ci-cd.yml` job `kp-renderer-tests` разрешает `node:22-bookworm-slim` в immutable digest, собирает `renderer-oci` и `renderer-runtime` одним Buildx graph с frozen lockfile, Chromium141.0.0/Puppeteer24.43.1. Labels фиксируют Git SHA, run/attempt, base image и source/font/template hashes. `ci/pipeline.mjs test` проверяет весь OCI-граф/provenance и равенство Docker config/layers, затем запускает именно эту проекцию по image ID с network=none/read-only/1536 MiB/CPU1/PID128/tmpfs512 MiB. `ci/smoke.cjs` использует настоящий private HTTP, подтверждает Chromium141, сравнивает все PDF/PNG страницы с исходником и DOCX из двух КП со всеми исходными ZIP entries, проверяет границы и отказ без секрета. OCI и receipt загружаются artifact только после успеха.

`native-tests` строит web только после успешного `kp-renderer-tests`: его OCI label `pero.kp.renderer-index` содержит digest именно испытанного renderer. Оба образа фиксируют protocol1, одинаковые revision/run/attempt и source/font/template hashes. `build-push` и `build-push-bot` требуют success всей unit matrix, native-tests и kp-renderer-tests. Существующий promotion через regctl переносит тот же OCI index вместе с provenance без пересборки в `ghcr.io/navasiolau/pero_kp_renderer:sha-<Git SHA>` и branch tag, повторно проверяя digest. После подтверждения обоих registry digest и их label bindings создаётся artifact `kp-release-<run>-<attempt>-<Git SHA>`: `release.json`, `kp-images.env`, `kp-images.override.json`, `docker-compose.kp.yml`. Это аудируемая пара `repository@sha256:…` для приёмки/воспроизведения; флаг и секреты в packet отсутствуют.

Component cohorts стартуют параллельно renderer. Backend вынесен в отдельный `unit-tests-backend`, который вместе с native ждёт renderer; общее содержимое шагов переиспользуется YAML alias без merge keys. Display name `unit-tests (backend)` сохранён для строгих artifact receipts. Поэтому renderer не расходует backend types budget: poll18 минут, consumer20 минут, job25 минут. Оба publication jobs отдельно требуют component matrix и backend job. Native публикует types до ожидания backend bot-dist, сохраняя прежний порядок обмена без цикла.

Штатный `deploy/watch-crm.py` сохраняет автоматический staging/main GitFlow. При `PERO_KP_ENABLED=0` используется прежний web-only путь, даже если файл KP overlay уже установлен. Для opt-in после сквозной приёмки один раз устанавливаются reviewed helper/`docker-compose.kp.yml` и приватный секрет, затем явно включается флаг. Watcher добавляет профиль, сохраняя стандартный override и прежние W07/lock/расписания. Web branch tag служит discovery; renderer берётся только из его immutable OCI label. Перед `up` проверяются revision/run/attempt/protocol/source/font/template обеих картинок, private resource caps, отсутствие container/config/tag drift и прежний DB container/mounts. Actual `up` получает только resolved digest refs через собственный временный JSON override, без pull/build/зависимостей.

Если второй образ ещё не опубликован, running services не меняются. Ошибка здоровья любой половины возвращает обе на прежние локальные image IDs; health rollback и postcheck входят в прежний200-секундный deadline под W07. При первой активации неудачный вновь созданный renderer удаляется только после проверки точного ID/образа/owner и отсутствия постоянных mounts; прежний web восстанавливается. БД не откатывается и её том не изменяется watcher. Временный override удаляется по точному собственному пути; постоянный pin не остаётся, следующие успешные публикации снова обновляются автоматически. При guard mismatch автоисправления нет. Момент несовпадения процессов дополнительно закрыт проверкой templateHash в RPC: несовместимый render не публикует бизнес-результат.

Редактор использует только `/api/kp` с сессией. Session endpoints/общие DTO согласованы в `transport.d.ts`: documents, clients, rates, media, versions/restore, PDF, contracts, contract, jobs и artifacts/download. Публичный `/api/v1/kp` обслуживается отдельно с Bearer/scopes. Обработчики и публикация реализуются №185–187.
