# PERO CRM v2 — план реализации базовой CRM

> CRM для производства корпусной мебели на заказ. Современная замена «Бизнес в плюсе» (https://pero.b-plus.pro/).
> Стек: **Next.js (App Router) + TypeScript + PostgreSQL + Prisma + shadcn/ui + Tailwind + PWA**.
> Дата: 18.07.2026. Редакция 4 — объединяет исходный PLAN.md и все правки владельца.
> **Ревизия 07.2026: Проект = заказ клиента, содержащий изделия (ранее проект = одно изделие); см. §6, §8.**
> Связанные документы: «План экспорта данных из legacy CRM» (выполняется первым), «План плагина Базис-Мебельщик», «План плагина Telegram-бот».

---

## 1. Главный принцип

**Простота превыше всего.** Воркфлоу понятен ребёнку: открыл телефон → увидел свои задачи → нажал «Выполнено» → увидел, сколько заработал. Аналитику и «умные» отчёты на первом этапе не делаем.

## 2. Почему не дорабатываем v1

Разбор v1 показал: реальный CRUD только у проектов; импорт сломан архитектурно (связи по именам, не по ID); 83–88% пустых «Этап»/«Статус» в CSV; нет расчёта ЗП, PWA, роли монтажника. **Пишем v2 с нуля.**

## 3. Этап 0 — экспорт legacy (ЗАДАЧА №1, до первой строки кода)

Выполняется по отдельному документу **«PERO CRM v2 — План экспорта данных из legacy CRM»**: полная read-only выгрузка всех таблиц, связей (по ID) и файлов, результат — PostgreSQL-база `legacy_*` + JSON-схема + дерево файлов + отчёт верификации. **Только после зелёного отчёта начинаем писать код.**

## 4. Роли и права (6 ролей)

Две роли с полными правами: **Администратор** (IT-специалист, оплата 3% с оборота организации) и **Директор** (отдельная роль с теми же правами, но **зарплата не считается** — он получает остаток прибыли организации после вычета зарплат остальных).

## 5. Журнал изменений (логи) — обязательная функция

**Каждый чих в CRM логируется**: кто, что, когда сделал, прошлое состояние → новое состояние, источник действия (веб / Telegram / плагин). Примеры: менеджер изменил прайс — директор видит в журнале «было 45 → стало 50, кто, когда»; администратор поменял статус задачи — визуально итог тот же, что и от работника, но в журнале запись, что это сделал администратор.

- Одна сущность `ChangeLog`: автор, сущность, id записи, поле/действие, было → стало, дата-время, источник.
- Просмотр: администратор и директор; фильтры по сотруднику, сущности, периоду. В карточке каждой сущности — своя локальная «История».
- Это пользовательская функция контроля (входит в MVP). Отдельная инфраструктура аудита и бэкапов — **выносится из этого плана**, будет описана владельцем позже отдельным планом.

## 6. Воркфлоу проекта — радикально упрощённый

В legacy две лестницы (6 статусов заявки + 9 этапов заказа) — избыточно. Клиент часто приходит **с готовым дизайн-проектом**, и половина этапов просто не нужна. Лучшая практика корпоративных CRM (воронка продаж как в AmoCRM/Bitrix24/HubSpot + управление исполнением задачами): **этапы — короткая понятная воронка для руководства, вся детализация процесса — задачи внутри проекта**, а не новые этапы.

**Две сущности вместо одной:** **Проект** — заказ клиента (название, клиент, менеджер, инженер, адрес, валюта, создатель, даты; заявка и заказ — одно и то же на разных этапах); **Изделие** — единица производства внутри проекта (кухня, шкаф, прихожая…). Изделий в проекте может быть много — заказ «мебель на весь дом» содержит десятки изделий. Воронка этапов живёт на проекте, производственный цикл каждого изделия — его собственные статусы (см. ниже).

**Воронка проекта — 5 основных этапов:**

1. **Лид** — новое обращение (звонок, сайт, Авито).
2. **Просчёт** — считаем и согласуем стоимость. *Пропускается, если клиент пришёл с готовым проектом и ценой.*
3. **Договор** — подписан, получен аванс.
4. **В работе** — проектирование (Базис), производство, отгрузка, монтаж. Всё это — задачи внутри проекта, а не этапы: автоматизация (плагин Базиса) создаёт задачи сама, и «проскакивать» нечего.
5. **Завершён** — установлено и оплачено.

**Служебные состояния проекта:** **Отказ** (обязательная причина + комментарий, с любого этапа), **Пауза**, **Рекламация** (см. §6.3).

**Статусы изделия (6, проще этапов проекта):** **Проектирование** → **В производстве** → **Доставка** → **Установка** → **Готово** + служебное **Рекламация**. Изделия одного проекта могут находиться на разных статусах (кухня уже в производстве, шкаф ещё проектируется). Каждая смена статуса изделия фиксируется в истории статусов изделия и в журнале изменений.

Переходы **свободные**: карточку можно перетащить из любого этапа в любой (как в Trello) — система не заставляет проходить этапы последовательно; если для перехода не хватает данных (напр. причина отказа) — мини-форма добора прямо при перетаскивании. Каждый переход фиксируется в истории этапов и в журнале изменений.

### 6.1. Уведомления

По умолчанию администратор, директор и менеджер получают уведомления **на каждый чих в организации** (любое изменение состояния проекта, задач, импорты, дедлайны). Администратор, директор и менеджер могут **настраивать свои типы уведомлений** (вкл/выкл по типам, по умолчанию всё включено). Работник, монтажник и инженер настраивать уведомления **не могут — сознательно**: они всегда получают свои уведомления («вам назначена задача», дедлайн, изменения по их задачам).

### 6.2. Замер — как задача, а не сущность

Отдельная таблица «Замеры» (legacy 261) не нужна. **Замер = типовая задача «Замер»** внутри проекта (назначается на замерщика). Результат замера — файлы: при выполнении задачи система просит приложить фото/замерный лист; файлы попадают в проект с категорией «Замер» и видны всем, кому виден проект. Просто для понимания (одна механика «задача + файлы» на всё) и правильно инженерно (данные не расползаются по отдельным сущностям, история в одном месте).

### 6.3. Рекламация — переоткрытие завершённого проекта

Рекламация = возврат/доработка закрытого заказа. Грамотно и по бизнесу, и технически: **не новый проект и не отдельная сущность, а служебное состояние «Рекламация» — и у проекта, и у изделия**. Брак по конкретному изделию — изделие переводится в «Рекламацию»; проблема по заказу в целом — проект из «Завершён» переводится в «Рекламацию» (обязательные поля: причина, описание, виновная сторона). Внутри создаются задачи доработки и расходы — они привязываются к проекту (и к изделию, если речь о нём) и уменьшают его маржу (видно реальную экономику с учётом брака). По закрытии — снова «Завершён»/«Готово». История рекламаций хранится в карточке проекта и изделия.

## 7. Канбан как вид по умолчанию

- **Канбан-доска — вид по умолчанию** для проектов (колонки = этапы §6) и задач (колонки = статусы). Перетаскивание как в Trello: плавный drag-n-drop (dnd-kit), работает на тачскрине, оптимистичное обновление с откатом при ошибке. На карточке проекта: номер, клиент, изделия, сумма (по правам), дней на этапе с подсветкой зависших.
- **Табличный вид** — по клику на переключатель. **Выбор сохраняется автоматически** per user + per раздел (`UserPreference`) — при перезаходе вид тот же.
- На мобильном — горизонтальный свайп колонок.

## 8. Доменная модель

Базовые сущности: User, Client, Project, Product, ProjectStageHistory, ProductStatusHistory, Work, Task, PriceItem, PayrollEntry, Payout, Payment, CashAccount, ExpenseArticle, Nomenclature, StockMovement, Communication, File + новые:

| # | Сущность | Назначение |
|---|---|---|
| 18 | **Plugin / PluginSetting** | Модули: статус, права, настройки |
| 19 | **TaskTemplate / WorkTemplate** | Шаблоны работ и задач по типу изделия (для плагина Базиса) |
| 20 | **ImportBatch** | Сеанс импорта из Базиса (аудит импорта, откат) |
| 21 | **Notification / NotificationPreference** | Уведомления и их настройки (настройка — только админ/директор/менеджер) |
| 22 | **TelegramLink** | Привязка Telegram-аккаунта |
| 23 | **UserPreference** | UI-предпочтения: вид разделов (канбан/таблица) и пр. |
| 24 | **ChangeLog** | Журнал изменений: кто/что/когда/было→стало/источник |
| 25 | **TimeEntry** | Запись времени по задаче: источник (таймер/ручной ввод), старт-стоп, минуты |

Ключевые поля:
- **User**: роль (admin/director/manager/engineer/worker/mounter), схема оплаты: `сдельная` / `% от стоимости` (размер %) / `% от оборота` (размер %) / `без расчёта` (директор).
- **Project** (заказ клиента): номер, название, клиент, менеджер, **engineerId** (инженер — на него % от стоимости, §10), адрес, основная валюта, создатель, даты. Этапы воронки — на проекте (§6), история — **ProjectStageHistory**. Платежи, кассы, маржа, экономика — на проекте (§11). Стоимость проекта = сумма цен его изделий.
- **Product** (изделие): номер вида «<номер проекта>-<порядковый>» (П-2026-001-1), статус (6 статусов, §6; история — **ProductStatusHistory**), **expectedPrice** — цена изделия (цена только на изделии, в валюте проекта), описание (тех. блок, правит инженер).
- **Task / Work**: `projectId` обязателен (проект), `productId` опционален (задача/работа может быть на проект в целом или на конкретное изделие). **Task**: `assigneeId` nullable (без исполнителя = черновик); **TaskDependency** (зависимости, DAG); **estimateMinutes** (§9); **spentMinutes** (сумма из TimeEntry).
- **File**: на проекте (`projectId`), опционально + изделие (`productId`); категория (фото/чертёж/КП/замер/документ/прочее) + пояснение; **число вложений к проекту не ограничено**; оригинал доступен всегда. Коммуникации — на проекте.
- **Payment**: сумма, валюта, **курс на момент внесения** (§11), эквивалент в валюте проекта; привязан к проекту.
- **PayrollEntry**: % инженеру начисляется от суммы цен изделий проекта при первом переходе проекта «В работе» (§10).
- **Склад (§12)**: потребность (**ProjectMaterial**) и движения (**StockMovement**) — на изделии (`productId`); на проекте — сводный агрегат по его изделиям.

Все деньги — `Decimal`. Все сущности из legacy несут `legacyId` + `legacyTable`.

## 9. Задачи, работы, прайсы и время

- Прайсы из legacy (221 расценка); управляют администратор, директор и менеджер; любое изменение — в журнал изменений. Цена фиксируется в работе на момент назначения (смена прайса не переписывает прошлое).
- Статусы задачи: **Черновик** (нет исполнителя) → **Новая** → **В работе** → **Выполнена**. В «Выполнена» её переводит сам исполнитель (одна кнопка), а также менеджер/админ/директор — визуально одинаково, в журнале видно, кто именно. Начисление денег — при «Выполнена».
- Зависимости: задача блокируется, пока предшественники не выполнены.
- **Временная оценка (estimateMinutes).** При создании задачи проставляется автоматически — **среднее фактическое время идентичных задач из истории организации** (тот же вид задачи/расценка/шаблон; пока истории нет — значение из шаблона или пусто). Менеджер (и админ/директор) может изменить оценку в любой момент, пока задача не закрыта.
- **Фактическое время (spentMinutes)** — два способа ввода:
  - **Таймер**: в задаче кнопка «Старт» → время идёт → **большая кнопка «Стоп»** останавливает и записывает факт. Таймер живёт на сервере (переживает перезаход/другое устройство), у пользователя один активный таймер. Работнику не нужно ничего считать — время считается само, пока он работает.
  - **Ручной ввод**: внести затраченное время числом (для случаев, когда таймер забыли).
- Карточка задачи показывает «оценка / факт» — руководство видит, где оценки расходятся с реальностью (база для будущей аналитики, не в MVP).

## 10. Зарплата

Схемы оплаты (задаются в карточке сотрудника):

1. **Сдельно за операцию**: расценка × количество × доля исполнителя. Начисление при переходе работы/задачи в «Выполнена».
2. **% от стоимости**: напр. инженер — % от стоимости спроектированного. **Этап начисления — передача проекта в производство** (первый переход проекта в «В работе»): на этом работа инженера закончена. Начисляется **от суммы цен всех изделий проекта**, запись одна на проект.
3. **% от оборота организации**: напр. IT-администратор — 3% с оборота за расчётный месяц.
4. **Без расчёта**: директор — получает остаток прибыли после зарплат, в системе ему зарплата не считается.

- **Валюта зарплаты** — единая, задаётся в настройках CRM администратором, по умолчанию **BYN**; все начисления и расчётники показываются в ней.
- **Расчётник real-time** «Моя зарплата»: начислено за месяц + детализация − выплаченное. Обновляется в момент выполнения задачи.
- **Выплаты**: вносит администратор; история по месяцам; закрытие месяца — сводка по сотрудникам с **экспортом в CSV**.

## 11. Финансы и мультивалютность

Раздел «Финансы» и экономика проекта — **только администратор и директор** (у менеджера и инженера вкладки нет вообще).

- Экономика проекта: ожидаемая цена (**= сумма цен изделий проекта**), оплаты, расходы (ЗП + материалы + прочее; **складские расходы собираются через изделия проекта**, §12), маржа с цветовым индикатором.
- **Валюты: BYN, RUB, USD, EUR.** Любой платёж/расход — в любой из 4 валют. **Курс подтягивается автоматически с сайта НБ РБ** в момент внесения операции и **сохраняется как запись о курсе в самой операции** (сумма, валюта, курс, дата курса, эквивалент в валюте проекта). Курс можно поправить вручную. Отдельного кэша курсов нет — историчность обеспечивается самими записями.
- У проекта основная валюта, итоги — в ней. Кассы — каждая в своей валюте.

## 12. Склад и номенклатура (MVP)

Без изменений по сути: справочник из legacy, приход/расход/возврат, остатки из движений, простые резервы. Полный WMS — за рамками MVP.

- **Потребность (резерв) и складские списания — на изделии**: строки потребности и движения расхода/возврата привязаны к конкретному изделию (`productId`), цена списания — учётная.
- **На проекте — сводный read-only агрегат** потребности по всем его изделиям (правки — только в карточке изделия).
- Бейдж **«Нехватка материалов»** агрегируется по изделиям проекта: если хотя бы одно изделие не обеспечено, проект помечается в карточке и на канбане/в таблице.

## 13. Хранение файлов

Файлы хранятся на диске (docker volume `/app/uploads`), структура папок по проектам (`uploads/<projectId>/`), превью фото (sharp), метаданные в БД. Файл привязан к проекту, опционально — дополнительно к изделию (`productId`). Требование «через 5 лет найти файл прикреплённым к проекту и скачать» — обязательное. **Вынос на NAS/S3-хранилище и бэкапы — не входят в этот план**: NAS ещё не развёрнут, владелец опишет это позже отдельным планом.

## 14. Плагинная архитектура (Plugin Core — инфраструктура ядра)

- **Плагин = нативный пакет в монорепозитории** (`packages/plugins/<id>/`) на том же стеке: Next.js (RSC) + TypeScript + shadcn/ui + общие токены темы. Никаких iframe — интеграция неотличима от встроенного функционала.
- **Производительность:** UI плагина через `next/dynamic` — не грузится, пока экран не открыт; отключённый плагин не рендерится; общая сборка/типизация/линт.
- **Манифест** `plugin.ts`: id, версия, `apiVersion` (N и N-1), `permissions`, `hooks`, `slots`, `commands`, `settingsSchema`.
- **Точки расширения:** UI-слоты (`project.tab`, `project.action`, `dashboard.widget`, `task.action`, `settings.page`), шина доменных событий (outbox-таблица PostgreSQL), обработчики типов файлов, команды (UI/cron/REST).
- **Plugin SDK + REST `/api/v1`** с токенами; OpenAPI-документация + шаблон `_template/`.
- **Управление:** «Настройки → Модули» — вкл/выкл одной кнопкой (данные не удаляются), автоформа настроек, журнал запусков плагина.
- **Установка только ручная**, публичного магазина нет. **Безопасность прагматичная:** доверенный код в процессе приложения; проверка `permissions` + RBAC; действия плагина пишутся в журнал изменений с `actor = plugin:<id>`.

## 15. Интерфейс (shadcn/ui, mobile-first)

- Тёмная/светлая тема, русская локаль, крупные контролы.
- Экраны: Дашборд; **Канбан** (по умолчанию)/Таблица проектов-заказов и задач; **Карточка проекта** («Общее», **«Изделия» — мини-канбан изделий по статусам с перетаскиванием и добавлением**, «Задачи», «Файлы», «Материалы» — сводка по изделиям, «Коммуникации», «Финансы» — только админ/директор, «История»); **«Изделия» — общая таблица всех изделий**; **Карточка изделия** (статус с быстрой сменой, цена, тех. блок, вкладки «Работы и задачи», «Материалы», «Файлы», «История»); «Мои задачи» (с таймером и большой кнопкой «Стоп»); «Моя зарплата»; Справочники; Финансы; Склад; Журнал изменений; Настройки → Модули.
- PWA: manifest + service worker (Serwist), установка на экран; офлайн-очередь и web-push — фаза 8. Цель: первый экран < 1 c на 4G.

## 16. Техническая архитектура

- Next.js 15+ / TypeScript strict, App Router, server actions + zod; **плюс публичный REST `/api/v1`** (Plugin API и внешние интеграции).
- Prisma + PostgreSQL 16, миграции в git.
- Auth.js v5: credentials, JWT-сессия (userId + роль), middleware, CSRF из коробки.
- Redis осознанно отсутствует. Бэкапы и аудит-инфраструктура — вне этого плана (отдельный план владельца позже).
- Деплой: docker-compose (`app`, `postgres:16`, `caddy` — HTTPS обязателен для PWA) на Mini-PC Proxmox. Обновление: `git pull && docker compose up -d --build`.

## 17. Миграция данных (после экспорта legacy и готовности схемы v2)

Staging-схема `legacy_*` (результат плана экспорта) → трансформация строго по ID-связям с логом маппинга; «удалённые» не импортируем, «архив» с флагом; сверка контрольных итогов (число проектов, ЗП по месяцам, обороты касс, остатки склада); параллельный запуск 1–2 недели; legacy → read-only навсегда.

Маппинг на две сущности (§6, §8): **заказ legacy → Проект** (заказ клиента), **изделие заказа legacy → Изделие** внутри этого проекта (номер «<номер проекта>-<порядковый>»); `legacyId` + `legacyTable` проставляются на обеих сущностях.

## 19. Риски

| Риск | Снижение |
|---|---|
| Потеря данных при экспорте legacy | Отдельный план экспорта с верификацией — до кода |
| Связи по именам (ошибка v1) | Только ID-связи, лог маппинга, сверка итогов |
| Непринятие сотрудниками | Экран работника = задача + таймер + «Выполнено»; обучение 15 мин; параллельный запуск |
| Scope creep | Жёсткие фазы; аналитика/3D/аудит/бэкапы — отдельными планами позже |
| НБ РБ недоступен при вводе платежа | Ручной ввод курса; курс фиксируется в записи операции |
| Таймер забыли остановить | Автостоп по таймауту (напр. 12 ч) с пометкой; ручная правка факта менеджером с записью в журнал |
